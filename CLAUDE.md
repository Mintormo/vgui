Этот файл даёт указания Claude Code (claude.ai/code) при работе с кодом в этом репозитории.

> **ОБЯЗАТЕЛЬНО прочитайте [PROJECT.md](PROJECT.md) перед началом работы.** Здесь - только
> неизменные правила и рабочие команды. В `PROJECT.md` - подробное устройство каждой подсистемы:

## Что это за проект

vgui - GUI-библиотека на языке [V](https://vlang.io) поверх SDL3. Корень репозитория - сам модуль
`vgui`. Библиотека самостоятельна и ничего не знает о биндингах. Соседние проекты:

- `../vgui-capi` - C-ABI-мост (`libvgui.so`, функции `vgui_*`, реестры-якоря GC);
- `../vguipy` - Python-обёртка над `libvgui.so` через ctypes;
- `../vraw` - приложение на vgui (потребитель API).

Компилятор находит модуль через симлинк `~/.vmodules/vgui -> ~/projects/vgui`. Правка публичного API
(переименование, смена сигнатуры, `pub` → не `pub`) может сломать vgui-capi и vraw - проверяйте их сборку.

## Команды

Компилятор V не в `PATH` - `~/soft/v/v`. Проект собирается **новым** компилятором V; откат на старый,
расхождения компиляторов и обходы их багов - PROJECT.md, «Компилятор V». SDL3 не бандлится, должна
стоять в системе (PROJECT.md, «Зависимости SDL3»).

```bash
# тесты — все *_test.v (из корня, дисплей не нужен)
SDL_VIDEODRIVER=dummy ~/soft/v/v -enable-globals test .

# один тест
SDL_VIDEODRIVER=dummy ~/soft/v/v -enable-globals test layout_test.v

# снапшоты рендера: намеренно изменили вид - перезаписать эталоны, посмотреть и закоммитить
VGUI_UPDATE_SNAPSHOTS=1 SDL_VIDEODRIVER=dummy ~/soft/v/v -enable-globals test snapshot_test.v

# примеры (статически включают vgui — ПЕРЕСОБИРАТЬ после правок движка)
PATH="$HOME/soft/v:$PATH" ./examples/build.sh
~/soft/v/v -enable-globals run examples/01_label.v
```

«В демо не работает, а тесты зелёные» почти всегда означает устаревший бинарник примера.
`__global`-переменные модуля не видны из `_test.v` - тестам нужны функции-аксессоры.
Новые тесты интерфейса пишите через `testkit.v` (`new_test_ui`, `t.click_widget`, `t.capture`,
`match_snapshot`), а не копией своего окна/захвата кадра: каждый `_test.v` компилируется отдельно,
общий код живёт только в модуле. Упал `snapshot_test.v` - откройте `testdata/snapshots/*.actual.png`.

## Правила V-кода и демо

- **Не используйте указатели на анонимные структуры** - `&struct { mut: n int }{}` даёт невалидный C
  (`incompatible types when initializing type 'T *'`). Объявляйте именованную структуру на уровне модуля.
- **`chan fn ()` сегфолтится при push** - оборачивайте в структуру (`chan Posted`).
- **Никакого длинного тире (`—`) в заголовках окон и в `vgui.label(...)` демо** - глиф не рендерится
  (кракозябра/квадрат). Пишите дефис-минус `-`. В TextArea/CodeEditor тире допустимы.
- В V `shared` - ключевое слово, не называйте так переменные.
- **Суффиксы ОС в именах файлов** (`_macos`, `_linux`, `_windows`, `_darwin`, `_nix`...): V собирает
  такой файл только на этой ОС - `theme_macos_test.v` на Linux молча SKIP. Не называйте так файлы
  без намерения.
- Обходы багов компилятора V (например, как сохранять замыкание в поле) - PROJECT.md, «Компилятор V».

## Комментарии и читаемость кода

Код пишется для человека, который захочет его прочитать и разобраться, - не только для компилятора.

- **Подробные комментарии с описанием логики обязательны.** У каждого модуля/файла - шапка: что в нём и
  как он связан с остальным. У каждой нетривиальной функции, структуры и метода - что делает, что
  принимает и возвращает, какие у неё предусловия и побочные эффекты.
- **Внутри функций - пояснения к шагам алгоритма**: что происходит и, главное, почему именно так
  (инвариант, найденный баг, ограничение SDL/V/ctypes). Ссылка на раздел PROJECT.md не заменяет
  комментарий, а дополняет его.
- **Читаемость важнее краткости**: говорящие имена, короткие функции, промежуточные переменные с
  понятными именами вместо длинных выражений, без «умных» трюков там, где хватает простого кода.
- Меняете код - обновите и его комментарии: устаревший комментарий хуже отсутствующего.
- Сгенерированный код (`vgui_capi_gen.v`, `_capi_sigs.py`) комментируется через спеку (`doc=`, `pynote=`).

## Ключевые инварианты (подробности - в PROJECT.md)

**Потоки** («Мост из фоновых потоков», «Глобальное изменяемое состояние»). Всё - в одном главном потоке,
локов нет намеренно, один `App` на процесс. Единственный мост из фонового потока - `app.post()`. Свой цикл:
`pump_events()` / `render_all()`.

**Тег типа** («Тег типа виджета»). Первое поле каждой структуры виджета - `type_tag int = kind_<name>`
(константы - `widget_kinds.v`, номера - часть ABI, занятые не перенумеровывать). Поле обязано оставаться
**первым** (читается по смещению 0) и задаётся значением по умолчанию, а не присваиванием в фабрике.

**Указателя на родителя у виджета нет намеренно** («Дерево виджетов»). Любой сырой `voidptr` на виджет в
долгоживущей структуре (фокус-учёт, оверлеи) пинит его для GC - такую запись обязательно снимать при
уничтожении виджета.

**Время жизни** («Время жизни SDL-текстур», «Временные модальные диалоги»). `SDL_DestroyTexture` - только
при `is_renderer_alive_gen(renderer, gen)`. Временные диалоги сами делают `app.remove_dialog` +
`win.cleanup()` на каждом пути выхода. Байты, пришедшие извне (шрифты, картинки), храните копией (`.clone()`).

**Шрифты** («Архитектура рендеринга»). `FontSet` в `g_font_cache` общий и со счётчиком ссылок: окно держит
одну ссылку, меняет набор только через `Window.reload_scaled_fonts()`. Никогда не переинициализируйте
`ctx.fonts` на месте и не храните `TTF_Font` в полях виджетов. Кэш текстур текста проверяет коллизии хэша -
поля верификации не удалять.

**Контейнеры.** `remove`/`clear` - detach по тождеству указателя, структура ребёнка не освобождается.

**Раскладка** («Layout: measure/arrange», «Фаза arrange», «Дерево виджетов»). Один `add(w)` -
размер из содержимого; `flex:` - доля остатка **от нуля**; `min:`/`max:`/`align:`. Пикселей нет
(намеренно). Окна/диалоги с размером 0 - по содержимому; в них растягиваемому виджету `flex` не давать
(`add(w)` растёт от `measure()`). Каждому виджету, даже внутреннему, - `measure()`. `measure()` обязан быть
чистым (его результат кэшируется на проход измерения). Каждый тип виджета реализует `Layouted`
(`bounds_of`/`set_bounds`) в `widget_tree.v` - иначе рисуется в (0,0) нулевого размера. Контейнер с частично
рисуемыми детьми - ещё `HitTestable`. Bounds детям контейнер раздаёт **только в `arrange()`**
(`Arrangeable`), не в `draw()`; анимация, от которой зависит раскладка, шагает в `arrange()` раз за
`ctx.frame_no`.

**Инвалидация** («Инвалидация и dirty regions»). Никогда не пишите `ctx.needs_animation = true` напрямую -
только `mark_anim` / `mark_anim_rect` (иначе анимация замирает); виджет, чья анимация не выходит за свои
`bounds`, обязан звать `mark_anim_rect(reason, bounds)`, а не `mark_anim` - иначе наведение мышью снова
перерисовывает всё окно. `mouse_move` - единственное событие, которое НЕ зовёт `invalidate_all()`: у него
точечный путь `Window.invalidate_hover_change`. Сеттеры виджетов кадр не инвалидируют - в своём цикле зовите
`Window.invalidate*`. Анимации виджетов - только через `Anim` (`anim.v`, «Анимации»): `a.update(цель, ctx)`
в `draw()`/`arrange()`, пока вернула true - `mark_anim_rect`; не `x += (цель - x) * k` (зависит от fps).
Тесты, рисующие кадры подряд, ставят `win.ctx.anim_fixed_dt`. Новый путь рисования сам выставляет blend
mode. Масштаб рендера выставляется заново после каждого `SDL_SetRenderTarget`; HiDPI проверять через
`set_ui_scale`.

**Фокус** («Фокус-учёт»). Каждому focusable-виджету - свой элемент `FocusKind` (cast «похожим» типом = UB);
`fm.current` - индекс, корректируется при удалении записи.

**Неактивное состояние** («Неактивное состояние (enabled)»). У каждого виджета поле `enabled bool = true`
(у HBox/VBox/WindowTitleDrag - `box.enabled`). В `draw()` - один раз `en := ctx.is_enabled(w.enabled)` и
дальше только `en` (учитывает отключённых предков); focusable регистрируется при `en`, иначе
`ctx.focus_block(&w)`. Контейнер рисует детей между `ctx.begin_disabled(own)`/`end_disabled(own)` и при
`!enabled` не передаёт им ввод (`is_input_event`).

**Оверлеи попапов** («Оверлеи попапов»). Один слот на окно с владельцем: только
`ctx.set_overlay(owner, draw, ev, close)` / `ctx.clear_overlay(owner)`, никогда не присваивание
`overlay_cb`/`overlay_ev`. `owner` - адрес самого виджета.

**Нативные диалоги, трей, drag-and-drop** - соответствующие разделы PROJECT.md. Коротко: `message_box`
кастомный (не `SDL_ShowMessageBox`); нативного диалога цвета/даты нет; трей - не виджет, клика по иконке
в SDL3 нет.

## Добавление нового виджета

В библиотеке (подробно - PROJECT.md, «Добавление нового виджета (часть библиотеки)»):

1. Константа `kind_<name>` в `widget_kinds.v` (следующий свободный номер); структура виджета **первым полем**
   `type_tag int = kind_<name>` + строка в `widget_tag_test.v`.
2. `widget_tree.v`: `bounds_of`/`set_bounds` (+ `child_widgets`/`hit_children` для контейнеров, собственное
   поле `visible bool`) и проверка в `widget_tree_test.v`. Контейнер - ещё `arrange()`.
3. Поле `enabled bool = true` и неактивный вид через `en := ctx.is_enabled(...)` (сложному содержимому -
   `ctx.draw_disabled_veil`); контейнер - `begin_disabled`/`end_disabled` вокруг детей.
4. По желанию: `measure()` в `layout_measure.v`; `FocusKind` + ветки в `focus.v` для фокусируемых.
5. Пример `examples/NN_виджет.v`.

Чтобы виджет появился в биндингах - C-ABI в `../vgui-capi` (его `CLAUDE.md`, чек-лист), затем класс в `../vguipy`.
