архитектура, инварианты, причины принятых решений и найденные грабли. Краткая
выжимка и рабочие команды - в `CLAUDE.md`; здесь - всё, что нужно, прежде чем

## Тег типа виджета (`widget_tag.v`)

`_kind` — это **обещание** Python-класса, а не факт: через C-ABI виджет приходит парой `(voidptr, kind int)`, и до появления тега неверное число (свой класс с чужим `_kind`, сырой handle из `tree.widget("id")`, ошибка в другом языке-биндинге) давало приведение чужой памяти к `&Label` — порчу памяти без единого шанса её заметить.

Поэтому **первое поле каждой структуры виджета** — `type_tag int = kind_<name>`. Значение по умолчанию проставляет V при любом создании: фабрика, голый литерал `&Label{}`, сборка дерева из YAML в `ui_builder.v`. Отдельного шага «не забыть записать тег» в фабриках нет — и не должно появляться.

Так как поле объявлено первым, оно лежит по смещению 0, и тег читается, не зная типа, — через `WidgetTagHeader` (`widget_type_tag(ptr)` / `widget_tag_matches(ptr, kind)`). **Инвариант смещения обязателен**: если `type_tag` уедет вниз по структуре, `widget_type_tag` вернёт чужие байты. Проверяется в `widget_tag_test.v` — тест создаёт каждый из типов и сверяет прочитанный тег с ожидаемым `kind`.

Сверка живёт в `vgui_resolve_widget` — единственной точке приведения `(ptr, kind)` к типизированному указателю. Несовпадение — не паника, а `none`: capi-функция возвращает 0, `_check_added` превращает 0 в `TypeError`, причём различает два случая (kind вообще не добавляется в контейнеры против «`_kind` врёт про объект» — для второго Python читает тег через экспорт `vgui_widget_tag`). Цена — одно сравнение на вызов.

Чего тег **не** ловит: висячий указатель на уже освобождённую структуру (в её памяти тег может ещё лежать) и прямые касты в узкоспециализированных capi-функциях (`vgui_label_set_text` и подобные), где `kind` не передаётся, а тип задан самой функцией — туда `_kind` от пользователя не попадает.

## Время жизни SDL-текстур и рендерер (реестр живых рендереров)

SDL привязывает каждую текстуру к создавшему её рендереру; `SDL_DestroyRenderer` **уничтожает заодно все текстуры этого рендерера**. Поэтому виджет, владеющий текстурой (сейчас это только `ImageView`), **не должен** вызывать `SDL_DestroyTexture` после того, как его окно/рендерер исчезли — это use-after-free / двойное освобождение. Такое возможно при недетерминированном teardown со стороны GC Python: цепочка `__del__` обёртки `ImageView` → `vgui_destroy` → `iv.destroy_texture()` может выполниться *после* того, как окно уже было очищено.

Защита: глобальный **реестр живых рендереров** в `sdl3_window.v` — `g_live_renderers []LiveRenderer` (пары `{ptr voidptr, gen u64}`) с функциями `register_renderer` / `unregister_renderer` / `renderer_generation` / `is_renderer_alive` / `is_renderer_alive_gen`. `Window` регистрирует свой рендерер сразу после `SDL_CreateRenderer`; `Window.cleanup()` вызывает `unregister_renderer` **до** `SDL_DestroyRenderer`.

**Защита от ABA — generation-счётчик.** Голое сравнение указателей недостаточно: новый рендерер может быть аллоцирован по адресу умершего, и устаревший снимок указателя выглядел бы «живым» (то же обоснование, что у монотонных `cb_id` в `_lib.py`). Поэтому каждая регистрация получает монотонный `gen u64` (`g_renderer_gen`, никогда не переиспользуется; 0 — невалидное поколение). `ImageView` хранит пару `tex_renderer` + `tex_renderer_gen` (снимаются в `ensure_texture_loaded` через `renderer_generation(ctx.renderer)`); и `destroy_texture()`, и swap-destroy внутри `ensure_texture_loaded` вызывают `SDL_DestroyTexture` **только если `is_renderer_alive_gen(iv.tex_renderer, iv.tex_renderer_gen)`** — иначе SDL уже освободил текстуру (или по адресу живёт другой рендерер), и они просто обнуляют дескрипторы. Нулевой (nil) рендерер и `gen == 0` считаются мёртвыми. `unregister_renderer` ищет по указателю — это корректно, потому что реестр содержит только живые рендереры, а два живых не могут делить адрес. Все рендереры (Window + `Dialog.win`) уничтожаются через единую точку `Window.cleanup()`, поэтому регистрация/снятие симметричны. Так же устроен кэш картинок `MarkdownView` (`MdImageTexture`: текстура + рендерер + поколение): запись чужого или мёртвого рендерера не используется и не освобождается повторно (тест `markdown_view_test.v`). Юнит-тест: `renderer_registry_test.v` (фиктивные указатели, SDL не нужен) — запуск `v test renderer_registry_test.v` из корня.

## Layout: measure/arrange (`layout.v`)

Раскладка двухпроходная, как в Qt/WPF: сначала виджеты сообщают желаемый размер (**measure**), затем контейнер раздаёт им `bounds` (**arrange**, существующий `set_widget_bounds`).

Интерфейс `Widget` (`draw` + `handle_event`) **не менялся**. Измерение подключается отдельным опциональным интерфейсом:

```v
pub interface Measurable {
	measure(ctx &RenderContext) SizeHint
}
```

`measure_widget(w, ctx)` — единая точка входа: если виджет реализует `Measurable`, берётся его `SizeHint`; если нет — размер восстанавливается из текущих `bounds` (`get_widget_bounds`) с политикой `expanding`, то есть старые раскладки ведут себя как раньше. Благодаря этому пользовательские виджеты не обязаны ничего реализовывать.

`SizeHint` несёт желаемый размер, `min`/`max` по каждой оси и `SizePolicy` (`fixed` / `preferred` / `expanding`). Реализации `measure()` для встроенных виджетов собраны в одном файле — `layout_measure.v`; отрисовка остаётся в файлах самих виджетов. **`measure()` обязан быть чистым**: не менять состояние виджета и не трогать renderer (только шрифтовые метрики) — его зовут несколько раз за кадр и до первого кадра.

**Шрифт для измерения — `ctx.get_font_immut(style, size)`; шрифт ещё не открытого размера он открывает
сам** (заполняет общий кэш `FontSet` — для вызывающего это мемоизация, `measure()` остаётся чистой). До
14.10.2026 он при промахе отдавал regular базового размера, рассчитывая на «прогрев» в `draw()`: первая
раскладка (до первой отрисовки) мерила метку `size=20` шрифтом 15 пт, со второго кадра всё ниже неё
сдвигалось на 5 px, а перерисовывались только dirty-области — на экране оставались куски кадра со старыми
позициями (полоски поверх рамок полей при наведении в примере 56). Тест — `font_measure_test.v`.

**Кэш `SizeHint` (`measure_cache.v`, аудит 3.A).** `measure_widget` кэширует результат Measurable-виджета на один **проход измерения**. Зачем: `BoxLayout` спрашивает одного и того же ребёнка дважды за проход (`content_size()` и `child_main_item()`, плюс третий раз при `cross_align != .stretch`), и на каждом уровне вложенности это множится — измерение поддерева росло как 2^глубина, причём каждый `Label`/`Button` идёт в метрики TTF.

- **Срок жизни — один проход, не кадр.** Проход открывает `measure_pass_begin()`: его зовёт `Window.arrange()` (все измерения одного arrange видят один кэш) и сам `measure_widget`, когда измерение начинается «с нуля» вне arrange (`g_measure_depth == 0 && ctx.arrange_depth == 0`) — это `fit_to_content`, `vgui_widget_measure`, тесты и свой цикл. Поэтому hint из прошлого кадра не всплывает никогда, и **отдельная инвалидация по тексту/шрифту/теме не нужна**: внутри прохода ничего из этого не меняется. `measure_pass_begin()` чистит map целиком, так что кэш не растёт и не пинит уничтоженные виджеты; поле `pass` в записи — страховка на случай, если чистка когда-нибудь пропадёт.
- **Ключ — адрес самого виджета**, а не интерфейсного значения: «толстая» структура интерфейса копируется при каждой передаче (V делает `memdup`), её адрес у каждой копии свой. Адрес читается прямо из обёртки: указатель `_object` у старого (0.5.2) и нового компилятора лежит в ней первым полем, поэтому `widget_object_addr` превращает `&Widget` в `voidptr` и читает `voidptr` по смещению 0. Приведение `&WidgetTagHeader(w)` для этого не годится: старый компилятор при нём снимает обёртку, а новый отдаёт адрес самой обёртки. Адрес берётся **до** `if w is Measurable`: после сужения типа `w` становится `&Measurable`, и `&Widget` из него уже не получить.
- **Самопроверка.** `measure_cache_enabled()` один раз за процесс сверяет адрес заведомо известного `&Label{}` с тем, что вернул `widget_object_addr`. Не совпало — кэш выключается целиком (`g_measure_cache_ok = -1`), и всё работает как до него: медленнее, но верно. Это страховка на случай, если V изменит раскладку интерфейсных значений; тест `measure_cache_test.v` ловит такое раньше.
- **Деградация к `bounds` не кэшируется** намеренно: у виджета без `measure()` hint — это его текущие `bounds`, а они меняются прямо в проходе arrange.
- **Грабли V (0.5.2).** Приведение интерфейса к указателю (`&T(w)`, `&voidptr(w)`) старый компилятор разворачивает до `_object`, а новый — нет, поэтому в `widget_object_addr` сначала `voidptr(w)`, и все шаги — отдельными переменными; параметр типа `&Measurable` даёт то же (`&(I_..._as_I_...(*w))`) — поэтому адрес и снимается до сужения; глобальная map со структурой-значением объявляется **без** инициализатора (`__global g_measure_cache map[u64]MeasureCacheEntry`), иначе старый компилятор не видит саму переменную («undefined ident»).

Тесты — `measure_cache_test.v`: адрес объекта (в том числе из массива интерфейсных значений), попадание внутри прохода, ровно одно измерение на виджет поддерева, отсутствие склейки разных виджетов, новый проход после изменения размера, некэширование виджета без `measure()`.

Ребёнок `HBox`/`VBox`/`WindowTitleDrag` добавляется **одним** методом `add(w, LayoutParams)` — как в современных фреймворках (Flutter, SwiftUI, Compose): размер берётся из содержимого, а не задаётся числами.

```v
box.add(w)                                   // естественный размер из measure()
box.add(w, flex: 1)                          // доля свободного места, от нуля
box.add(w, min: 80, max: 200, align: .center) // границы вдоль оси, выравнивание поперёк
```

| Вызов | `SizeMode` | Размер вдоль главной оси |
|-------|-----------|--------------------------|
| `add(w)` | `.auto` | естественный (`measure()`); виджет с политикой `expanding` (поле ввода, ползунок, список, холст, распорка) **растёт от него** в свободное место и сжимается до `min` |
| `add(w, flex: n)` | `.flex` | доля свободного места по весу **от нуля** (как `Expanded` во Flutter) |

`min:`/`max:` — границы вдоль главной оси, сильнее `measure()`; `align:` — `CrossAlign` этого ребёнка. Режима «жёстко N пикселей» **нет намеренно** (`add_fixed`/`add_auto`/`add_ex`, `gap()`, `Px`/`Flex`/`px()`/`flex()` удалены): размер — из содержимого, ограничения — `min`/`max`, расстояния — `spacing`/`padding`. Нужна колонка ровной ширины (подписи формы) — `min:` по самому длинному тексту (`Window.measure_text`). Виджет без `measure()` в режиме `.auto` занимает свободное место (как прежний `add(w, 1)`).

Делёж вдоль главной оси выполняет `distribute_main()`: нефлексовые дети сразу получают свой размер (зажатый в `min`/`max`); flex-дети стартуют со своей базы (у `add(w, flex:)` она 0, у растягиваемых по природе авто-детей — естественный размер) и делят остаток по весам; упёршийся в `min`/`max` фиксируется, и его доля переразделяется между остальными (поэтому цикл, а не один проход).

**Грабли «flex от нуля».** В окне или диалоге **по содержимому** (см. ниже) `add(w, flex: 1)` даёт виджету только остаток — его естественный размер в размер окна не входит. Растягиваемому виджету, который должен быть не меньше своего `measure()` (палитра `CpArea`, календарь `DpArea`), `flex` не нужен: `add(w)` — и он сам растёт от естественного размера.

Поперёк главной оси действует `CrossAlign` (`stretch` по умолчанию; `start`/`center`/`end` берут размер из `measure()`), у контейнера (`set_cross_align`) или у ребёнка (`align:`). **Виджеты фиксированного размера поперёк** (флажок, бейдж, метка в ряду — `v_policy`/`h_policy == .fixed`) при `stretch` не растягиваются: в ряду встают по центру высоты, в столбце — у левого края; явный `align:` ребёнка сильнее этого правила. `Panel`/`Stack` — контейнеры (меряются по детям). `Spacer` растягивает только вдоль своего контейнера — ряд с распоркой не становится от неё «высоким».

**Стандартная высота контролов** — `Theme.control_height` (30): кнопки, поля, списки, флажки, вкладки (`ctx.control_h()`); кнопка-значок — квадрат этой высоты.

**Окна и диалоги по содержимому.** `create_window`/`create_dialog` с `width`/`height` 0 (`auto_size`) получают размер из `measure()` содержимого: окно создаётся скрытым и показывается первой раскладкой (не уже своего заголовка), диалог подгоняется при каждом `show()`. Окно видимо сразу (`show()` — только для скрытого), диалог скрыт до `show()`. `DialogConfig.min_*`/`max_*` и `set_size_limits` ограничивают подгонку (Python: `Dialog(min_w=…, max_w=…)`). Отдельно от этого **окно не меньше содержимого**: `Window.fit_min_size()` в конце `arrange` ставит минимальный размер окна SDL по сумме `min` детей и увеличивает окно, если оно уже меньше (сменился шрифт или масштаб). Измерение защищено от циклов.

**Перенос текста.** `Label` с `wrap`: высота — по ширине (второй проход `arrange` через `g_relayout`, если ширина метки изменилась), желаемая ширина — не больше `label_wrap_pref_w` (400), минимальная — 0; поэтому окно по содержимому не вытягивается в одну длинную строку. Так же многострочна `DropZone`. `ProgressBar` с текстом — полоса по высоте строки. `TextInput.chars` — ширина поля в символах.

**Колесо мыши — флажок `wheel`** (интерфейс `HasWheel`, `set_widget_wheel`; C API `vgui_widget_set_wheel`; Python `widget.set_wheel(bool)`) у `Slider`, `ListBox`, `TreeView`, `TableView`, `TabBox`, `TextArea`, `CodeEditor`, `ImageView`, `PlotView`, `MarkdownView`, `PropertyGrid`, `Accordion`, `ScrollBox`. `wheel = false` — виджет колесо не берёт, и оно уходит родителю: ползунки внутри прокручиваемой панели не меняют значение, а панель прокручивается. `ListBox` крутится колесом **по наведению, без фокуса** и, если по оси есть что прокручивать, поглощает колесо и на краю — не отдаёт его родителю (тест `list_box_wheel_test.v`); горизонтальный список — вниз/наклон вправо = вправо, как `ScrollBox` (раньше знак был обратный). `TreeView` и `CodeEditor` пока берут колесо только при фокусе.

Прочее, что даёт фаза измерения:

- **`MenuBar.keys_when_hidden`** (08.10.2026): скрытая полоса меню (`visible = false` — не рисуется, `measure` 0, мышь не берёт) всё равно обрабатывает сочетания клавиш пунктов — для полноэкранного режима без меню.
- **Диалог — по центру экрана** (08.10.2026): `Dialog.show()` ставит его в центр монитора, на котором родитель (`dialog_center_pos`: `SDL_WINDOWPOS_CENTERED | SDL_GetDisplayForWindow`; без родителя — монитор самого диалога), а не по центру родителя. Позиция ставится и до, и ПОСЛЕ `SDL_ShowWindow`: KWin позицию, заданную скрытому окну, не берёт и ставит новое окно по своим правилам.
- `Window.fit_to_content(max_w, max_h)` / `Dialog.fit_to_content(...)` — подогнать размер вручную. У диалога размер пишется в `base_width`/`base_height`, откуда его берёт `show()`.
- `GridLayout`: дорожки (колонки/строки) **по умолчанию — по содержимому** (самый широкий/высокий виджет); растёт только дорожка с весом (`set_col_weight`/`set_row_weight`); `set_col_auto`/`set_row_auto` возвращают к содержимому. `set_col_width`/`set_row_height` удалены.
- `measure()` есть у всех встроенных виджетов, включая `MenuBar`, `DropZone`, `Splitter`, `Calendar`, `ImageBackground`, `DatePicker`, `ColorPicker`, внутренние `CpArea`/`CpPreview`/`DpArea`; `Canvas` со `stretch` — по размеру буфера; `TabBox` — заголовок + содержимое.
- Python: `box.add(w, flex=0.0, min=0.0, max=0.0, align=None)` (голое позиционное число — ошибка), `widget.measure(window) -> (w, h, min_w, min_h)`, `window.fit_to_content()`, `widget.set_wheel()`.

Тесты — `layout_test.v` (SDL и шрифты не нужны: проверки идут на виджетах вроде `Icon`, чей размер не зависит от шрифта). Запуск: `v test layout_test.v`.

## Фаза arrange (`Arrangeable`, `Window.arrange()`)

До аудита 3.A раскладка была побочным эффектом отрисовки: каждый контейнер первым делом в своём `draw()` раздавал детям `bounds`. Отсюда целый класс багов с одной причиной: hit-test работал по bounds **прошлого кадра** (переключил вкладку — следующее событие в той же пачке шло в старую раскладку, у новой вкладки `Rect{0,0,0,0}`), в `skip_draw`-кадре раскладка не выполнялась вовсе, а актуальность bounds зависела от порядка отрисовки.

Теперь раскладка — отдельный проход по дереву:

```v
pub interface Arrangeable {
mut:
	arrange(mut ctx RenderContext)
}
```

- **`arrange()` контейнера выставляет bounds ровно тем детям, которых нарисует `draw()`, и спускается в них** через `arrange_child(mut w, rect, mut ctx)` (= `set_widget_bounds` + `arrange_widget`). `draw()` контейнера bounds детям **больше не выставляет** — только рисует. Реализовано у `HBox`/`VBox`/`WindowTitleDrag` (через `BoxLayout.arrange`), `GridLayout`, `Panel`, `Stack`, `Centered`, `ScrollBox`, `Splitter`, `TabBox` (только активная вкладка), `Accordion` (секции с `anim > 0.01`), `ListBox` (виджеты-ячейки видимого диапазона строк, тот же фильтр, что у `hit_children`). Листьям `arrange` не нужен.
- `BoxLayout.layout(ctx)` и `GridLayout.layout(ctx)` оставлены **без рекурсии** — их напрямую зовёт `layout_test.v`; рекурсия живёт в `arrange()`.
- Заливка экрана для незаданных bounds (`is_bounds_unset` → весь экран) переехала из `draw()` в `arrange()`. Сюда же переехали пересчёт `eff_content_*` и клампинг скролла у `ScrollBox`/`ListBox`/`Accordion` — эти значения определяют позиции детей.
- `arrange_widget` ограничивает глубину через `ctx.arrange_depth` и `widget_tree_max_depth` (цикл `A → B → A` не переполняет стек).

**Когда вызывается** (`sdl3_window.v`):

- `Window.render()`: кадр, который рисуется, **всегда** зовёт `w.arrange()` — ровно та частота, с какой раньше раскладывали `draw()` контейнеров, поэтому по производительности не хуже. `skip_draw`-кадр зовёт `arrange_if_needed()`.
- `dispatch_event_with_app`: **перед каждым событием** — `arrange_if_needed()`. Предыдущее событие закончилось `invalidate_all()`, поэтому раскладка, изменённая им, видна следующему событию без кадра между ними. Это и есть починка устаревшего hit-test.
- `Window.arrange()` при изменении размера экрана выставляет корням весь экран (раньше это делал `render()` по `size_changed`). Для этого у окна отдельная пара `arranged_w/h`: `last_layout_w/h` по-прежнему решают «полный кадр» в `render()`, а arrange может пройти раньше — перед событием — и не должен съесть `size_changed`.

**`ctx.layout_dirty`** (по умолчанию `true`) взводят `invalidate()`, `invalidate_all()` и `request_layout()`, снимает `Window.arrange()`. Сейчас это консервативно: любая инвалидация — повод пересчитать раскладку (включая мигание курсора через `mark_anim_rect`), что совпадает с прежней частотой. Разделить «грязно для отрисовки» и «грязно для раскладки» имеет смысл вместе с кэшем `SizeHint` и точечной инвалидацией hover (аудит 3.C). **Контракт тот же, что у отрисовки:** сеттер без инвалидации раскладку не двигает — в своём цикле зовите `Window.invalidate*`.

**Анимации, от которых зависит раскладка, шагают в `arrange()`, а не в `draw()`.** Пример — `Accordion`: позиция ребёнка секции зависит от `anim` всех секций выше. Если шаг остаётся в `draw()`, он происходит *после* arrange того же кадра, и заголовки рисуются на шаг анимации впереди разложенных детей. Но arrange зовут ещё и перед каждым событием, поэтому шаг защищён **номером кадра**: `ctx.frame_no` растёт в `render()` только для рисуемого кадра, `Accordion.anim_frame` помнит номер последнего шага. Без этой проверки анимация ускорялась бы от движения мыши. `draw()` лишь читает `a.animating` и зовёт `mark_anim_rect`.

**Что осталось вне фазы:** выпадающий список `ComboBox` (это оверлей, не дерево — bounds его пунктов по-прежнему выставляются в overlay-draw и в пути событий); внутренние под-виджеты, которые виджет рисует сам (`TextInput` внутри `Spinbox`/`PropertyGrid`, `CodeEditor` в `MarkdownView`); `ListBox.dispatch_to_row_widgets[_h]` по-прежнему дублирует bounds ячеек перед доставкой события (безвредно, совпадает с arrange). `measure()` по-прежнему зовётся на каждый arrange, но внутри одного прохода результат берётся из кэша `SizeHint` (см. «Кэш `SizeHint`» выше).

Тесты — `arrange_test.v` (dummy-драйвер): событие видит изменение раскладки до кадра (VBox), переключение вкладки сразу даёт bounds новой вкладке, `skip_draw` раскладывает только по запросу, анимация Accordion шагает раз за кадр и не двигается от событий, ребёнок Accordion стоит под заголовком по `anim` этого же кадра, цикл в дереве. Первые два проверены мутацией: без `arrange_if_needed()` в `dispatch_event_with_app` они падают.

## Дерево виджетов (`widget_tree.v`)

До этого файла `get_widget_bounds` (`layout.v`) и `set_widget_bounds` (`containers.v`) были одним длинным `if w is Type1 {...} else if w is Type2 {...}` по всем типам виджетов — забытая при добавлении нового виджета ветка молча рендерила его в (0,0) с нулевым размером, и баг обнаруживался только визуально. Теперь оба списка заменены на интерфейсы:

```v
pub interface Layouted {
	bounds_of() Rect
mut:
	set_bounds(r Rect)
}

pub interface HasChildren {
	child_widgets() []&Widget
}

pub interface HitTestable {
	hit_children() []&Widget
}

pub interface HasVisibility {
	visible bool
}
```

(`bounds_of()` обязан быть ВНЕ `mut:`-блока — иначе V ругается «cannot mutate `w` in a non-mut smartcast» на вызове из `get_widget_bounds`.)

`get_widget_bounds`/`set_widget_bounds` сохранили прежние публичные сигнатуры (на них завязано много кода) и внутри стали однострочными: `if w is Layouted { return w.bounds_of() }` / `if mut w is Layouted { w.set_bounds(r) }`. Неизвестный (не реализующий `Layouted`) виджет по-прежнему тихо даёт нулевой `Rect` / no-op — то же поведение, что и раньше у забытой ветки, только явно задокументированное как поведение по умолчанию, а не забытый случай.

Реализации `bounds_of`/`set_bounds` для всех **51** типа (50 публичных виджетов + внутренний `CpPreview` из `color_picker.v`) собраны компактно в одном файле (по образцу `layout_measure.v` для `measure()`) — сами файлы виджетов не тронуты. Особенности сохранены: у `HBox`/`VBox`/`WindowTitleDrag` bounds живёт в `w.box.bounds` (не в собственном поле), а `MarkdownView.set_bounds` дополнительно взводит `w.dirty = true`, чтобы содержимое перевёрстывалось при изменении размера.

`HasChildren` реализован только настоящими контейнерами Widget-детей: `HBox`/`VBox`/`WindowTitleDrag` (через `box.children`), `Panel`/`Centered` (один `child`), `Stack`/`ScrollBox` (`children []&Widget`), `Splitter` (`first`/`second`), `TabBox` (`tabs[].widget`), `Accordion` (`sections[].widget`), `GridLayout` (`cells[].widget`), `ListBox` (`rows[].cells[].widget`, если строки — виджеты, а не текст). `MenuItem`/`TreeNode`/`Property` — НЕ Widget (отдельные типы, принадлежащие своему владельцу — `ContextMenu`/`TreeView`/`PropertyGrid`, а не слою раскладки), поэтому `ContextMenu`/`TreeView`/`PropertyGrid` не реализуют `HasChildren`.

**`HitTestable` — сужение `HasChildren` специально для `widget_at`.** У части контейнеров `child_widgets()` отдаёт всех детей (это нужно для обхода/инспекции), но `bounds` в `arrange()` (см. «Фаза arrange») выставляется не всем — у остальных остаются **устаревшие** значения с прошлых кадров: `TabBox` раскладывает только активную вкладку, `Accordion` — только развёрнутые секции, `ListBox` — только строки текущего видимого диапазона. Без сужения `widget_at` попадал бы в чужой устаревший `Rect` (открыть вкладку 1, вернуться на вкладку 0, кликнуть — клик ушёл бы в виджет вкладки 1). Эти три типа реализуют `hit_children()`; `widget_at` берёт его, если тип его реализует, иначе падает на `child_widgets()`.

**`HasVisibility` — поле-интерфейс, а не метод.** V сопоставляет интерфейсы и с полями структур, поэтому любой тип с топ-уровневым `visible bool` удовлетворяет ему без единой строки кода, и `widget_at` не попадает в скрытые виджеты. **Известное исключение — `HBox`/`VBox`**: у них нет собственного `visible`, флаг лежит глубже, в `box.visible` (общий `BoxLayout`), поэтому field-интерфейс их не ловит и в `widget_at_impl` для них стоит явная проверка типа. (Практического эффекта сегодня нет: `box.visible` читается в `draw_impl`/`event_impl`, но нигде не присваивается — `set_visible` у боксов нет, скрыть бокс через публичный API нельзя; проверка — защита на будущее.) Новый тип-обёртка над вложенным полем без собственного `visible` попадёт в ту же ловушку молча.

**Указателя на родителя (`parent`) у `Widget` НАМЕРЕННО нет.** Цикл владения ребёнок→родитель→ребёнок сломал бы якоря Boehm-GC в реестрах `*_capi.v` (см. vgui-capi/PROJECT.md, «Реестры объектов — якоря Boehm-GC») — GC решил бы, что структуры держат друг друга живыми, даже когда снаружи на них нет ссылок, и виджет никогда бы не собрался. Обход дерева поэтому идёт только сверху вниз:

- `walk_widgets(w, cb)` — pre-order, спускается через `HasChildren`;
- `widget_at(w, x, y) ?&Widget` — hit-testing: самый глубокий виджет, чей `bounds` содержит точку. Среди пересекающихся детей выигрывает последний (верхний по z-порядку, как в порядке отрисовки/событий у контейнеров). Пропускает виджеты с нулевым/отрицательным `bounds` (`b.w <= 0 || b.h <= 0`) и невидимые (см. `HasVisibility`).

Оба обхода ограничены `widget_tree_max_depth = 256`: дерево строится из C-ABI, где ничто не мешает сделать цикл (`vbox_a.add(vbox_b)` + `vbox_b.add(vbox_a)`), а рекурсия без потолка дала бы переполнение стека вместо диагностируемого поведения. На глубине потолка обход просто перестаёт спускаться.

**`walk_widgets`/`widget_at` — пока V-only API без потребителей в боевом коде.** Доставка событий по-прежнему идёт старым путём (`handle_event` вниз по контейнерам), в C-ABI и Python эти функции не проброшены. Это заготовленная инфраструктура; перевод hit-testing на `widget_at` — отдельная незакрытая задача (см. ROADMAP, пункт 2). Учтите цену: `child_widgets()` аллоцирует новый `[]&Widget` на каждый вызов (даже когда внутреннее хранилище уже `[]&Widget` — отдаётся `.clone()`, чтобы наружу не утёк внутренний буфер контейнера), и при переводе на путь событий это станет аллокацией на каждое событие на каждый уровень дерева — тогда нужен итератор/callback без аллокации.

**Видимый диапазон строк `ListBox` — один источник правды.** Формулы «какие строки сейчас на экране» раньше были продублированы трижды (в `draw()`, в `dispatch_to_row_widgets[_h]()` и в новом `hit_children()`), и копии разошлись: `hit_children()` потерял per-item фильтр и отдавал на одну полностью съехавшую строку больше, чем реально красит `draw()`. Теперь все трое зовут пару функций из `list_box.v`: `visible_row_range_v(vp)` / `visible_row_range_h(vp, iw)` возвращают **консервативный супернабор** `[first, last]` (концевой `+1` покрывает частично видимую строку), поэтому вызывающий **обязан** дополнительно фильтровать каждый индекс через `row_visible_v(i, vp)` / `row_visible_h(i, vp, iw)` — точный предикат, совпадающий с тем, что рисует `draw()`. `visible_row_range_v` заодно защищает от `item_height <= 0` (возвращает пустой диапазон `(0, -1)`): публичные пути значение клампят (`ui_builder.v` присваивает только при `ih > 0`, `vgui_list_box_set_item_height` делает `max_f32(height, 1)`), но поле публичное и присваивание напрямую из V-кода обходит оба. Перевод `draw()` на эти хелперы попутно ускорил его: цикл идёт по `[first, last]` вместо скана всех строк от нуля (на 10 000 строк — 6 итераций вместо 5000+ пропусков), а множество реально закрашенных строк не изменилось (проверено перебором по сетке item_height × числа строк × высоты вьюпорта × позиции скролла, включая точные кратные и отрицательные значения).

Тест — `widget_tree_test.v` (SDL и шрифты не нужны): по одной проверке `bounds_of`/`set_bounds` на каждый из 51 типа (список сверен построчно со старыми `get_widget_bounds`/`set_widget_bounds` перед их удалением), плюс `walk_widgets`/`widget_at`/`HasChildren` на дереве `VBox → [Label, HBox → [Button, Button]]`, сценарии `HitTestable` (клик мимо неактивной вкладки и попадание в активную, границы видимого диапазона `ListBox`), цикл `VBox A → VBox B → A`, нулевой `bounds`, скрытые `HBox`/`VBox` и доставка событий по ячейкам `ListBox`. Запуск: `v test widget_tree_test.v`.

**Поведенческие изменения, попутные переходу на интерфейсы** (все — исправление молчаливых багов старых switch, но заметны глазом):

- **`CpPreview` (превью «Old/New» в диалоге цвета) раньше вообще не рисовался.** Тип отсутствовал в switch `set_widget_bounds`, поэтому его `bounds` навсегда оставался `Rect{0,0,0,0}`. Теперь он `Layouted` и виден; заодно его слот в строке увеличен с 30 до 84 px (на 30 px две подписи налезали на поле hex-ввода) и `draw` обёрнут в `push_clip`/`pop_clip`.
- **`Tooltip` показывается для тех виджетов, для которых раньше молча не показывался** (Icon, Canvas, TableView, CodeEditor, TextArea, GridLayout, Accordion): ручной switch в `tooltip.v` имел устаревший список типов и отдавал для них `Rect{}`. Теперь он зовёт `get_widget_bounds(target)`.
- **`ContextMenu` реагирует строго в границах цели.** Такой же устаревший switch в `menu.v` для незнакомого типа откатывался на `cm.bounds`, то есть на весь экран — ПКМ в любой точке окна открывал меню. Ветка «весь экран при `cm.target == nil`» сохранена намеренно.

## Фокус-учёт (`focus.v`) — регистрация обязана сниматься

`FocusManager` окна держит `entries []FocusEntry`, где каждая запись — **сырой `voidptr` на структуру виджета**. Регистрация происходит из `draw()` каждого focusable-виджета (`ctx.focus.register_button(&b, ...)` и т.п.), то есть достаточно одного отрисованного кадра.

**Запись в `entries` — такой же GC-якорь, как реестры `g_*` в `vgui-capi/vgui_capi.v`**: Boehm-GC консервативен и считает указатель внутри записи живой ссылкой. Поэтому оставленная запись даёт сразу три беды — структура уничтоженного виджета не собирается (утечка ~1.4 КБ на виджет), мёртвый виджет остаётся в Tab-цикле (фокус «пропадает в никуда»), а при переиспользовании его адреса под виджет другого типа `blur_current`/`focus_index`/`is_entry_available` делают cast чужого типа.

Снятие: `fm.unregister(ptr)` вызывается из `vgui_destroy` через `capi_unregister_focus_everywhere(ptr)` → `App.unregister_focus(ptr)` — обходом `g_apps` по всем окнам и диалогам, потому что указателя на родителя у виджета намеренно нет (тот же приём, что у `capi_invalidate_everything`). Вызов идёт для **любого** kind, до удаления из `g_*`, так что новый focusable-виджет ничего дополнительно регистрировать не должен.

Две вещи, которые легко сломать при правках `unregister`:

- **`fm.current` — это ИНДЕКС в `entries`, а не указатель.** После `entries.delete(i)` всё правее съезжает влево, поэтому `current` обязан корректироваться (`== i` → `-1`, `> i` → `--`). Без этого фокус молча переезжает на соседний виджет.
- **Удаляемый виджет НЕ блюрится.** `blur_current()` пишет в поля виджета, а его структура вот-вот будет освобождена. Фокус на удаляемой записи просто сбрасывается в `-1`.

**`kind` записи обязан соответствовать реальному типу по адресу.** Все ветки `blur_current`/`focus_index`/`is_entry_available` приводят `e.ptr` к типу, который обещает `kind`, — регистрация «похожим» типом означает чтение и запись по чужим смещениям. Так было у `MenuButton`, который регистрировался как `&Button(&mb)`: `sizeof` 176 против 240, расхождение раскладки начинается с поля `placeholder`, поэтому `visible`/`enabled` читались всегда как `false` (виджет не попадал в Tab-цикл вообще), а `blur_current` писал байт внутрь строки. У него теперь свой `FocusKind.menu_button`. Новому focusable-виджету нужен **свой** элемент enum, а не ближайший похожий.

ABA-страховка живёт в `register_ptr`: `registered` — это `map[voidptr]FocusKind` (не `bool`), и регистрация того же адреса с **другим** kind заменяет запись вместо того, чтобы молча ничего не сделать. Штатный путь до этого не доходит (destroy снимает регистрацию раньше), это защита на случай виджета, не дошедшего до `vgui_destroy`.

Интроспекция для тестов на утечки: `vgui_window_focus_count(win)` (объявлена в `_lib.py`) — сколько виджетов сейчас на фокус-учёте окна; после уничтожения всех виджетов должно быть 0. Юнит-тесты — `focus_test.v` (SDL не нужен): симметрия register/unregister, поведение `current` при удалении записи левее/правее фокуса, выпадение из Tab-цикла, ABA-замена записи, 50 000 циклов «зарегистрировать → снять» без остатка. Запуск: `v test focus_test.v` из `v/`.

## Неактивное состояние (enabled) (`enabled.v`)

С 13.10.2026 у **каждого** виджета есть поле `enabled bool = true` (у `HBox`/`VBox`/`WindowTitleDrag` -
`box.enabled` в общем `BoxLayout`). Раньше оно было только у ~30 интерактивных виджетов, контейнеры
его не имели, а подписи, иконки, прогресс и т.п. неактивными не рисовались вовсе. Единые точки:
`set_widget_enabled(mut w, en)` / `widget_enabled(w)` (поле-интерфейс `HasEnabled`, как
`HasVisibility`, плюс явные ветки для боксов), C-ABI `vgui_widget_set_enabled(ptr, kind, en)` /
`vgui_widget_is_enabled` (vgui-capi; заодно `MenuItem`, kind 29), Python `_Widget.set_enabled` /
`is_enabled`, в разметке `.vui` - свойство `disabled` у любого элемента.

**Наследование без указателя на родителя.** Отключённый контейнер гасит всё поддерево, но
собственные флаги детей не трогает: включили контейнер - каждый ребёнок снова такой, каким был.
Родителя у виджета нет (намеренно, см. «Дерево виджетов»), поэтому «отключён ли предок» виджет
узнаёт только во время `draw()` из `ctx.disabled_depth`:

- контейнер рисует детей между `ctx.begin_disabled(own)` / `ctx.end_disabled(own)` (при `own == false`
  глубина +1/-1). Так сделаны `BoxLayout`, `Panel`, `Stack`, `Centered`, `ScrollBox`, `GridLayout`,
  `Splitter`, `TabBox` (содержимое вкладки), `Accordion` (секции), `NotificationManager`, а также
  владельцы встроенных виджетов: `Spinbox` (своё поле ввода), `ListBox` (виджеты-ячейки),
  `MarkdownView` (редактор в режиме исходника), `TreeView`/`TableView`/`PropertyGrid`/`CodeEditor`/`Canvas`;
- виджет в `draw()` один раз берёт `en := ctx.is_enabled(w.enabled)` и дальше пользуется только `en`.
  Прямое чтение `w.enabled` в рисовании - ошибка: внутри отключённого контейнера виджет рисовался бы
  активным;
- `Window.render()` обнуляет `disabled_depth` в начале кадра - страховка от несбалансированной пары;
  тест `test_disabled_depth_balanced_after_frame` проверяет, что после кадра там 0.

**Ввод.** Отключённый контейнер не передаёт детям события ввода (`is_input_event`: клавиатура, текст,
мышь, drop). Служебные события окна (`window_resize`, фокус окна, сворачивание) идут насквозь: по ним
корневые контейнеры подгоняют размер, и неактивность это ломать не должна. Свой флаг каждый виджет
проверял в `handle_event` и раньше. `ScrollBox`/`Splitter`/`DropZone` при отключении сбрасывают
перетаскивание и подсветку. `TabBox`/`Accordion` при своём `!enabled` по-прежнему не отдают детям
вообще ничего (как было до этого раздела).

**Фокус.** Регистрация в фокус-учёте идёт из `draw()` и живёт дольше кадра, поэтому неактивный
focusable-виджет зовёт `ctx.focus_block(&w)` вместо `register_*`: адрес попадает в
`FocusManager.blocked` (map, O(1)), запись выпадает из Tab-обхода (`is_entry_available`), а если фокус
стоял на ней - `blur_current()` снимает его (и с ним открытый список `ComboBox`, выделение текста и т.п.).
Следующая регистрация (`register_ptr` того же адреса и kind) блок снимает. `blocked` - такой же
GC-якорь, как `entries`: `unregister` чистит и его. Следствие: собственный `enabled = false` теперь тоже
снимает фокус уже на следующем кадре (раньше поле ввода с фокусом оставалось «в фокусе», хотя ввод
не принимало).

**Вид.** Простые контролы перекрашиваются цветами темы: текст - `text_disabled`, кнопки -
`button_disabled_*`, фон полей - `input_bg.darken(0.05)`. Акцентные заливки (ползунок, тумблер,
прогресс, бейдж, полоса активной вкладки) - `ctx.disabled_color(c)`: цвет наполовину к фону окна.
**Не `darken`**: на светлой теме затемнённый акцент выглядел *активнее* обычного (так было у
`Slider`/`ToggleSwitch` до правки). Виджеты со сложным содержимым (`ListBox`, `TreeView`, `TableView`,
`PropertyGrid`, `CodeEditor`, `MarkdownView`, `PlotView`, `Canvas`, `CurveEditor`, `ImageView`,
`ImageBackground`, `Calendar`, `ColorPicker`, `Notification`) рисуются как обычно и накрываются
`ctx.draw_disabled_veil(bounds, radius)` - полупрозрачной заливкой цветом фона окна (через `defer`
после проверки клипа, чтобы попасть на все пути выхода). `draw_item_icon` считает `fallback ==
theme.text_disabled` признаком неактивного элемента: глиф красится им даже при своём цвете иконки,
картинка рисуется с `SDL_SetTextureAlphaMod(disabled_image_alpha)` (так её звали меню и раньше).

Особые случаи: `Tooltip.enabled = false` - подсказка не показывается, но неактивность **цели**
подсказку не гасит (объяснить, почему элемент недоступен, - её работа). Поэтому `Button` со своей
подсказкой (поле `tooltip`) отдаёт ей события ДО проверки `enabled`. `WindowTitleDrag` без
`enabled` не перетаскивает окно. `ContextMenu`/`MenuBar` при неактивности закрывают открытое меню.
`Spacer.enabled` ни на что не влияет - флаг только для единообразия. Холст, который только
рисует (фон, миниатюра в ячейке `ListBox`), - `Canvas.passive = true`, а не `enabled = false`: события
и фокус он не берёт, щелчок идёт виджету под ним, а рисуется как обычно (до 13.10.2026 для этого
ставили `enabled = false`, теперь такой холст накрыт вуалью). `TreeNode` и `Property` флага не
имеют (у `Property` есть `readonly`); неактивные строки `ListBox`/пункты `ComboBox` - не сделаны.

Тесты - `enabled_test.v` (клик сквозь отключённый контейнер, Tab и снятие фокуса, баланс глубины,
разметка) и снапшоты `*_disabled_*` в `snapshot_test.v` (те же галереи с отключённым корнем, обе темы);
Python - `vguipy/tests/test_enabled.py`.

## Оверлеи попапов (`overlay.v`) — один слот с владельцем

Выпадающий список `ComboBox`, `ContextMenu`, `MenuBar` и `MenuButton` рисуются поверх дерева через слот оверлея окна: `RenderContext.overlay_cb` (рисуется после всех виджетов, без клипа) и `overlay_ev` (получает событие раньше виджетов, `dispatch_event_with_app` в `sdl3_window.v`). Слот **один на окно**, и у него есть **владелец** `overlay_owner` — адрес виджета, открывшего попап, — плюс close-хук `overlay_close`.

Писать в слот — только через два метода:

- `ctx.set_overlay(owner, draw, ev, close)` — если слот занят **другим** владельцем, его попап сначала закрывается его же close-хуком. Слот освобождается до вызова хука, поэтому `clear_overlay` внутри хука ничего не трогает. Повторная установка тем же владельцем хук не зовёт (MenuBar переключает пункты через `open_entry`).
- `ctx.clear_overlay(owner)` — освобождает слот, только если он принадлежит `owner`; при `owner == nil` ничего не делает.

Почему нельзя присваивать `overlay_cb`/`overlay_ev` напрямую (так было до аудита 2.4):

- второй попап перетирал первый, и тот навсегда оставался `open = true` без отрисовки и событий; у ComboBox при этом глохла клавиатура — при `open` его `handle_event` отдаёт клавиши оверлею, которого уже нет;
- close обнулял слот без проверки: ComboBox, закрываясь по потере фокуса из `draw()`, стирал уже открытое ContextMenu, а `MenuState.close_all` в начале открытия меню стирал чужой попап;
- уничтожение виджета с раскрытым попапом оставляло замыкания в слоте: список рисовался каждый кадр и пинил структуру для Boehm-GC (как запись фокус-учёта).

**Ключ владельца обязан совпадать с указателем, который приходит в `vgui_destroy`** — это адрес самого виджета (`voidptr(&cb)` в его методе), а не адрес вложенного поля. `MenuState` своего виджета не знает, поэтому у него есть поле `owner`, которое владелец ставит перед открытием (`cm.state.owner = voidptr(&cm)`), и `close_all` чистит слот по нему.

Снятие при уничтожении: `vgui_destroy` → `capi_release_overlay_everywhere(ptr)` → `App.release_overlay(ptr)`, обходом всех окон и диалогов — тем же приёмом, что у фокус-учёта. close-хук при этом **не** зовётся (он пишет в поля уходящего виджета); окно инвалидируется, а `prev_overlayish` делает следующий кадр полным, так что попап стирается сразу.

Почему не стек оверлеев (второй вариант из аудита): подменю уже живут внутри одного `MenuState` (`levels`), а два независимых попапа одновременно на десктопе не показывают — открытие нового закрывает старый. Стек понадобится, только если появится попап, обязанный жить поверх попапа другого владельца.

Известное ограничение: виджет, снятый из контейнера **без** `destroy`, с раскрытым попапом — попап остаётся до клика вне него (ComboBox закрывается по потере фокуса из своего `draw()`, который для отсоединённого виджета больше не вызывается).

Тесты — `overlay_test.v` (реальное окно под dummy-драйвером): вытеснение ComboBox меню и MenuButton комбобоксом, поздний close не стирает чужой слот, переключение пунктов MenuBar, `release_overlay`.

## Область модальности (`modal_scope.v`) — чьи события гасит модальный диалог

Модальный диалог блокирует **не всё приложение, а своё дерево владения**: родительское окно, его предков
и остальные диалоги того же дерева. До аудита 3.D `process_events` брал верхний открытый модальный диалог
по всему `app.dialogs`, не глядя на `parent`, и гасил события всех окон разом — в многооконном приложении
модальный диалог одного окна замораживал второе, никак с ним не связанное.

Дерево владения строится по `Dialog.parent_id` — `sdl_id` окна-родителя, проставленный в `create_dialog`
(0, если родителя нет). Решение принимает чистая функция `modal_blocker_index(entries, event_wid)`:
диалоги просматриваются сверху вниз (с конца `app.dialogs`, то есть от самого позднего), и первый
подходящий модальный побеждает. Правила по порядку:

1. событие самого модального диалога — отдаётся ему же;
2. окно из **поддерева** модального диалога (`is_owned_by`) им не блокируется — так работает вложенный
   диалог, открытый поверх модального;
3. `parent_id == 0` (диалог без родителя) — блокирует всё приложение, это прежнее поведение и на него
   опираются `message_box`-подобные сценарии без явного родителя;
4. иначе блокируются окна с тем же корнем дерева (`owner_root`), и только они.

`owner_root` и `is_owned_by` обходят цепочку `parent_id` с лимитом шагов, поэтому кольцо (в норме
недостижимое) обход не вешает. Снимок `[]ModalScopeEntry` строится в `process_events` только когда
открыт хотя бы один модальный диалог — на «горячем» пути без диалогов лишних аллокаций нет. Закрытые
диалоги попадают в снимок с `modal: false`: блокерами они не являются, но остаются звеном цепочки
владения для своих детей.

Заблокированное окно по-прежнему поднимает модальный диалог наверх (`SDL_RaiseWindow`) при клике или
получении фокуса — ветка `else` в `process_events`. Затемняющая подложка (`Window.has_modal_child`,
пересчитывается с нуля каждый кадр в `render_all`) ставится и на окно-диалог, если модальный диалог
открыт поверх другого диалога.

Тесты: `modal_scope_test.v` — таблица случаев для `modal_blocker_index` без SDL (два окна с
собственными диалогами, вложенная модальность, соседний диалог того же окна, диалог без родителя,
кольцо); `modal_scope_events_test.v` — сквозная проверка через реальный `app.process_events()`
с событиями, подложенными в очередь SDL (`SDL_PushEvent`) под dummy-драйвером: клик по соседнему окну
доходит, клик по заблокированному — нет. Демо: `vguipy/examples/50_modal_scope.py` и
`examples/50_modal_scope.v`.


**`Button.tooltip` обслуживает сама кнопка** (`button_tooltip_test.v`). Раньше поле только
хранилось и ничего не рисовало — приложения вешали отдельный `Tooltip` в окно после корня. Теперь
кнопка лениво создаёт внутренний `Tooltip` (`sync_tip`, привязан к ней самой), зовёт его `draw`
сразу после проверки `visible` (до клипа: пока подсказка ждёт задержку или показана, кадры
полные — `mark_anim`/`prev_overlayish` — и кнопка рисуется каждый кадр) и `handle_event` — до
проверки `enabled`. Бонус: подсказка кнопки, убранной из дерева, не всплывает над её старыми
`bounds` (её `draw` больше не зовётся) — с отдельным `Tooltip` её приходилось гасить вручную.
Пустой `tooltip` гасит уже созданную подсказку.

**Символьные сочетания совпадают и по физической клавише** (`menu_shortcut_matches`,
`us_scancode`, `shortcut_layout_test.v`). Сначала сравнивается keycode (символ раскладки), затем
scancode клавиши, которая печатает этот символ в раскладке US. Иначе в русской раскладке «[»/«]»,
«;», «'» и т.п. не срабатывали: эти клавиши дают кириллицу, а SDL3 (подсказка
`SDL_HINT_KEYCODE_OPTIONS`, по умолчанию `latin_letters`) переводит в латиницу только буквенные
клавиши US-раскладки. Касается и меню, и `bind_hotkey` (общий разбор).

**Холст по умолчанию забирает клавиши** (`Canvas.take_keys = true`): после клика (инструмент берёт
фокус) горячие клавиши окна и сочетания до него не доходят. Приложению, которому клавиши холста не
нужны (кисть — мышью), ставить `take_keys = false`.
## Инвалидация и dirty regions (`dirty.v`, `render_context.v`, `sdl3_window.v`)

Раньше любой кадр перерисовывал всё окно целиком, а анимация означала вечный цикл на 60 fps. Теперь `Window` хранит **persistent render target** (`rt`, текстура в ФИЗИЧЕСКИХ пикселях) и `RenderContext` копит грязные прямоугольники в `DirtyRegion`. `Window.render()` выбирает одну из трёх веток:

- **full** — грязь помечена как `full`, `rt` только что создан/пересоздан, изменился размер, есть модальный ребёнок или оверлей (`prev_overlayish`: выпадающий список, контекстное меню, тултип). Рисуется всё дерево;
- **partial** — рисуется только bbox грязи (клип + заливка фона под ним), остальное берётся из `rt` прошлых кадров;
- **skip_draw** — грязи нет: дерево виджетов не обходится вообще, `rt` просто блитится и презентуется.

Ключевые вещи, которые легко сломать:

**Содержимое `rt` может пропасть без пересоздания текстуры.** Direct3D (бэкенд SDL по умолчанию на Windows) теряет render target-текстуры при сбросе устройства: D3D9 сбрасывает его при каждом изменении размера окна, D3D11 — при потере устройства (обновление драйвера, RDP, сбой GPU). SDL сообщает об этом событиями `SDL_EVENT_RENDER_TARGETS_RESET` / `SDL_EVENT_RENDER_DEVICE_RESET` — `process_events` (`sdl3_app.v`) отвечает на них `invalidate_all_windows()`, то есть полным кадром. Без этого `rt` остался бы пустым, а частичные кадры дорисовывали бы только изменившееся (добавлено 09.10.2026 профилактически, по документации SDL; под Wine не воспроизводилось). Сами текстуры виджетов при `DEVICE_RESET` не пересоздаются — пока не обработано.

**Blend mode рендерера — ГЛОБАЛЬНОЕ состояние SDL.** Оно живёт до конца кадра И переходит в следующие кадры (включая full). Partial-ветка ставит `SDL_SetRenderDrawBlendMode(none)` для заливки фона под грязью и **обязана вернуть `blend`**. Все примитивы в `sdl3_render.v` ставят blend сами; исключением был `spinner_draw_circle_arc`, который звал `SDL_RenderGeometry` без него — из-за этого полупрозрачное кольцо спиннера писалось в таргет вместе с альфой 60 и визуально темнело. Теперь спиннер ставит blend сам, но правило общее: **новый путь рисования обязан выставлять blend самостоятельно, не наследуя чужой**.

**Блит `rt` на бэкбуфер идёт с `SDL_SetTextureBlendMode(rt, none)`**, а не `blend`: бэкбуфер после введения RT никем не очищается (`SDL_RenderClear` уходит внутрь `rt`), и при блендинге неполная альфа копилась бы из кадра в кадр. Блит persistent target — копия, а не наложение.

**Viewport/clip/scale в SDL3 хранятся ПО-ТАРГЕТНО.** `SDL_SetRenderScale` не переносится с бэкбуфера на текстуру, поэтому масштаб выставляется заново после каждого `SDL_SetRenderTarget`. Без этого ломается весь HiDPI и `set_ui_scale` (UI рисуется в 1/scale окна). На машине с `dpi_scale = 1` обычные примеры выглядят нормально — проверять только через `set_ui_scale`.

**`dirty.clear()` стоит ДО цикла отрисовки** (сразу после решения full/partial), а не после: виджеты инвалидируют себя из собственного `draw()`, и очистка после цикла стирала бы запросы на следующий кадр — все анимации в библиотеке вставали намертво.

**Снимки `overlay_active`/`tooltips_active` годны только для решения о ветке.** Сама отрисовка идёт по live-состоянию: `pending_tooltips` наполняется ВНУТРИ цикла `draw()` (`tooltip.v`), поэтому по снимку тултип появлялся бы на кадр позже и мигал через кадр.

**Точечная инвалидация hover (`mouse_move`).** Все остальные события (клик, клавиша, колесо, drop) в конце `dispatch_event_with_app` зовут `invalidate_all()` — консервативно и дёшево, они не идут с частотой кадров. Для `mouse_move` это было бы разорительно: движение мыши перерисовывало всё окно, и весь смысл dirty regions оставался только для простоя. Поэтому у `mouse_move` отдельный путь — `Window.invalidate_hover_change()`:

- `hover_target(x, y)` находит верхний видимый виджет под курсором (`widget_at` из `widget_tree.v` по верхнеуровневым виджетам с конца) и его `bounds`;
- инвалидируются два прямоугольника: сохранённый `hover_rect` прошлого виджета под курсором и `bounds` нынешнего. Больше на движение мыши в окне ничего не меняется;
- курсор над пустым фоном (оба — `nil`) не инвалидирует ничего: кадр вообще не рисуется (`skip_draw`).

`hover_widget` — сырой адрес (`voidptr(&Widget)`), и он **никогда не разыменовывается**: виджет мог быть уничтожен между событиями. Он нужен только для сравнения «тот же или другой», перерисовывается сохранённый `hover_rect`. Сравнение идёт и по адресу, и по прямоугольнику — адрес мёртвого виджета может достаться новому (ABA).

Учёт hover ведётся **всегда**, даже когда кадр решено сделать полным, иначе после полного кадра `hover_widget` остался бы от позапрошлого движения и следующий частичный кадр стёр бы не то место.

Полным кадр остаётся, когда двух прямоугольников заведомо мало (`hover_partial_ok`): зажата кнопка мыши (`ev.mouse_buttons != 0` — идёт перетаскивание ручки Slider, полосы Splitter, выделение текста, панорама Canvas, и виджет меняется, когда курсор давно вне его `bounds`); открыт оверлей; показан тултип или подложка модального диалога. Поле `mouse_buttons` в `GuiEvent` заполняется из `SDL_MouseMotionEvent.state` и, в отличие от `mouse_btn`, говорит не «какая кнопка сработала этим событием», а «тянут ли что-то прямо сейчас».

Условие про оверлей/тултип/модалку дублирует то, по которому `render()` и так делает кадр полным — намеренно: решение «этот кадр частичный» не должно зависеть от того, что именно сочтёт полным `render()` завтра.

Осечка возможна ровно одна: виджет без `Layouted` имеет нулевой `bounds`, `widget_at` его не видит, и hover над ним не инвалидирует ничего. Такой виджет и так рисуется в (0,0) нулевого размера, то есть сломан задолго до hover'а (см. чек-лист «Добавление нового виджета»).

**Hover-анимации виджетов помечают только себя.** Точечная инвалидация `mouse_move` бесполезна, если виджет под курсором в ответ зовёт `mark_anim` (полный кадр). Поэтому `Button`, `CheckBox`, `RadioButton`, `ToggleSwitch`, `Slider`, `Spinbox`, `MenuButton` мигрированы на `mark_anim_rect(reason, bounds)` — все их анимации (hover/press/focus/active/slide) лежат внутри собственных `bounds`. `mark_anim` остался там, где рисование выходит за `bounds` виджета: `Tooltip`, всплывающая подсказка ссылки в `MarkdownView`, `Notification` (менеджер двигает его по экрану). Обёртка `if ctx.is_in_clip(bounds) { ... }` вокруг такого вызова больше не нужна — `mark_anim_rect` проверяет клип сам.

Тесты — `hover_dirty_test.v` (какие прямоугольники накопились, когда кадр остаётся полным, ведётся ли учёт hover на полном кадре) и `test_partial_hover_frames_match_full_frame_pixels` в `render_dirty_test.v` (серия частичных кадров после движений мыши совпадает с полным кадром попиксельно; там же страховка, что подсветка hover вообще видна в пикселях — иначе сравнение ничего не доказывает).

**Инвариант самоподдержания анимации.** `mark_anim_rect(reason, r)` взводит `needs_animation` только если `r` пересекает текущий клип **и** `invalidate(r)` реально принял прямоугольник. Заморозки это не даёт, потому что грязь попадает в `render()` как **bounding box объединения** всех накопленных прямоугольников: виджет, пометивший себя в кадре N, по построению лежит внутри клипа кадра N+1 — рисуется, метится снова, цикл замкнут. Выйти из него можно только став реально невидимым (за клипом `ScrollBox`, неактивная вкладка `TabBox`, свёрнутая секция `Accordion`, скрытый слой `Stack`), а возврат в видимость всегда идёт по входному событию — `dispatch_event_with_app` на входных событиях зовёт `invalidate_all()`. Исключение `mouse_move` (см. выше) инвариант не трогает: он только ДОБАВЛЯЕТ прямоугольники в уже накопленную грязь, никогда её не уменьшая, поэтому виджет, пометивший себя в кадре N, остаётся внутри bbox кадра N+1 — а вернуть виджету видимость одно лишь движение мыши не может (это делают клик, колесо или код). Пути без событий (`app.post()`, клики по трею) закрывает `App.invalidate_all_windows()` в `run()`. **Не убирайте ни гвард в `mark_anim_rect`, ни `invalidate_all()` на выходных путях `dispatch_event_with_app`: без второго первый превращается в вечную заморозку.** Следствие: расположение `mark_anim_rect` относительно собственного `if !ctx.is_in_clip(bounds) { return }` виджета ни на что не влияет — функция перепроверяет тот же предикат с тем же прямоугольником. В `text_input.v`/`text_area.v` порядок всё же содержателен, но по другой причине: он выносит `ctx.focus.register_*` из-под клипа, и полностью отсечённый TextInput/TextArea теперь достижим по Tab (изменение поведения).

**Прямая запись `ctx.needs_animation = true` — теперь баг, а не оптимизация.** Виджет, взводящий флаг без инвалидации, замирает после первого кадра: следующий кадр не находит грязи, уходит в `skip_draw` и вообще не зовёт его `draw()`. Все встроенные виджеты (Spinner, ProgressBar, Accordion, TextArea, CodeEditor, TextInput) мигрированы на `mark_anim_rect`. Используйте `mark_anim` / `mark_anim_rect`.

**Сброс `needs_animation`/`anim_reason` выполняется в самом начале `render()`**, до проверки `!w.open || !w.visible` и независимо от `skip_draw`. Иначе флаг переживал кадр, на котором дерево не рисовалось: окно, скрытое (`hide()` / в трей) при взведённом флаге, оставляло `any_anim = true` в `run()` навсегда, и цикл крутился на 60 fps вхолостую.

**`visual_margin() = shadow_blur + |shadow_offset|`** — на сколько раздувается прямоугольник при `invalidate()`. Виджеты рисуют за пределами своих `bounds` (тени, фокусные рамки), и раздувания на 1 px не хватало: под кнопкой оставалось ~14 000 расходящихся пикселей.

**`visual_margin()` нужен не только грязному прямоугольнику, но и КЛИПУ контейнера.** `BoxLayout` (`VBox`/`HBox`/`WindowTitleDrag`) и `Panel` клипают детей по своим `bounds`, а бокс обычно обтягивает детей вплотную — клип строго по `bounds` срезал тень крайнего ребёнка, заметнее всего снизу, куда её уводит `shadow_offset` (под наведённой кнопкой оставалась одна строка вместо восьмипиксельного градиента). Поэтому оба клипают `bounds.expanded(ctx.visual_margin())` (у `Panel` — ещё и `.intersection(p.bounds)`, чтобы тень содержимого не выходила за рамку самой панели). Это безопасно: `push_clip` пересекает прямоугольник с родительским клипом, так что содержимое `ScrollBox` по-прежнему не выходит за его viewport, а виджеты клипают собственное содержимое по своим `bounds` сами. Регрессионный тест — `test_container_clip_keeps_child_shadow` в `render_dirty_test.v` (без правки даёт 0 строк тени вместо ≥5). **`ScrollBox` (viewport) и `Accordion` (content_r) намеренно НЕ раздуваются**: там клип — не декоративная граница, а сама скролл-область и анимация разворачивания; раздутие пустило бы контент за их пределы. Тень соседа, закрытая следующим ребёнком (spacing меньше вылета тени), — не баг, а порядок отрисовки: тень лежит ПОД соседом.

**`DirtyRegion.add()` и `RenderContext.invalidate()` возвращают `bool`** — «прямоугольник принят» (или регион уже `full`); `false` означает вырожденный или полностью выпавший за границы окна прямоугольник. Вызывающие, выводящие из этого другое состояние (`mark_anim_rect` → `needs_animation`), обязаны проверять результат. Для стороннего V-кода это BREAKING. Публичные обёртки (`Window.invalidate`, `vgui_window_invalidate`, Python `Window.invalidate`) значение намеренно **не** возвращают: снаружи на него нечем реагировать — если прямоугольник схлопнулся за экраном, там нет пикселей для перерисовки.

**Инвалидация взводит и `ctx.layout_dirty`** — `invalidate()`/`invalidate_all()` заодно просят пересчитать раскладку до следующего события или кадра (см. «Фаза arrange»).

**Контракт инвалидации: НИ ОДИН сеттер виджета кадр не инвалидирует** (кроме двух исключений ниже). Пока состояние меняется из колбэков — то есть внутри обработки события — всё работает: событие само вызывает `invalidate_all()`. Но если вы крутите **свой** цикл (`Dialog.exec()`-подобный код, ручные `process_events`/`render_all`) и меняете состояние между кадрами, изменение на экран не попадёт. Для этого есть публичные `Window.invalidate(x, y, w, h)` / `Window.invalidate_all()` и `Dialog.invalidate(...)` / `Dialog.invalidate_all()` (Python) поверх `vgui_window_invalidate` / `vgui_window_invalidate_all` (capi принимает и указатель окна диалога из `vgui_dialog_get_win_ptr`). Обе Python-обёртки безопасны на уничтоженном/непоказанном объекте — nil-дескриптор гасится в capi.

**Исключение — два сеттера анимации.** `vgui_spinner_start` и `vgui_progress_bar_set_indeterminate(on = 1)` инвалидируют кадр: их единственное назначение — запустить анимацию, а анимация самоподдерживается только начиная с кадра, в котором виджет реально нарисовался, поэтому вызванные вне пути событий они иначе не запустили бы её никогда. Инвалидация идёт обходом `g_apps` (`capi_invalidate_everything`), а не через `app.get_active_ctx()`: у виджета намеренно нет указателя на родителя, а активный контекст — ровно одно окно (nil до первого кадра, чужое при нескольких окнах/диалогах). Выключение не инвалидирует — в этот момент виджет ещё анимируется, кадр уже запрошен. Оговорка: `g_apps` наполняет только `vgui_app_create`, поэтому для V-кода, создающего `App` напрямую через `create_app()`, эти два сеттера не инвалидируют.

Тесты — `dirty_test.v` (бухгалтерия `DirtyRegion` в изоляции), `hover_dirty_test.v` (точечная инвалидация `mouse_move`) и `render_dirty_test.v` (сам шов `render()`; там же инструмент попиксельного сравнения `capture_rgba`/`get_px`/`diff_count`, которым проверяется «совпадает ли partial-кадр с full»). Оба под `SDL_VIDEODRIVER=dummy`, дисплей не нужен: `v test dirty_test.v` из `v/`.

**Пересобирайте примеры после правок движка.** V-примеры (`examples/bin/`) статически включают код vgui, поэтому старые бинарники продолжают показывать старые баги — «в демо не работает, а тесты зелёные» почти всегда означает устаревший бинарник. Пересборка: `examples/build.sh` (для Python-примеров достаточно `vgui-capi/build.sh`, они ходят в `libvgui.so`).

**Отсечение по клипу — с тем же запасом, что у SDL** (`clip_pad`, `sdl3_render.v`). `clip_sdl_rect`
раздвигает реальный клип на 1 логический пиксель (чтобы не срезать рамки на краю), и частичный кадр
очищает именно расширенную область. `is_in_clip` обязан сравнивать с тем же расширенным клипом: до
14.10.2026 он проверял нерасширенный строгим пересечением, и виджет, лишь касающийся dirty-области краем,
не перерисовывался, хотя его крайняя строка пикселей уже была стёрта. Типичный случай — область
перерисовки, раздутая на `visual_margin` (тень тёмной темы, 8 px) ровно на зазор `gap=8` до соседа сверху:
при анимации чекбокса или наведении на переключатель у поля ввода над ними пропадала нижняя рамка
(пример 56). Старые снапшоты тёмной темы были сняты с этим багом (срезанный низ кнопок) и обновлены.
Тест — `clip_edge_test.v`.

## Анимации (`anim.v`)

Раньше каждый анимирующийся виджет держал голые `f32` и в `draw()` делал `x += (цель - x) * k` с «прилипанием» при разнице < 0.005 — около 30 копий в 20 виджетах. Две беды: скорость зависела от частоты кадров (шаг — доля **за кадр**), а шесть виджетов (`ComboBox`, `ListBox`, `TabBox`, `TableView`, `TreeView`, `PropertyGrid`) и фокус-рамка `TextInput`/`TextArea`/`CodeEditor` шагали, не прося следующего кадра: под dirty regions кольцо фокуса застывало на первом шаге (~18%) до следующего события. Теперь у всех — общий `Anim`.

**`Anim`** — одно анимируемое число: `value` (по нему рисуют) и `goal`. Виджет зовёт `a.update(цель, ctx)` и, пока она возвращает true, — `ctx.mark_anim_rect(...)`. Читать `value`/`goal` можно напрямую, менять — только через `set_target`/`snap`/`update` (иначе собьётся состояние перехода); стоящее в покое значение по умолчанию — `Anim{...}.at(v)`.

- `.smooth` (по умолчанию) — экспоненциальное следование: `value += (goal - value) * (1 - exp(-dt/tau))`. Цель можно менять каждый кадр, движение не дёргается — так анимируются hover/press/focus/выбор. Постоянные `anim_tau_focus/hover/toggle/press` (84/75/58/47 мс) подобраны так, что при 60 fps шаг совпадает с прежними `k` 0.18/0.2/0.25/0.3 (`tau = -16.67 / ln(1 - k)`; тест `test_smooth_matches_old_per_frame_factor`) — на глаз ничего не поменялось. `epsilon` — порог прилипания (у `Slider`, `ToggleSwitch`, `Spinbox`, `Accordion` — 0.02, как было).
- `.tween` — переход за `duration_ms` по кривой `easing` (`ease(e, t)`: `linear`, `in/out/in_out_quad`, `in/out/in_out_cubic`, `out_back`); смена цели начинает новый переход от текущего значения.

**Шаг кадра — `ctx.anim_dt`**, его выставляет `Window.render()` в самом начале (до сброса `needs_animation`):

- если **прошлый кадр анимировался** — настоящий интервал по `SDL_GetTicks`, зажатый в `anim_max_dt` (100 мс: после подвисания анимация продолжается, а не перескакивает в конец);
- иначе — `anim_nominal_dt` (1/60 с). Иначе интервал после простоя — это секунды тишины, и анимация, начатая этим кадром (наведение после паузы), сразу прыгнула бы к цели;
- `ctx.anim_fixed_dt > 0` — ровно он, без часов. **Тесты, которые рисуют кадры подряд и ждут, что анимация сойдётся за N кадров, обязаны его ставить** (`win.ctx.anim_fixed_dt = anim_nominal_dt`): кадры в тесте идут за доли миллисекунды, и по часам анимация почти не двигается. Так сделано в `arrange_test.v`, `render_dirty_test.v`, `accordion_fit_test.v`. Тот же рычаг пригодится для записи видео по кадрам.

Вне `render()` (ручной `RenderContext`) `anim_dt` по умолчанию номинальный.

**Не больше шага за кадр.** `Anim.step` запоминает `ctx.frame_no` и второй раз в том же кадре не шагает — `update` можно звать и из `arrange()` (анимация, от которой зависит раскладка: `Accordion`), и из `draw()`. Охрана `anim_frame` в `Accordion.arrange` осталась (она же решает, считать ли виджет анимирующимся), но теперь избыточна. При `frame_no == 0` (контекст без окна) шаг — на каждый вызов.

**Что НЕ на `Anim`.** Спиннер, неопределённый прогресс, мигание курсора, задержка подсказки ссылки в `MarkdownView` и таймер уведомления — это циклы и таймеры, а не переходы к цели; они по-прежнему считают время сами от `SDL_GetTicks`. Появление/исчезновение `Notification` — на `Anim`.

Тесты — `anim_test.v`: кривые, совпадение со старым `k`, независимость от fps (два кадра по 8 мс = один на 16), прилипание и смена цели, твин и потолок шага, один шаг за кадр, расчёт `anim_dt` в `render()`, и регрессия «виджет с гаснущим кольцом фокуса просит следующий кадр» по всем девяти виджетам (проверена мутацией).

## Тема приложения и окон

`AppConfig.theme` — тема приложения. `WindowConfig.theme` и `DialogConfig.theme` — `?Theme`,
по умолчанию `none`: окно без своей темы до регистрации светлое, а `App.add_window` применяет
к нему тему приложения. Диалог без темы берёт тему родителя (`dialog_theme`), без родителя —
тему приложения в `App.add_dialog`. Заданная тема явная (`Window.theme_explicit`), как и
вызванный `Window.set_theme`. `App.set_theme(theme)` запоминает тему для будущих окон и
применяет её ко всем окнам и диалогам без явной темы (внутренний `apply_theme` меняет тему,
не делая её явной). C-ABI `vgui_app_set_theme` по-прежнему меняет тему всем открытым окнам и

## Accordion: высота секции по содержимому (`fit_content`)

По умолчанию открытая секция получает «всё свободное место» (`section_child_height`: высота
аккордеона минус заголовки) — годится для `.single`, но в `.multiple` каждая открытая секция
растягивается на всю высоту. `fit_content = true` даёт секции высоту её содержимого
(`child_height_at`): `measure_widget(...).h` содержимого, снятый в `arrange()` в
`AccordionSection.content_h` (для `measure()` самого аккордеона, который бывает раньше
`arrange`, — `fit_height` меряет секции напрямую).

В этом режиме аккордеон не прокручивается сам (`max_scroll() == 0`) — его кладут в `ScrollBox`:
`calc_widget_content_size` и `measure()` отдают полную высоту (`total_content_height`).
`ScrollBox` раскладывает ребёнка в прямоугольник высотой с видимую область, поэтому рисование,
клип и попадание мыши у аккордеона идут по `area()` — `bounds` с высотой на весь контент;
видимую часть режет клип `ScrollBox`. Тест — `accordion_fit_test.v` (позиции секций,
свёрнутая секция, `ScrollBox` видит полную высоту, клик по ряду ниже исходной видимой области
после прокрутки доходит до ребёнка, режим по умолчанию не изменился).

## Hover после прокрутки колесом

Hover-состояния (подсветка кнопок, заголовков `Accordion`, точек `CurveEditor`...) виджеты
обновляют только по `mouse_move`. Прокрутка колесом сдвигает содержимое под неподвижным курсором,

(`layout_dirty`) и рекурсивно диспетчеризуется синтетический `mouse_move` в текущей точке курсора
(`ctx.mouse_x/y`) — hover пересчитывается по новой раскладке. Тест — `wheel_hover_test.v`
(проверен мутацией).

## CurveEditor (kind 52) — редактор тональной кривой

`curve_editor.v`. Точки `points []CurvePoint` (x, y в 0..1, по возрастанию x, крайние x = 0 и 1
есть всегда и двигаются только по вертикали), через них — монотонный кубический сплайн
Фрича–Карлсона (`curve_tangents` + `hermite`): монотонные точки дают монотонную кривую, между
точками с равным y — ровное плато, без выбросов. Свободные функции `curve_eval`, `curve_lut(pts, n)`,
`curve_is_identity` работают и без виджета (vraw строит по ним таблицы пайплайна).

Мышь: левая кнопка на точке (радиус захвата ~2× точки) — перетаскивание; на пустом месте —
новая точка (не ближе `ce_min_gap` к соседям, не больше 16) и сразу перетаскивание; правая на
внутренней точке — удаление; `mouse_dbl_click` — сброс в диагональ. `on_change` — на каждое
движение, `on_release` — один раз по окончании правки (отпускание, добавление-удаление правой
кнопкой, сброс). Рисование — через рендерер (не пиксельный буфер): фон `plot_bg`, гистограмма
(`histogram`, высоты 0..1), сетка `grid_divs`, диагональ, призраки (`ghosts`), кривая толщиной 2,
точки с обводкой у активной.

**Грабля:** у `Color` альфа по умолчанию 255, поэтому «не задан (a == 0) — цвет темы» требует
ЯВНОГО значения по умолчанию `Color{0, 0, 0, 0}` (так у `curve_color`, `histogram_color`). Поле
`Color` без него — непрозрачный чёрный: кривая, точки и гистограмма рисовались чёрными. Та же
ошибка была у `Icon.color` (иконка без явного цвета — чёрная на любой теме, хотя Python-обёртка
обещала `color=None` — цвет темы); исправлено, тест `icon_color_test.v`. В `Theme` запасные цвета
(`eff_*`) объявлены с `Color{0, 0, 0, 0}` правильно.

C-ABI: `vgui_curve_editor_*` (create, set/get points, point_count, lut, reset, is_identity, цвет,
гистограмма, призраки, enabled/visible, on_change/on_release через click-диспетчер). Python —
`vguipy.CurveEditor` (`set_points`/`get_points` списком пар, `lut(n)`, `set_histogram`,
`add_ghost`...). Тесты: `curve_editor_test.v` (сплайн, мышь), `vguipy/tests/test_curve_editor.py`,
дымовой рендер. Примеры `51_curve_editor.v` / `.py`.

## ListBox: множественный выбор (`multi_select`); MenuBar.set_items

Добавлено 30.09.2026 для ленты кадров vraw (вставка настроек в несколько кадров). Флаг
`ListBox.multi_select` (по умолчанию выключен — поведение прежнее): Ctrl+щелчок добавляет/убирает
строку, Shift+щелчок — диапазон от якоря (последней строки, выбранной без Shift), Ctrl+Shift —
диапазон добавляется к выбранным, Shift+стрелки/Home/End/PgUp/PgDn — диапазон от якоря, переход без

`MenuBar.set_items(idx, items)` заменяет пункты меню `idx` (номер в порядке `add_menu`) — для меню,
меняющегося на ходу (пресеты vraw). Уже открытое меню держит свою копию списка (`MenuLevel.items`)

## Размер окна — логические единицы

`Window.config.width/height` и `Window.set_size` — в логических единицах vgui (как bounds виджетов): окно SDL имеет размер × `ui_scale`. Все пути, получающие размер от SDL (событие resize, развернуть/восстановить, первая раскладка по содержимому), переводят его через `apply_sdl_size` (SDL-размер / `ui_scale`). Раньше часть путей писала в `config` SDL-размер, и `set_ui_scale` пересчитывал окно от неверной базы, а `fit_to_content` при `ui_scale != 1` делал окно меньше содержимого. `center()` центрирует на дисплее, где окно сейчас. Тест — `window_size_test.v`.

## Сочетания Ctrl+буква (`ctrl_letter`)

TextInput, TextArea и CodeEditor распознают Ctrl+A/C/X/V/Z через `ctrl_letter(ev, буква, scancode)` (`text_input.v`): если клавиша даёт латинскую букву (keycode a..z), сравнивается сама буква — так сочетание на месте своей буквы в любой латинской раскладке (AZERTY, Dvorak); иначе раскладка нелатинская, и буква берётся по физической клавише (scancode позиции в QWERTY), поэтому Ctrl+Я работает как Ctrl+Z. Проверять только scancode нельзя (в AZERTY Ctrl+Z срабатывал на W), `keycode || scancode` — тоже (Ctrl+Q ловился как Ctrl+A). Тест — `text_area_test.v`.

## Текстовый ввод SDL — только по фокусу; Canvas.take_keys

Раньше окно звало `SDL_StartTextInput` при создании и не выключало ввод никогда. С методом ввода
(IBus, fcitx — в Ubuntu/KDE по умолчанию) SDL при включённом вводе отдаёт клавиши ему, и буквы без
модификаторов приходят только событием `text_input`, без `key_down`: однобуквенные сочетания меню и
окна (J в vraw) молча не срабатывали, а стрелки и Ctrl+буква работали (найдено 30.09.2026, vraw).
Теперь `Window.sync_text_input()` включает ввод, только пока `wants_text_input()`:
`FocusManager.wants_text()` — в фокусе `text_input` (в том числе внутренние поля Spinbox и
PropertyGrid — они фокусируются как TextInput), `text_area`, `code_editor`, либо `tree_view` /
`property_grid` во время правки (`editing`); плюс `TableView` с `editing` (своей записи в
FocusManager у таблицы нет — поиск обходом дерева `walk_widgets`). Сверка — после каждого события
кроме `mouse_move` (`dispatch_event_with_app` → `dispatch_event_inner` + `sync_text_input`), в начале
`render()` (смена фокуса из кода приложения) и в `set_default_focus_text_input` (поле с фокусом по
умолчанию получает первую же букву). Новый виджет, принимающий `text_input`, обязан попасть в
`wants_text` (или в обход у `wants_text_input`), иначе при IBus он не получит ни одной буквы.
Тест — `text_input_gate_test.v`.

`Canvas.take_keys` (по умолчанию `true` — как было): холст в фокусе забирает себе все клавиши
(`on_input`), и после щелчка по нему не работают сочетания меню и горячие клавиши окна. Холсту,
которому нужна только мышь (пипетка, щелчки по индикатору), — `take_keys = false`: клавиши идут
дальше, `on_input` их не получает. C-ABI `vgui_canvas_set_take_keys`, Python
`Canvas.set_take_keys`.

## Кольцо пипетки (Canvas.brush_ring, brush_min_px); key_mods()

Курсор-кружок кисти (`brush_cursor`, радиус `brush_radius` в пикселях буфера) при вписанном кадре
сжимается вместе с картинкой: пятно пипетки 9×9 у vraw было 2–3 экранных пикселя (30.09.2026).

## Canvas: инструменты поверх снимка (on_overlay, fx/fy, set_cursor, двойной щелчок)

Для рамки кадрирования vraw (30.09.2026):
- `Canvas.on_overlay fn (mut ctx RenderContext)` — зовётся в конце `draw` (после снимка, до полос
  прокрутки и кружка кисти), с отсечением по viewport: рамка, ручки, направляющие инструмента в
  ЭКРАННЫХ координатах. Буфер пикселей не трогает — перерисовка без загрузки текстуры. Координаты:
  `buf_to_screen(x, y)` (пиксели буфера, дробные и за краем → экран последнего кадра),
  `screen_scale()` (экранных пикселей на пиксель буфера). Только V API (RenderContext в Python не
  выведен).
- `CanvasInputEvent.fx, fy` — указатель в пикселях буфера дробными числами, БЕЗ клампа (x, y
  клампятся к буферу): ручки на краю снимка и чуть за ним. C-ABI `vgui_canvas_event_fx/fy`, Python
  `CanvasEvent.fx/fy`.
- `vgui.set_cursor(kind)` — системный курсор (`sdl_system_cursor_*`, в т.ч. `sizeall` 9 и `hand`
  11); курсоры создаются один раз на вид и кэшируются (`g_cursors`), выставляются всегда (другие
  виджеты ставят курсор напрямую — запомненный «текущий» мог бы устареть). Только V API.
- Двойной щелчок: второй быстрый щелчок приходит обычным `mouse_down` с `clicks = 2` (см.
  «Двойной клик: mouse_down, затем mouse_dbl_click»), `on_input` получает `pointer_down` с
  `clicks = 2`; следующий за ним `mouse_dbl_click` холст не обрабатывает.

## Canvas: слой детализации (set_detail)

Для настоящего 1:1 vraw (03.10.2026): превью half-size в буфере, а при увеличении поверх — фрагмент
полного кадра.
- `set_detail(pixels, n, w, h, x, y, rw, rh)` — RGBA-картинка w×h (копируется) рисуется поверх
  буфера на прямоугольнике (x, y, rw, rh) в ПИКСЕЛЯХ БУФЕРА (дробные можно): плотнее буфера
  (rw < w) — остаётся резкой при увеличении. Рисуется после снимка, до полос прокрутки и
  `on_overlay`, с отсечением по viewport; своя текстура (`detail_tex`, пересоздаётся при смене
  размера или рендерера, освобождается в `destroy_texture`), поэтому смена слоя основной буфер не
  перезагружает. Неверный размер (`n < w*h*4`, пустой прямоугольник) — слой снимается.
  Масштабирование текстуры — nearest, как у снимка.
- `clear_detail()`, `has_detail()`; `visible_buf_rect()` — видимая часть буфера в последнем кадре
  (пиксели буфера, в пределах буфера; пусто до первой отрисовки) — что должен покрыть фрагмент.
- C-ABI `vgui_canvas_set_detail/clear_detail/has_detail`, `vgui_canvas_visible_buf_rect` (out-
  параметры); Python `Canvas.set_detail(data, width, height, x, y, w, h)` (размер данных и
  прямоугольника проверяется — `ValueError`), `clear_detail`, `has_detail`, `visible_buf_rect()`.
- Тест `canvas_detail_test.v` — по настоящим пикселям кадра (`SDL_RenderReadPixels`): слой поверх
  нужной четверти, снятие, видимая часть при увеличении.

## Клик срабатывает по отпусканию (Button, CheckBox, RadioButton, ToggleSwitch)

Действие по клику у всех четырёх — на `mouse_up`, а не на `mouse_down`, как в Qt/GTK/Windows.
`mouse_down` над виджетом только фокусирует и ставит флаг `pressed`. `mouse_up` при `pressed`
снимает флаг и, если курсор всё ещё над виджетом (`hovered`), выполняет действие: `do_activate` /
`toggle` / `select_in_group`. `mouse_move` за пределы виджета сбрасывает `pressed`, то есть увод
курсора отменяет клик. Клавиатура (пробел/Enter) по-прежнему срабатывает сразу по `key_down`.

Зачем: колбэк приложения может быть тяжёлым (перепроявка кадра в vraw ~0.6 с), и на `mouse_down`
он выполнялся, пока кнопка мыши зажата. Раньше CheckBox/RadioButton/ToggleSwitch переключались на
`mouse_down`. Новый кликабельный виджет должен делать так же (образец — `Button`, `DropZone`).
Тестовый `support.click()` шлёт down+up, так что тесты это покрывают.

## Двойной клик: mouse_down, затем mouse_dbl_click

С 13.10.2026 (аудит 2026-10, п. 6.3). `parse_sdl_event` превращает любое нажатие кнопки мыши в
`mouse_down` с `clicks` (счёт быстрых кликов ведёт SDL), а `Window.dispatch_event_with_app` при
`clicks >= 2` сразу следом рассылает копию события с типом `mouse_dbl_click`. Раньше второй клик
приходил ВМЕСТО `mouse_down`, и виджет, слушающий только нажатия, его терял.

Следствие для виджетов: **`mouse_dbl_click` — добавка к уже отработавшему нажатию, а не замена**.
Ветка двойного клика не должна повторять действие нажатия, иначе оно сработает дважды: `TreeView`
по стрелке в `mouse_dbl_click` ничего не делает (ветку уже переключил `mouse_down`),
`PropertyGrid` не переключает повторно стрелку группы и флажок в колонке значения, `Canvas`
обрабатывает только `mouse_down` (с `clicks = 2`). Тест — `dbl_click_test.v`.

## CodeEditor в фокус-учёте: Tab - отступ, Ctrl+Tab - фокус

С 13.10.2026 (п. 6.1). `CodeEditor` регистрируется в `FocusManager` из `draw()` (`FocusKind`
свой), фокус берёт/отдаёт через `ctx.focus` (`take_focus`/`drop_focus`: клик, Esc), поле
`focused` лишь отражает состояние менеджера. Tab/Shift+Tab в редактируемом режиме — отступ,
Ctrl+Tab/Ctrl+Shift+Tab — переход к следующему/предыдущему виджету (`tab_focus`); в `readonly`
отступов нет, и Tab тоже передаёт фокус.

«Желаемая колонка»: при движении вверх/вниз (`move_to_line`) курсор держит колонку `goal_col`,
даже проходя короткие строки. Колонка действительна, пока курсор стоит там, куда его поставило
последнее вертикальное движение (`goal_at`); любое другое перемещение её сбрасывает. Тест —
`code_editor_focus_test.v`.

## ListBox: сортировка строк (`auto_sort`)

С 13.10.2026 (п. 6.2). При `auto_sort = true` (по умолчанию) ListBox сам упорядочивает строки по
колонке с индикатором сортировки — щелчок по кнопке в шапке или `set_column_sort` (последний
`on_sort` не зовёт). `resort()` переставляет все строки, `push_row` вставляет новую сразу на её
место. Сортировка устойчива: равенства разбивает порядковый номер добавления `LbRow.seq`, и
направление `none_` возвращает исходный порядок. Выбор (`selected`, отметки множественного выбора,
якорь Shift) следует за своими строками. Сравнение — `sort_cmp` или по умолчанию `lb_text_cmp`
(оба текста числа — как числа, иначе строки без учёта регистра). `set_row_cell_text` порядок не
обновляет — после правки зовите `resort()`. `auto_sort = false` — прежнее поведение: только
индикатор и `on_sort`, сортирует приложение. Только V API (сортируемых колонок в Python нет). Тест —
`list_box_sort_test.v`.

## Виртуальный режим ListBox и TableView (`set_virtual`); шапка колонок

С 16.10.2026. **Зачем.** В обычном режиме каждая строка - копия данных внутри виджета (`LbRow`,
`TableRow`). Для десятков тысяч строк это нормально, для миллиона (лог, выборка из БД) - лишняя память
и долгое заполнение. В виртуальном режиме виджет хранит только число строк и спрашивает текст ячейки
колбэком `fn (row, col) string`, и только для строк, видимых в этом кадре.

**API** (у обоих виджетов одинаковое): `set_virtual(count, text_fn)` - включить (строки, добавленные
раньше, удаляются, выбор/прокрутка сбрасываются; `text_fn = nil` - выключить); `set_virtual_count(n)` -
данных стало больше/меньше (прокрутка остаётся, выбор за концом переезжает на последнюю строку, отметки
множественного выбора за концом снимаются, правка ушедшей строки таблицы отменяется);
`clear_virtual()`, а также `clear()`/`clear_rows()` - выключить, виджет снова обычный и пустой. Данные
поменялись при том же числе строк - просто перерисовать окно: колбэк зовётся на каждом кадре. У ListBox
ещё `set_virtual_icons(fn (row) ItemIcon)`. Пример - `examples/57_virtual_rows.v`.

**Устройство.** Весь код, которому всё равно, откуда данные, ходит через `row_total()` (число строк в
любом режиме), `cell_text`/`cell_at` (таблица), `cell_text`/`item_text`/`row_icon`/`cell_widget`
(список), а не напрямую в `rows`/`items`. Новое место, читающее `rows.len` как «число строк», в
виртуальном режиме увидит ноль - это первое, что проверять при странностях.
- Отрисовка и попадание мышью перебирают только видимый диапазон. У ListBox так было и раньше
  (`visible_row_range_*`); у TableView цикл раньше шёл с нулевой строки и пропускал невидимые -
  теперь стартует с `first_row_from(scroll_y)`: в виртуальном режиме это деление (все строки высотой
  `row_height`), в обычном - проход по высотам, как раньше (у строк своя высота).
- **Позиции строк считаются в f64** (`TableView.row_y`, `ListBox.row_screen_y`/`item_screen_x`,
  `hit_item`). `i * item_height` при миллионах строк выходит за 24 бита мантиссы f32, и соседние строки
  рисовались бы со сдвигом в пиксель-другой, а клик попадал бы в соседнюю строку. Сама прокрутка
  (`scroll_y`) осталась f32 (публичное поле, C-ABI): на ~1 млн строк её шаг - 2 px, на ~10 млн - 16 px;
  для просмотра этого хватает.
- Чего в виртуальном режиме нет. Таблица: своих цветов/выравнивания/флага правки у ячеек (только у
  колонки и `editable` таблицы), своей высоты строки и её перетаскивания (`hit_row_border` → -1);
  правка ячейки не сохраняется в виджете, текст уходит в `on_change`, и приложение само обновляет данные
  (иначе ячейка покажет старый текст). `auto_fit_columns` меряет только первые
  `tbl_autofit_max_rows` (1000) строк. Список: виджетов в ячейках, `user_data`, `set_row_icon`,
  `auto_sort` (`resort` ничего не делает; порядок задаёт приложение в `on_sort` и перерисовывает окно).
  `add_*`/`set_cell*` в виртуальном режиме на экране ничего не меняют.
- Колбэки зовутся из `draw()` главного потока (и из `get_selected_text`, `on_select`, Enter): они
  должны быть быстрыми и не менять виджет.

**Множественный выбор на больших списках.** `sel_marks` теперь всегда отсортирован и без повторов:
`is_row_selected` (на каждую видимую строку каждого кадра) - двоичный поиск `lb_marks_find`, Shift-
диапазон - `lb_range`, Ctrl+Shift - слияние `lb_merge_marks` за один проход, Ctrl - вставка/удаление по
позиции. Раньше диапазон собирался с проверкой `i !in marks` на каждый элемент - квадратично, Shift+щелчок
через 300 тыс. строк подвешивал программу. `resort` после перестановки сортирует отметки заново.
`set_selection` сохраняет прежнюю семантику: текущая строка - последняя из первых вхождений.

**Шапка колонок** (общий вид у TableView и ListBox, `draw_header` в обоих файлах):
- полоса на всю внутреннюю ширину (и над вертикальной полосой прокрутки) со скруглёнными **верхними**
  углами радиуса `border_radius - pad` (`tbl_fill_header_band`: SDL умеет только все четыре угла, так что
  скруглённый прямоугольник + обычный поверх нижней части) - прямоугольная заливка вылезала углами за
  скруглённую рамку; снизу линия `header_border` (у таблицы CSS-свойство `header-border-color` раньше ни
  на что не влияло - виджет его не читал);
- заголовки - **обычным** шрифтом, не `.bold`: настоящего Roboto Bold в наборе нет (см. `embedded_fonts.v`),
  а синтезированный SDL3_ttf жирный грубо утолщает и расширяет буквы («Разм…» обрезалось там, где
  обычный текст помещается). Выравнивание - как у данных колонки (у таблицы раньше всегда по центру);
- между колонками - короткие чёрточки цвета сетки (`tbl_header_sep_inset` сверху и снизу), а не линии на
  всю высоту; у ListBox - всегда, а не только при `show_grid`;
- ListBox: сортировать можно щелчком **по всему заголовку** сортируемой колонки (`hit_sort_col`; границы
  для изменения ширины проверяются раньше), колонка под курсором подсвечивается; индикатор - треугольник
  у отсортированной, бледный ромб у неотсортированной только при наведении.
- TableView: PageUp/PageDown - на страницу строк (без них по виртуальной таблице с клавиатуры не походить).

Тесты - `virtual_rows_test.v` (колбэк зовётся только для видимых строк на 10 млн, клик и клавиши на
глубокой прокрутке, правка через `on_change`, `set_virtual_count`, Shift-диапазон на 300 тыс. строк,
помощники отметок), вид шапки - снапшоты `lists_*`, `state_hover_row_*`, `css_styles_*`.

## Временные модальные диалоги освобождают себя сами

Одноразовые диалоги (`message_box` в `native_file_dialog.v`, `color_dialog`, `date_dialog`) вызывают `app.remove_dialog(dlg)` + `dlg.win.cleanup()` после wait-loop на **каждом** пути выхода — `close_with_result` лишь прячет SDL-окно, поэтому без этого каждый вызов навсегда утекал скрытым `SDL_Window` + рендерером + деревом виджетов, а `app.dialogs` рос (и перебирался) каждый кадр. `App.remove_dialog(d)` / `App.remove_window(w)` (`sdl3_app.v`) отсоединяют по тождеству указателя, не освобождая. `vgui_dialog_destroy` / `vgui_window_destroy` дополнительно убирают объект из `app.dialogs` / `app.windows` (обходом `g_apps`), так что Python-сторонний `_destroy_now()` больше не оставляет висячую V-ссылку в списках App. Интроспекционные экспорты для тестов на утечки: `vgui_app_dialog_count` / `vgui_app_window_count` (объявлены в `_lib.py`). Нюанс: уничтожение окна/диалога изнутри Python-колбэка делает delete из списка, по которому `process_events` может в этот момент итерироваться, — V-шный `for-in` перечитывает `len` на каждом шаге, поэтому худший случай — один пропущенный элемент в текущем проходе, а не UB.

## Компилятор V

Компилятор V не в `PATH`: `~/soft/v/v` (на 15.10.2026 — V 0.5.2 `ecafbd9`). Команды из CLAUDE.md подставляют его через `PATH="$HOME/soft/v:$PATH"` или вызывают по полному пути.

**Новый компилятор и откат на старый.** С V 0.5.2 `0cd9c45` проект целиком собирается новым компилятором. Если в выводе снова появилось `V compilation failed (...); retrying with ...`, V откатился на старый (`~/.cache/v/v1-fallback/0.5.2/v`): сборка пройдёт, но это регрессия, её стоит разобрать. Проверять без отката — с `V_MACOS_V3_NO_FALLBACK=1` (несмотря на имя, работает и на Linux). При своём падении V сам шлёт отчёт на `bugs.vlang.io` — это нормально, глушить не надо.

**Глобальные переменные без `-enable-globals`** (с 15.10.2026). Каждый файл, где объявлена `__global`, начинается с атрибута `@[has_globals]` перед строкой `module` - тогда флаг `-enable-globals` не нужен ни при сборке, ни в `v test`. Атрибут действует на **файл**, а не на модуль (`has_globals_files` в чекере V): проверяется только объявление `__global`, использовать глобальную переменную из других файлов модуля можно без него. Новый файл с `__global` без атрибута - ошибка сборки `use v -enable-globals ... to enable globals`. Так устроены vgui, vgui-capi (`vgui_capi.v` и тесты со своими `__global`) и vraw.

**Где компиляторы расходятся** (обходы уже в коде — не откатывайте их):

- **Приведение интерфейса к указателю.** Старый при `&T(w)` от интерфейса снимал обёртку, новый — нет: адрес объекта за интерфейсом читается из поля `_object` по смещению 0 (`widget_object_addr`, «Layout: measure/arrange», кэш `SizeHint`).
- **Экспорт всех функций из `.so`** (vlang/v#28749, исправлен 02.10.2026, проверено на `0137eb5`). Новый `v -shared` выставлял наружу не только `@[export]`, но и все функции модуля и `builtin`, а позже - символы `GC_*` Boehm GC. Сейчас экспортируются только `vgui_*`; `check_capi.py` считает лишний `vgui__*` в экспорте ошибкой (vgui-capi/PROJECT.md, «Кодогенерация C-ABI»), так что возврат бага будет замечен.
- **Замыкание, присвоенное полю через приведённый указатель, уничтожается** (vlang/v#28795, исправлен 28.09.2026, проверено на `0137eb5` вместе с вариантом в цикле; обход оставлен - он безвреден). `mut w := unsafe { &T(ptr) }; w.f = fn [id] ...` — новый V вставлял `closure_try_destroy` на выходе из функции, и первый вызов колбэка прыгал на адрес 0. По-прежнему писать через локальную переменную: `callback := fn [id] ...; w.f = callback`. Так генерирует `gen_capi.py` и так написаны ручные сеттеры; подробности и регрессионные тесты — vgui-capi/PROJECT.md, «Кодогенерация C-ABI». То же в **теле цикла** у приложения (27.09.2026, vraw): `for c in .. { mut b := arr[c]; b.on_click = fn [c] ... }` — замыкание уничтожалось в конце итерации, вызов попадал в чужое замыкание или в неверную память (кнопки молча не работали). Обход был тот же, либо ставить колбэк на только что созданный объект, либо присваивать по индексу `arr[c].on_click = ...`.
- **Несуществующее значение enum молча принималось** (vlang/v#28796, исправлен 01.10.2026, проверено на `0137eb5`): полное имя `Color2.blue` при enum без `blue` компилировалось в 0, а `.blue` в ветке `match` просто принималось. Теперь, как и у старого компилятора, это ошибка сборки; vgui на `0137eb5` собирается, то есть таких опечаток в коде нет.
- **Метод с параметром `mut x &T` получает не тот указатель** (vlang/v#28864, исправлен 23.09.2026, проверено на `fe156bd`; обход оставлен - он безвреден). В C параметр объявлен как `T**`, а при вызове **метода** передаётся сама переменная `T*` без `&` - падение `invalid memory access`; у обычной функции всё верно. Параметры-ссылки методов объявлять неизменяемыми (`entry &T`) и внутри делать `mut e := unsafe { entry }` - так написан `Tray.add_entry` (без обхода падал любой `Tray.add_item`). Сейчас других `mut x &T` в vgui нет; новые не заводить.

- **`int` в этой V 64-битный** (обнаружено 30.09.2026 на `fe156bd`), а ctypes передаёт `c_int` —
  32 бита. Массив `c_int`, прочитанный через `&int`, давал склеенные пары (`[3, 1]` → `4294967299`),
  а out-параметр `*out = v` через `&int` писал 8 байт в 4-байтовый `c_int` — затирал соседнюю память
  (`vgui_date_picker_get_date`, `vgui_table_view_get_selected`, `vgui_embedded_*_font`), а у
  `vgui_date_dialog` месяц и день вообще попадали не в свои ячейки `out_ymd`. Исправлено там же:
  тип спеки `p_int` теперь `&i32` (`capi_dsl.py`), raw-функции пишут `*out = i32(v)` и читают
  `int(arr[i])`; `check_capi.py` сверяет сигнатуры, так что `&int` в raw-функции с `p_int` не
  пройдёт. Регрессия — `vguipy/tests/test_int_width.py`: за out-параметром лежит «часовой», который
  должен остаться цел. Скалярные `int`-аргументы и результаты на практике работают, в том числе отрицательные
  (`set_selected(-1)` в `test_validation.py`), но отдельно по ABI не разбирались.

- **`match`-выражение с `!` в ветках и интерфейсным результатом — невалидный C** (13.10.2026,
  V 0.5.2 `1b4ecb9`, vlang/v#30446). `s := match k { 'a' { make_a()! } else { make_b()! } }`, где
  функции возвращают `!&Interface`, генерирует `_ifexpr = (!__or_opt_1.ok ? : )` — ошибка сборки C,
  после чего V молча откатывается на старый компилятор (а тот vgui уже не собирает).
  Воспроизведение — 40 строк: интерфейс, две структуры, две фабрики `!&Shape` и такой `match`.
  Обход — `match` оператором с `return` в каждой ветке (`UiBuilder.build_widget`/`build_leaf` в
  `ui_markup.v`).
  На 15.10.2026 issue открыта, на master `ecafbd9` ещё воспроизводится; исправление - PR
  vlang/v#30588 (на его ветке пример собирается и работает). Обход оставить и после слияния.

Статус issue смотреть через `gh issue view <номер> -R vlang/v`; после исправления обходы можно оставить — они безвредны.

## Зависимости SDL3 (поиск в системных путях)

`libvgui.so` динамически линкуется с тремя SDL3-библиотеками (`libSDL3.so.0`, `libSDL3_ttf.so.0`, `libSDL3_image.so.0`). Они **не бандлятся** рядом с `libvgui.so` — зависимости резолвит штатный механизм ОС по системным путям, и никакого RPATH/RUNPATH в библиотеку не вшивается (`vgui-capi/build.sh` только собирает `.so` и копирует её в соседний vguipy).

Из этого следует, что SDL3 (>= 3.2, для `IMG_SaveWEBP` — SDL_image >= 3.4.0) должна быть **установлена на машине**. В стандартных репозиториях дистрибутивов её ещё нет, поэтому обычно она собирается из исходников и ставится в `/usr/local/lib`.

- **Linux (ELF)** — ищет `ld.so`: пути из `/etc/ld.so.conf.d/*` + кэш `ldconfig`, затем `LD_LIBRARY_PATH`. Если SDL3 стоит в `/usr/local/lib`, а этот путь не в конфиге — добавьте его и выполните `sudo ldconfig`. Проверка: `ldd libvgui.so | grep -i sdl` — все три должны резолвиться (не `not found`); `readelf -d libvgui.so | grep -i runpath` не должен ничего печатать.
- **macOS (Mach-O)** — стандартные пути `dyld` (`/usr/local/lib`, `/opt/homebrew/lib`) либо `DYLD_LIBRARY_PATH`. Проверка — `otool -L libvgui.dylib`.
- **Windows (PE)** — каталог exe, System32 и `PATH`. Положите `SDL3.dll` / `SDL3_ttf.dll` / `SDL3_image.dll` (и их транзитивные зависимости из MinGW: harfbuzz/freetype/png/...) в один из этих путей; `_lib.py` **не** трогает путь поиска DLL.

Реально протестирована только **Linux**-ветка (на ней и собран проект); macOS/Windows-ветки `build.sh` заложены как кроссплатформенная основа и требуют проверки на соответствующей ОС.

Транзитивные зависимости самой SDL3 (`libharfbuzz`, `libfreetype`, `libpng`, `libz`, `libglib`, `libbrotli*` и т.д.) берутся оттуда же, из системы, и присутствуют практически на любом десктопе. Если когда-нибудь понадобится самодостаточная поставка «всё в одной папке» — это отдельная задача (AppImage / бандл с RUNPATH), а не точечная правка `build.sh`.

en и ru), язык системы и прежний API (`vgui.tr`, `vgui.set_locale`...).

- **Каталог** `локаль -> {ключ: перевод}`. Ключ — идентификатор или сам
  текст на исходном языке кода (`set_source_locale('ru')`, как gettext:
  код читаем, исходный язык не нужен отдельным файлом).
- **Поиск `tr(key)`:** текущая локаль → ключ, если текущая — исходная →
  запасная (`set_fallback`, по умолчанию en) → ключ. Ключи-идентификаторы
  vgui ищутся в таблице и для исходного языка (`btn.ok` → «ОК» в ru).
- **Таблицы:** `set_loader(fn (code) string)` — текст JSON
  `{"ключ": "перевод"}` (приложение вшивает файлы `$embed_file`);
  `set_locale` подгружает текущую и запасную (раз на локаль, `g_tr_loaded`).
  Или `add_translations(_json)`. `tr_in(code, key)` — перевод на другую
  локаль без смены текущей: незагруженную читает загрузчиком, не трогая
  каталог.
- **`trf`** — `{0}`, `{1}`; **`trc(ctx, s)`** — омоним (ключ
  `контекст::строка`); **`tr_all`**; **`pl(n, 'один|два|пять')`** — форма
  числа: в переводе формы своего языка через «|» в порядке
  `plural_index` (CLDR для целых: славянские 3, словенский 4, латышский —
  ноль/один/прочие, вьетнамский и индонезийский 1, остальные 2); без
  перевода — формы и правило исходного языка.
- **`languages`** — 31 язык с самоназванием и правилом форм (`known`,
  `lang_name`); **`locale_code`** — `uk_UA.UTF-8` → `uk`, no/nn → nb,
  C/POSIX → ''; **`env_locale`** — LC_ALL, LC_MESSAGES, LANG, LANGUAGE.
- **`vgui.detect_system_locale()`** — переменные окружения, иначе
  `SDL_GetPreferredLocales` (Windows, macOS: переменных там обычно нет),
  иначе en. Код может быть не из `languages`.
- **`i18n_init()`** (из `vgui.tr`/`set_locale`, раз): строки vgui в
  каталог; локаль — язык системы, только если приложение не выбрало её
  явно (`i18n.locale_set()`).
- **Потоки:** `set_*`, `add_*` — только из главного потока при запуске;
  дальше каталог только читается, `tr/trf/trc/pl/tr_in` — из любых потоков.
- Тесты: `i18n/i18n_test.v`, `vguipy/tests/test_i18n.py`.
- Строки vgui переведены только на en и ru: в других локалях диалоги
  vgui (выбор файла, даты, цвета) — по-английски.

## Заголовок окна вне Latin-1 на X11: `setlocale(LC_CTYPE, "")`

`create_app` на Linux первым делом зовёт `setlocale(LC_CTYPE, "")`. Причина — SDL3 (`SDL_X11_SetWindowTitle`): она сначала переводит заголовок в кодировку C-локали (`XmbTextListToTextProperty`) и, если хоть один символ не переводится, **выходит, не записав `_NET_WM_NAME`** (UTF-8 заголовок). Без `setlocale` программа живёт в локали «C»: кириллица случайно проходит (байты UTF-8 формально влезают в Latin-1), а вьетнамский заголовок — нет, и оконный менеджер показывает кашу из `WM_NAME`. Меняется только `LC_CTYPE` (классификация символов), форматы чисел (`LC_NUMERIC`) остаются «C». Проверка: `xprop -id <окно> _NET_WM_NAME` (08.10.2026, перевод vraw на вьетнамский).

## Архитектура рендеринга (`sdl3_render.v`)

Вся отрисовка идёт через `SDL_RenderGeometry` (массивы вершин) — без зависимости от SDL2_gfx.

**Скруглённые прямоугольники** — два отдельных примитива должны оставаться геометрически согласованными:
- `render_fill_rounded_rect` — веер треугольников от центра прямоугольника к контуру дуги
- `render_draw_rounded_rect` — лента квадов между внешней дугой (`r`) и внутренней (`r - 2t`), где `t = 0.5 / (dpi_scale * ui_scale)` (1 физический пиксель). Рамка полностью **врезана внутрь** — внешний край лежит ровно на `r`, никогда не выходя за границу заливки. **Прямые стороны рисуются `SDL_RenderFillRects`, не геометрией** (с 14.10.2026): программный рендерер SDL распознаёт пару треугольников-прямоугольник и рисует её прямоугольником, отбрасывая дробную часть размеров, и полоса шириной «1 пиксель минус погрешность float» при дробном масштабе (1.25, 1.5) обнулялась — у полей, панелей, списков пропадали стороны рамки. GPU-рендереры (OpenGL, GLES2, Vulkan) рисовали верно, но тесты и машины без ускорения идут через программный. Стороны считаются как в `draw_rect`: от границ, привязанных к сетке, ширина ровно `1/scale`. Проверка рендереров без экрана: `SDL_VIDEODRIVER=offscreen SDL_RENDER_DRIVER=opengl|vulkan|software` (окно — не через `testkit`, он ставит `dummy`).

Оба используют одну формулу сегментации дуги: `n = max(8, r * 2.0)` на четверть окружности. Расхождение этих формул даёт визуально неодинаковые углы.

**Пиксельная привязка** — `snap_rect(r Rect) Rect` приводит логические координаты к ближайшей границе физического пикселя перед отрисовкой скруглённых прямоугольников. Без этого кнопки на разных X получают разные субпиксельные смещения, и углы выглядят по-разному при дробном `ui_scale` (например, 1.25).

**Масштаб рендера** — `ctx.dpi_scale * ctx.ui_scale` — совокупный коэффициент преобразования логических координат в физические. Вся геометрия в логических единицах; физическое отображение берёт на себя render scale SDL.

**Кэш текстовых текстур (`sdl3_fonts.v`, `text_cache` в RenderContext)** — ключ остаётся u64 FNV-1a (горячий путь без аллокации строки-ключа), но коллизии **обрабатываются**, а не игнорируются: каждая `TextCacheEntry` хранит исходные (text, font_size, style_int, color), и хит хэша с несовпадающими полями трактуется как промах — чужая текстура уничтожается и перерисовывается. Цена коллизии — один лишний рендер, а не навсегда неверный текст. Не убирайте поля верификации ради «экономии памяти».

**Кэш шрифтов по размерам (`FontSet.size_cache`)** — ключ `'{style}_{логический_размер}_{физический_размер}'`. Физический размер (`open_size = размер × dpi_scale × ui_scale`) обязан входить в ключ: `FontSet` шарится через `g_font_cache` между окнами, у которых масштабы могут различаться, и ключ только по логическому размеру отдавал бы окну шрифт, открытый под чужой масштаб. `get_font` и `get_font_immut` обязаны вычислять ключ одинаково.

**Время жизни `FontSet` — подсчёт ссылок (`font_cache.v`).** Масштаб входит в размер, размер — в ключ `g_font_cache`, поэтому раньше каждое уникальное `ui_scale` навсегда оставляло набор из шести `TTF_Font` (+38 МБ за один жест Ctrl+колесо). Теперь у `FontSet` есть `refs`/`cache_key`: каждое окно держит **ровно одну** ссылку — `get_or_load_fonts` её берёт, `release_fonts` отдаёт, а на нуле закрываются все шрифты набора вместе с `size_cache` и запись удаляется. Флаг `Window.fonts_held` не даёт `cleanup()` отпустить ссылку дважды; `release_fonts` для набора, который уже не лежит в кэше под своим ключом (освобождён `destroy_font_cache` при выходе), — no-op. Правила: (1) смена шрифтов окна — только через `Window.reload_scaled_fonts()`, который **сначала берёт новый набор, потом отпускает старый** (тот же масштаб не переоткрывает шрифты, соседнее окно с тем же набором не страдает); (2) **никогда не переинициализируйте `ctx.fonts` на месте** (`init_fonts` на уже закэшированном наборе) — набор общий: так делал старый `reload_fonts_for_dpi` на HiDPI, у которого текли старые хэндлы, а у второго окна молча удваивался шрифт; (3) хэндлы `TTF_Font` нельзя хранить в полях виджетов между кадрами — после смены масштаба они закрыты. `create_dialog` копирует `Window` по значению (`*w`), и ссылка переходит к копии — исходный heap-`Window` не чистится. Ключ содержит FNV-1a **содержимого** буферов шрифта плюс длину (раньше — адрес буфера, что давало ABA), а хит проверяется сравнением байтов с пробой `#n` при несовпадении. `__global` не видны из `_test.v`, поэтому тесты ходят через `font_cache_len`/`font_cache_entry`/`font_cache_put`/`font_cache_drop`. Юнит-тесты обоих кэшей: `text_font_cache_test.v` (нужен SDL, видеодрайвер dummy) — запуск `v test text_font_cache_test.v` из корня.

**Измерение текста до первого кадра — `Window.measure_text(text, style:, size:)`** (`sdl3_fonts.v`). Возвращает логический `Vec2` размера строки тем шрифтом, каким её нарисуют виджеты; параметры по умолчанию соответствуют обычному `Label`. Работает сразу после `create_window` — шрифты загружаются там же (`get_or_load_fonts`), а `TTF_GetStringSize` не трогает рендерер, — поэтому раскладку (ширины колонок и т.п.) можно считать по фактическому тексту при сборке UI, не дожидаясь `RenderContext` в `draw()`. Внутри — `ctx.get_font` + `ctx.measure_text_with_font` (деление на `dpi_scale × ui_scale` уже учтено). Тест — в том же `text_font_cache_test.v`. C API: `vgui_window_measure_text(win, text, style, size, out_w, out_h)` — style тем же int-кодом, что у `vgui_label_set_font_style` (0=regular … 5=mono_bold), результат через out-параметры `&f32` (обнуляются даже при nil-окне). Python: `win.measure_text(text, style=FontStyle.REGULAR, size=0) -> (w, h)`.

## Экспорт кадра в файл (`image_export.v`)

`Window.save_to_image(path, quality)` / `save_region_to_image(path, region, quality)` читают текущий кадр из рендерера и пишут его на диск. Формат — по расширению: png (`IMG_SavePNG`), jpg/jpeg (`IMG_SaveJPG`), bmp (`SDL_SaveBMP`), webp (`IMG_SaveWEBP`); **tiff не пишется** — SDL_image поддерживает его только на чтение, и функция возвращает `false`, а не молча кладёт JPEG под расширением `.tiff` (то же поведение, что у `Canvas.save_file`).

**`SDL_RenderReadPixels` принимает `const SDL_Rect *` — целые числа, а НЕ `SDL_FRect`.** Раньше сюда передавался `C.SDL_FRect`, и SDL интерпретировал битовые представления float как мусорные int'ы, поэтому **любой** вызов заканчивался ошибкой «Can't read outside the current viewport» — экспорт кадра был сломан на 100 % вызовов и молча возвращал `false`. Из-за ленивого связывания (`FLAGS: SYMBOLIC`) несовпадение типов ничем не проявлялось на старте. Биндинг теперь объявлен строго: `fn C.SDL_RenderReadPixels(renderer voidptr, rect &C.SDL_Rect) voidptr`.

`IMG_SaveWEBP` требует **SDL_image >= 3.4.0**; в более старой сборке символ не найдётся при первом обращении.

## Нативные диалоги ОС (`native_file_dialog.v`)

SDL3 (>= 3.2) предоставляет нативные **файловые** диалоги (`SDL_ShowOpenFileDialog` / `SDL_ShowSaveFileDialog` / `SDL_ShowOpenFolderDialog`). vgui выставляет их как **альтернативу** кастомным диалогам из `file_dialog.v` — кастомные остаются по умолчанию; нативные включаются явно через `native=True` (Python) / функции `native_*` (V).

**`message_box` намеренно НЕ нативный SDL-овский.** `SDL_ShowMessageBox` блокирует вызывающий поток до закрытия, из-за чего родительское окно перестаёт перерисовываться и оставляет чёрные артефакты, когда окно сообщения таскают над ним. `message_box` в vgui — это кастомный модальный `Dialog` (та же механика, что у `color_dialog` / подтверждения удаления в файловом диалоге), который продолжает рендерить в своём wait-loop и чисто композитится. Поэтому ему нужны `mut app` (чтобы качать цикл) и ненулевое родительское окно. `kind` (info/warning/error) лишь выбирает глиф иконки и акцентный цвет. C-биндинги SDL_MessageBox удалены — не возвращайте их в расчёте на отсутствие артефактов.

**Нативного диалога цвета или даты намеренно нет** — в SDL3 нет такого API. `color_dialog` / `date_dialog` остаются только кастомными.

**API диалогов SDL асинхронный** — он запускает диалог ОС и вызывает C-колбэк позже из цикла событий (во время `SDL_PumpEvents`), а не на месте. Чтобы публичный API vgui остался синхронным (как кастомный `fd_run`), `native_fd_run` регистрирует ожидающий запрос с ключом — **монотонным u64 id** (то же обоснование ABA-защиты, что у `_cb_counter` в `_lib.py` — id никогда не переиспользуются), передаёт id в SDL как `userdata`, затем качает `app.process_events()`/`render_all()`, пока трамплин не пометит запрос `done`. Запоздавший колбэк брошенного запроса не находит ничего в `g_native_fd_requests` и отбрасывается.

**Время жизни фильтров / результата.** `NativeFilterSet` клонирует строки имён/паттернов фильтров в стабильные V-строки, удерживаемые весь (блокирующий) wait-loop — SDL хранит указатели `SDL_DialogFileFilter` только на время вызова, но строки, на которые они указывают, должны пережить асинхронный диалог. Та же ловушка времени жизни, что в заметках о данных шрифта / метках трея в этом файле.

Проводной формат через границу capi (`vgui_native_file_dialog` / `vgui_message_box`):
- Фильтры: одна строка `"name1|pattern1\nname2|pattern2"`; паттерны — SDL-списки через точку с запятой (`"png;jpg"`) или `"*"`. Python `_encode_filters` собирает её из списка `[(name, pattern), ...]` и вычищает случайные `|`/`\n`.
- Результаты: пути, склеенные переводами строк (мультивыбор возвращает >1); пустая строка = отмена/ошибка.

**Собственного (виджетного) файлового диалога больше нет** — удалён 13.10.2026 вместе с его переводами `fd.*`: нативный выглядит привычно для ОС и не требует поддержки. V API — `native_open_file_dialog`/`native_open_files_dialog`/`native_save_file_dialog`/`native_select_folder_dialog` (`NativeFileDialogConfig`), `FileDialogMode` живёт в `native_file_dialog.v`. Python API (`widgets.py`): `file_dialog`/`open_file_dialog`/`open_files_dialog`/`save_file_dialog`/`select_folder_dialog` всегда открывают нативный диалог (`filters=`), `message_box(window, app, title, message, kind, buttons, default_button, cancel_button)` (возвращает индекс нажатой кнопки или -1). Отдельного примера для нативных диалогов сейчас нет (демо `demo32.py`/`demo48.v` удалены при переезде на `vguipy/examples/` + `examples/`).

## Drag and drop (приём файлов/текста из других приложений)

SDL3 доставляет **drop'ы** drag-and-drop (файлы/текст, перетащенные *в* наше окно) как обычные события — никаких хинтов в стиле SDL2 или опт-ина через `SDL_EventState` не нужно; они приходят через `SDL_PollEvent` и будят цикл. API SDL3 для инициирования перетаскивания *из* окна (`SDL_StartDragAndDrop`) **не** подключён — только приём.

Конвейер (зеркалит путь клавиатуры/мыши):
- `sdl3_bindings.v` — структура `SDL_DropEvent` + константы `sdl_event_drop_file/_text/_begin/_complete/_position` (0x1000..0x1004).
- `events.v` — `EventType.drop_file/drop_text/drop_position/drop_begin/drop_complete`. Оконные координаты drop'а `x`/`y` кладутся в `ev.mouse_x`/`mouse_y` (то же координатное пространство, что у мыши, поэтому деление на `ui_scale` в `sdl3_app.v` применяется автоматически), а путь к файлу / текст — в `ev.text`.
- `sdl3_window.v` — `Window.on_drop_file fn(path string)` / `on_drop_text fn(text string)` — это **оконный fallback**: в `dispatch_event_with_app` drop сначала предлагается каждому виджету через `handle_event`; оконный обработчик срабатывает только если никто его не поглотил (`handled == false`). Устанавливаются через `set_on_drop_file` / `set_on_drop_text`.

**Виджет `DropZone` (kind 48, `drop_zone.v`)** — прямоугольная мишень. Поглощает `drop_file`/`drop_text` **только когда координаты drop'а попадают в его `bounds`** (поэтому несколько зон сосуществуют; промах проваливается к оконному обработчику). События `drop_position` выставляют флаг `hovering`, подсвечивающий зону во время перетаскивания (возвращает `false` — никогда не поглощается, так что его видят все зоны); `drop_begin`/`drop_complete` его сбрасывают. `accept_files`/`accept_text` определяют, на какие виды зона реагирует. Python: `vgui.DropZone(text=..., on_drop_file=, on_drop_text=, accept_files=, accept_text=)`.

**Клик-для-выбора (опт-ин).** При установленном `click_to_browse` левый клик по зоне открывает диалог открытия файла и передаёт выбранный путь (пути) в `on_drop_file` — *тот же* колбэк, что и у реального drop'а, так что один обработчик покрывает и перетаскивание, и выбор кликом. Диалог — нативный диалог ОС; `browse_multi` вызывает `on_drop_file` по разу на каждый выбранный файл; `browse_start_dir` / фильтры его настраивают. Обработка мыши (`mouse_down`/`mouse_up`, флаг `pressed`, подсветка hover) зеркалит `Button`; запуск диалога (`dz_open_browse` в `drop_zone.v`) получает родительское окно из `app.get_active_ctx()` и кастует `&App`→`mut App` ровно как `dp_open_dialog` в `date_picker.v`. Фильтры пересекают границу capi (`vgui_drop_zone_set_browse`) в том же проводном формате `"name|pattern\n..."`, что и `vgui_native_file_dialog` (переиспользует `parse_native_filters` / Python `_encode_filters`). Python: `vgui.DropZone(..., click_to_browse=True, browse_multi=, browse_start_dir=, browse_filters=[(name, pattern), ...])` или `zone.set_browse(...)`. V: выставляйте поля `click_to_browse` / `browse_*` прямо на `DropZone`.

И колбэки `DropZone`, и оконные обработчики едут на существующем `STRING_DISPATCHER` (`g_py_string_dispatcher`) — строковая нагрузка — это сброшенный путь/текст. Демо: `vguipy/examples/39_drop_zone.py` и `examples/39_drop_zone.v` (и приём drop'а, и клик-для-выбора).

## ImageBackground (kind 49) и фон окна (`image_background.v`)

Лёгкий виджет вывода картинки для фонов/логотипов/баннеров — в отличие от `ImageView` (kind 17) у него **нет** зума/панорамы/скроллбаров, а `handle_event` всегда возвращает `false` (пассивный, событий не ест). Управление текстурой скопировано с `ImageView` дословно: `IMG_Load`/`IMG_Load_IO` → `SDL_CreateTextureFromSurface`, тот же generation-guard реестра живых рендереров при destroy (см. «Время жизни SDL-текстур»). Поддерживает источник из файла (`path`) и из сырых байтов (`data`, клонируются внутрь — argtype Python `c_char_p`). Режимы `BgMode`: `fit` (вписать, сохранив пропорции), `fill`/`cover` (заполнить с обрезкой), `stretch` (точно в bounds), `tile` (замостить повторами), `center` (нативный размер по центру). Вся отрисовка под `push_clip(bounds)`. Опциональный `bg_color` — подложка/fallback.

**Фон окна переиспользует тот же виджет, а не дублирует логику.** `Window` хранит `bg_image &ImageBackground` (по умолчанию nil). Он создаётся лениво методами `Window.set_background_image(path)` / `_data(bytes)` / `set_background_mode(mode)` и рисуется в `Window.render()` **после** `SDL_RenderClear` и **до** цикла виджетов, с `bounds = screen_rect` — то есть позади всех виджетов, заполняя окно. `bg_image` **НЕ** анкорится в `g_image_backgrounds` (им владеет Window напрямую, не Python через `_handle`); его текстура освобождается в `Window.cleanup()` **до** `SDL_DestroyRenderer`, пока рендерер ещё жив. `clear_background()` убирает фон. Python: `win.set_background_image(path=..., data=..., mode=BgMode.COVER)`.

Для размещаемого баннера/лого используйте сам виджет в layout: `vgui.ImageBackground(path=..., mode=BgMode.FIT, bg_color=...)`, либо нижним слоем в `Stack`. Демо: `vguipy/examples/44_image_background.py`.

## Canvas (kind 50) — рисуемая поверхность с доступом к пикселям (`canvas.v`)

Виджет владеет RGBA-буфером `pixels []u8` размера `width*height*4` и **streaming**-текстурой SDL, которая зеркалит буфер. Примитивы пишут в буфер и ставят `dirty=true`; в `draw()` при `dirty` буфер заливается в текстуру через `SDL_UpdateTexture(tex, nil, pixels.data, width*4)`, потом `dirty=false`.

- **Формат пикселей — `sdl_pixelformat_abgr8888`** (= `sdl_pixelformat_rgba32`): байты в памяти идут R,G,B,A (`buf[i*4+0]=R … +3=A`) — интуитивно для вызывающей стороны. Не путать с packed-форматом `rgba8888`.
- **Streaming-текстура** создаётся в `ensure_texture` (`SDL_CreateTexture(..., sdl_textureaccess_streaming, ...)`, scale mode `nearest` для чёткости пикселей), пересоздаётся при смене/смерти рендерера (тот же generation-guard, что у `ImageView`). Биндинги `SDL_UpdateTexture` + константа `sdl_textureaccess_streaming` добавлены в `sdl3_bindings.v` (`target`/`nearest`/`linear` там уже были).
- **Отображение** — буфер показывается внутри `bounds` в режиме fit (сохранение пропорций, центрирование) по умолчанию, либо stretch (`set_stretch(true)`). Dst-rect считается в `compute_disp()` каждый кадр и переиспользуется для обратного маппинга мыши.
- **Зум / панорама / скроллбары (навигация по изображению).** Модель скопирована с `ImageView` (kind 17): поля `auto_fit`/`zoom`/`scroll_x`/`scroll_y` + drag-состояния панорамы и скроллбаров. **`auto_fit = true` (по умолчанию)** — весь буфер вписан в `bounds` и центрирован (то самое прежнее fit-поведение, без скроллбаров); как только пользователь зумит или панорамирует, `auto_fit` выключается и включаются `zoom` + scroll со скроллбарами. `compute_disp()` теперь делегирует в `image_draw_rect()` (viewport минус ширина скроллбаров `cv_sb_w`, top-left со scroll-смещением, центрирование если меньше viewport) — **поэтому `map_to_pixel`/`map_to_pixel_clamped` остаются корректными на любом зуме**, и рисование/`on_stroke` идут с точностью до пикселя нативного разрешения. Мышь: **колесо — зум к курсору** (`zoom_at(mx,my,nz)`, anchored на пиксель под курсором; курсор берётся из `app.get_active_ctx()`, т.к. wheel-событие несёт устаревшие x/y), **средняя/правая кнопка — панорама**; **левая кнопка остаётся рисованием** (но сначала проверяется захват ползунка скроллбара). `handle_event` приоритизирует так: активный stroke (drawing) → панорама → drag вертикального/горизонтального скроллбара → обычная диспетчеризация по типу события. API: `set_zoom(z)` (px экрана на px буфера, выключает auto_fit), `get_zoom()` (возвращает `eff_scale()`), `zoom_in()`/`zoom_out()` (от центра), `fit_to_view()` (возврат в auto_fit). capi: `vgui_canvas_{set_zoom,get_zoom,zoom_in,zoom_out,fit_to_view}`. Константы `cv_min_zoom=0.02`/`cv_max_zoom=32.0`. **Это позволяет грузить картинку в нативном разрешении (`load_file` не уменьшает) и редактировать/сохранять в полном размере, навигируя зумом** — вместо вписывания фото в маленький холст.
- **Примитивы** (`set_pixel`/`get_pixel`/`fill`/`clear`/`draw_line` (Брезенхэм)/`draw_rect`/`fill_rect`/`draw_circle`/`fill_circle`) — все с bounds-check по `width/height`, перезапись без блендинга. `clear()` = прозрачный; конструктор инициализирует буфер непрозрачным белым.
- **Доступ к массиву пикселей.** `pixels_ptr()`/`pixels_len()` отдают сырой указатель/длину; `set_pixels(src, n)` копирует через `vmemcpy`. Python: `get_pixels() -> bytes` (`ctypes.string_at`, копия `w*h*4`), `set_pixels(data: bytes)` (валидирует длину == `w*h*4`). Совместимо с `bytes`/`bytearray`/`numpy.frombuffer(buf, np.uint8).reshape(h, w, 4)`. Для bulk-записи через границу capi argtype Python — **`c_char_p`** (та же ловушка `bytes`→null).
- **Freehand-рисование.** `handle_event` на `mouse_down`(left)/`mouse_move`(при `drawing`)/`mouse_up` отображает оконные координаты в пиксельные через сохранённый dst-rect и зовёт `on_draw(px, py)`. Python-колбэк едет на существующем `INT_INT_DISPATCHER` (`g_py_int_int_dispatcher`) — `vgui_canvas_set_on_draw` строит замыкание `fn [cb_id](x, y){ g_py_int_int_dispatcher(cb_id, x, y) }`, как `vgui_slider_set_on_change`. Колбэк сам пишет в буфер (set_pixel/fill_circle/...), реализуя кисть.
- **`on_stroke(phase, x, y)` — для инструментов рисования.** Надмножество `on_draw`: вызывается на тех же `mouse_down`/`mouse_move`, **но также на `mouse_up`** (фаза 2), а координату **клампит** в буфер (`map_to_pixel_clamped`), а не отбрасывает за пределами dst-rect — поэтому таскание за край прижимается к границе, а не пропадает. Фаза: int `0 = down`, `1 = move`, `2 = up`. Кистевые инструменты (кисть/карандаш/ластик/пипетка/заливка) рисуют на down/move; фигуры (линия/прямоугольник/эллипс) с **резиновой нитью** делаются так: на `down` снимок холста (`get_pixels` / V `pixels.clone()`), на `move`/`up` — откат снимка (`set_pixels` / V `copy`) + перерисовка фигуры старт→текущая. Едет на `INT_INT_INT_DISPATCHER` (`g_py_int_int_int_dispatcher`, тот же, что у `DatePicker.on_change`) — `vgui_canvas_set_on_stroke` строит `fn [cb_id](phase, x, y){ g_py_int_int_int_dispatcher(cb_id, phase, x, y) }`. Python-обёртка `set_on_stroke` транслирует int-фазу в строку `"down"/"move"/"up"`. Заливку (flood fill) демо делает через bulk `get_pixels`/`set_pixels` (один батч, без тысяч C-вызовов). `on_draw` и `on_stroke` независимы; для нового кода достаточно одного `on_stroke`.
- **`on_input(ev)` — единый богатый поток ввода (полная поверхность для инструментов редактора).** Надмножество `on_draw`/`on_stroke` (те остаются как удобные сокращения для простых кистей; реальный инструмент использует только `on_input`). Доставляет **все** события: `pointer_down/move/up`, `hover`, `enter/leave`, `wheel`, `key_down/key_up` — каждое с **модификаторами (shift/ctrl/alt), кнопкой мыши и счётчиком кликов**. Это даёт ровно то, чего не хватало одним `on_draw/on_stroke`: Shift-зажим фигур, правую кнопку как отдельный инструмент, клавиатурные шорткаты, hover-предпросмотр.
  - **Проводной формат — НЕ новый диспетчер, а struct-by-pointer.** `vgui_canvas_set_on_input` строит замыкание `fn [cb_id](ev &CanvasInputEvent){ g_py_voidp_dispatcher(cb_id, voidptr(ev)) }` — едет на **существующем `VOIDP_DISPATCHER`**, ровно как `PropertyGrid.on_change` отдаёт `&Property`. `CanvasInputEvent` — плоская value-структура (без указателей), её поля Python читает **ленивыми геттерами** `vgui_canvas_event_{kind,x,y,in_image,button,clicks,wheel_x,wheel_y,keycode,scancode,mods}` (тот же идиом, что у `vgui_property_get_*`). Указатель валиден **только** на время синхронного вызова (одно-поточность). Модификаторы упакованы в один геттер `mods` (биты shift=1/ctrl=2/alt=4), чтобы не делать 3 C-вызова на событие. **Расширять событие = добавить поле в `CanvasInputEvent` + геттер**, без правки сигнатуры диспетчера. `enum CanvasEventKind` дублирован на обеих сторонах (V + Python `types.py`); кнопки — `mouse_btn_to_int` (стабильные 1/2/3, независимо от ординалов `MouseButton`). SDL-free юнит-тест геттеров: `vgui-capi/canvas_event_test.v`.
  - **Маршрутизация ввода настраивается** (чтобы инструмент мог забрать кнопки/колесо у встроенной навигации): `pan_buttons` — битмаска `cv_pan_{left,middle,right}` каких кнопок панорамируют (по умолчанию middle|right; кнопки **вне** набора приходят в `on_input` как pointer-события — так ПКМ становится вторичным цветом); `wheel_zoom` (по умолчанию true) — колесо зумит; при `false` колесо идёт в `on_input` (можно мапить на размер кисти или зумить только с Ctrl). Сеттеры: `set_pan_buttons`/`set_wheel_zoom`. Левая кнопка по-прежнему: сначала захват ползунка скроллбара, иначе рисование.
  - **Клавиатура через фокус.** Canvas теперь участвует в `FocusManager` (`FocusKind.canvas` + `register_canvas`/`focus_canvas` в `focus.v`, ветки в `blur_current`/`focus_index`/`is_entry_available`). Tool-press (любая не-pan кнопка) **захватывает фокус** (как клик по TextInput), клик мимо/по другому виджету — снимает. Пока холст в фокусе, `key_down`/`key_up` идут в `on_input` (кроме `Tab` — он листает фокус по UI); координата `x/y` в key-событии = пиксель под текущим курсором (читается из `app.get_active_ctx()`, т.к. key-события не несут координат мыши). `Esc` **не** делает авто-blur (в отличие от Slider) — он отдаётся инструменту (отмена незавершённой фигуры). `set_focus_group(n)` задаёт Tab-группу.
  - Python: `Canvas(on_input=...)` / `canvas.set_on_input(cb)`; колбэк получает объект `CanvasEvent` (поля `kind` `CanvasEventKind`, `x`, `y`, `in_image`, `button` `MouseButton`, `clicks`, `wheel_x/y`, `keycode`, `scancode`, `shift/ctrl/alt`, предикаты `is_down/is_move/is_up`). Новые экспорты из пакета: `CanvasEvent`, `CanvasEventKind`, `MouseButton`, `PanButton`.
- **Загрузка/сохранение изображений** (`load_file`/`load_data`/`save_file`). `load_file(path)` / `load_data(bytes)` декодируют картинку через `IMG_Load`/`IMG_Load_IO` (любой формат, который умеет SDL_image: jpg, png, webp, gif, tiff, bmp, ...), конвертируют поверхность в `ABGR8888` через `SDL_ConvertSurface`, **меняют размер холста** под размер картинки и копируют пиксели **построчно** (pitch поверхности может содержать выравнивающий паддинг — буфер холста плотно упакован). После загрузки `destroy_texture()` сбрасывает streaming-текстуру, чтобы `draw()` пересоздал её под новый размер (`ensure_texture` следит только за сменой рендерера, не размера). `save_file(path)` создаёт `SDL_CreateSurface(ABGR8888)`, копирует буфер построчно и пишет через generic `IMG_Save` — формат выбирается **по расширению файла**: png, jpg/jpeg, webp, gif, bmp пишутся; **tiff только читается** (SDL_image не умеет писать TIFF — `save_file` вернёт `False`, не упадёт). Все три возвращают `bool` успеха. Биндинги: `SDL_ConvertSurface`, `IMG_Save` + частичный `@[typedef] struct C.SDL_Surface` (только поля `w`/`h`/`pitch`/`pixels`) в `sdl3_bindings.v`. argtype Python для `load_data` — **`c_char_p`** (та же ловушка `bytes`→null); байты декодируются синхронно, поэтому view не клонируется.

`get_pixel` через границу capi возвращает `u32` packed `0xRRGGBBAA` (Python распаковывает в `(r,g,b,a)`). Демо: `vguipy/examples/45_canvas.py` и `examples/45_canvas.v` (paint поверх **единого `on_input`**: инструменты кисть/карандаш/ластик/пипетка/заливка/линия/прямоугольник; ЛКМ — основной цвет, ПКМ — вторичный (`set_pan_buttons(cv_pan_middle)`); Shift зажимает линию к 45° и прямоугольник в квадрат; клавиши 1-7 выбор инструмента, `[`/`]` размер кисти, `X` обмен цветов, `Esc` отмена фигуры; колесо — размер кисти, Ctrl+колесо — масштаб (`set_wheel_zoom(false)`); hover показывает координату и цвет под курсором; палитра, размер слайдером, load/save в нативном разрешении, панорама средней кнопкой + кнопки Вписать/+/−/1:1, инверсия через round-trip `get_pixels`/`set_pixels`).

## Системный трей (`tray.v`)

Трей — **не Widget**: у него нет `bounds`, нет `_kind`, он никогда не рисуется конвейером рендеринга и *не* зарегистрирован ни в одном из switch'ей `vgui_get_kind` / `set_widget_bounds` / добавления в контейнеры. Это объект уровня ОС, которым владеет `App`, построенный на API `SDL_Tray` из SDL3 (кроссплатформенно: StatusItem на macOS, AppIndicator/StatusNotifier на Linux, Shell_NotifyIcon на Windows). Требует SDL >= 3.2.

Ключевые моменты:
- `App.run()` обычно завершается, когда не открыто ни одного окна. Регистрация трея (`app.add_tray`) выставляет `keep_alive = true`, чтобы цикл переживал **сворачивание в трей** (все окна скрыты); выход тогда явный — через `app.quit()`.
- `C.SDL_UpdateTrays()` качается на каждой итерации цикла, когда `app.trays.len > 0` — на некоторых платформах (особенно macOS) это обязательно, чтобы изменения состояния пунктов вступали в силу.
- **Один базовый API, на замыканиях.** У `Tray` единственный набор методов для пунктов — `on_item(menu, label, fn ())` и `on_checkbox(menu, label, checked, fn (bool))` — принимающих обычные V-замыкания. Приватный `add_entry()` — единственный путь вставки (клонировать метку → `SDL_InsertTrayEntryAt` → `SDL_SetTrayEntryCallback` → push в `Tray.entries`). Трамплин `tray_entry_trampoline(userdata, entry)` восстанавливает `&TrayEntry` из `userdata` и вызывает его `on_click`/`on_toggle` — и больше ничего. Параллельного метода на `cb_id` у `Tray` намеренно **нет**.
- **Python едет по тому же пути, без дублирования.** capi-мост в `vgui-capi/vgui_capi.v` (`vgui_tray_add_item`/`vgui_tray_add_checkbox`) строит V-замыкание, пробрасывающее `cb_id` в Python-диспетчер (`fn [cb_id] () { g_py_click_dispatcher(cb_id) }`), и пропускает его через те же `on_item`/`on_checkbox`. То есть Python — тонкая обёртка над V-API: добавляя функциональность трея, добавляйте её сначала в V-API, Python подтянется. Каждый `TrayEntry` удерживается живым в `Tray.entries` всё время жизни процесса (сохраняет живыми и метку, и замыкание).
- Иконка: `vgui_tray_create(path, tooltip)` грузит через `IMG_Load`; `vgui_tray_create_with_data(bytes, len, tooltip)` декодирует сырые байты изображения через `IMG_Load_IO`. **ctypes argtype для данных иконки должен быть `c_char_p`, а не `c_voidp`** (та же ловушка `bytes`→null, что у данных шрифта). SDL копирует поверхность, поэтому vgui освобождает её сразу после create/set. Смена иконки в рантайме: `vgui_tray_set_icon(path)` / `vgui_tray_set_icon_data(bytes, len)`.
- **Встроенная иконка (без файла на диске).** V: `vgui.create_tray_embedded(data []u8, tooltip)` — в паре с `$embed_file('icon.png').to_bytes()` иконка запекается в бинарник (демо трея на V удалено при переезде на `examples/`). Python: передайте `Tray(app, icon_data=<png bytes>, tooltip=...)` (или `tray.set_icon_data(bytes)` в рантайме) — байты могут прийти из встроенного base64-блоба или `importlib.resources`, файл в рантайме не нужен (отдельного примера трея в `vguipy/examples/` сейчас нет). Оба пути идут через `load_tray_icon_data` → `IMG_Load_IO`; SDL декодирует в собственную поверхность, поэтому исходные байты должны жить только на время вызова.
- **События клика по иконке нет.** API `SDL_Tray` в SDL3 не доставляет приложению клики по иконке трея (на Linux/DBus левый клик всегда открывает меню; хука двойного клика нет). «Восстановление по двойному клику» поэтому кроссплатформенно нереализуемо — используйте пункт меню `Show window`. Не добавляйте API `on_activate`/двойного клика в расчёте, что оно заработает.
- Python: `Tray` наследует `TrayMenu` (трей *сам* является своим корневым меню). Подменю возвращают `TrayMenu`; передавайте его аргументом `menu` (nil/None-дескриптор меню маршрутизируется в корень). Отдельных примеров трея в `vguipy/examples/` / `examples/` сейчас нет (старые `demo29.py`/`demo45.v` удалены).

**Три неочевидных бага, пойманных при первой интеграции (все исправлены) — перепроверьте их, если трей регрессирует:**

1. **`Tray._handle` затирался в `None`.** Наследование `Tray(TrayMenu)`: `TrayMenu.__init__` присваивал `self._handle`, конфликтуя с собственным дескриптором трея. Теперь дескриптор меню — `self._menu`; `self._handle` — всегда `SDL_Tray*`. Симптом регрессии: `tray._handle is None`, и каждый `vgui_tray_add_*` молча ничего не делает (меню не строится, колбэки не срабатывают).

2. **Падение DBus на метке пункта (Linux).** DBus-бэкенд трея в SDL хранит **указатель на метку без копирования** (`entry_dbus->item->utf8 = label`). V-строка, построенная из временного Python-`bytes`, собиралась GC до сериализации меню → abort на ассерте `dbus_check_is_valid_utf8`. Исправление: `TrayEntry` владеет `label.clone()`, и SDL получает указатель в эту стабильную копию. `add_entry()` сохраняет клон в структуре (запушенной в `Tray.entries`) **до** вызова `SDL_InsertTrayEntryAt`. Та же ловушка времени жизни, что в заметке о данных шрифта выше.

3. **`win.show()` из колбэка трея не восстанавливал окно.** Окно, скрытое через `win.hide()` (или закрытое в трей), на X11 несёт ещё и флаг `MINIMIZED` (0x40); `SDL_ShowWindow` + `SDL_RaiseWindow` снимают `HIDDEN`, но **не** разворачивают из минимизации. `Window.show()` теперь вызывает `SDL_RestoreWindow`, если установлен флаг `sdl_window_minimized`, затем поднимает окно и рендерит. Заметка: `sdl_window_minimized = 0x40` отсутствовал в `sdl3_bindings.v` (был только `maximized = 0x80`) — пришлось добавить.

Плюс: клики по трею приходят через DBus и **не порождают SDL-событий**, поэтому цикл не отрендерил бы после того, как колбэк изменил состояние окна. Глобальный флаг `g_tray_activity` (выставляется в трамплине, потребляется в `sdl3_app.v`) форсирует один рендер в той итерации. Проверено и работает на KDE/X11 с DBus-бэкендом StatusNotifier в SDL3.

**Тесты.** `vgui-capi/tray_test.v`: `on_item`/`on_checkbox` без настоящего трея (ранний возврат `add_entry`) отдают пункт с обработчиком; на реальном трее пункты получают `handle`, попадают в `Tray.entries` (с подменю), клик доходит до обработчика; путь C-ABI `vgui_tray_add_*` доводит клик до Python-диспетчеров с нужным `cb_id`. Python - `test_tray.py`. Тесты с реальным треем пропускаются, если трея в системе нет (под dummy-драйвером он есть, если доступна сессия DBus). Оба набора ловят vlang/v#28864 («Компилятор V»): без обхода в `add_entry` V-тест падает на invalid memory access, Python - SIGSEGV.

**Ошибки DBus-бэкенда SDL 3.5 (найдены 22.09.2026, есть и в upstream main).** `SDL_ClickTrayEntry` вызывает у драйвера `GetTrayEntryEnabled` вместо `ClickTrayEntry` (`src/tray/unix/SDL_tray.c`) и ничего не делает - поэтому тест имитирует клик вызовом `tray_entry_trampoline(userdata, entry)`, как его доставляет SDL. `InsertTrayEntryAt` в `SDL_dbustray.c` сбрасывает флаги пункта в `NONE` и теряет `SDL_TRAYENTRY_CHECKED`: `add_checkbox(checked=True)` на Linux показывает флажок неотмеченным (`is_checked()` - `False`). Обхода в vgui пока нет.

## Undo/redo (`undo.v`)

Два уровня, как в Qt (встроенная отмена `QLineEdit` против `QUndoStack`); они не связаны между собой.

**Встроенная отмена виджетов — `UndoHistory[T]`.** Раньше `TextInput`, `TextArea`, `CodeEditor` и редакторы ячеек `TableView`/`TreeView` держали каждый свою копию одного алгоритма (две стопки снимков, `save_undo`/`perform_undo`/`perform_redo`, обрезка по лимиту). Теперь алгоритм один: обобщённая `UndoHistory[T]` (`save(snap)`, `undo(cur) ?T`, `redo(cur) ?T`, `clear`), а виджет решает только, что такое снимок (`snap()`) и как его восстановить (`restore()`). Снимок однострочного редактора — общий `RuneSnap` (буфер + курсор). Отмена по-прежнему снимочная, по одной правке на шаг; лимиты прежние (100 / 100 / 200 / 50 / 50). Публичные `undo()`/`redo()`/`can_undo()`/`can_redo()`/`clear_undo()` — у `TextInput`, `TextArea`, `CodeEditor` (C-ABI `vgui_<виджет>_undo` и т.д., Python — те же методы через `_TextUndo`): для пунктов меню «Правка». `set_text` историю забывает. У редакторов ячеек таблицы и дерева отмена живёт только пока идёт правка ячейки, наружу не выставлена.

Правило для правки: снимок кладётся **только если правка точно будет**. `save` обрывает ветку повтора, поэтому «снять снимок, а потом выкинуть» теряет redo. Так и было в `TextInput.insert`: вставка, из которой фильтр выкинул все символы, удаляла выделение без возможности отмены и стирала ветку повтора; сейчас проверки (`filter_runes`, место до `max_len`) идут до `save_undo`.

**Стек команд приложения — `UndoStack`** (аналог `QUndoStack`). `UndoCommand{text, merge_id, undo, redo, release}`; команды `[0, pos)` применены, `[pos, len)` — ветка повтора.

- `push(cmd)` выполняет `redo` и кладёт команду; `record(cmd)` кладёт уже выполненное действие. Новая команда обрывает ветку повтора.
- **Слияние** (`merge_id` != 0, тот же id у вершины): вершина превращается в контейнер (`merged`), новые команды — его дети. Отмена контейнера откатывает детей в обратном порядке, поэтому слияние корректно для любых команд — Qt-шный `mergeWith` не нужен. Через «чистое» состояние не сливается (иначе сохранённая точка поменялась бы задним числом).
- **Группы** `begin_group(text)`/`end_group()` вкладываются; команды внутри уже выполнены, группа ложится в стек как `record`. Пустая группа шага не даёт. Пока группа открыта, `can_undo`/`can_redo` — false.
- **Чистое состояние** `set_clean`/`is_clean` — для «документ изменён». Обрыв ветки повтора над ним или выброс по `limit` делают его недостижимым (`clean_index = -1`); выброс команд **ниже** него индекс просто сдвигает (состояние «после выброшенной» по-прежнему достижимо на pos 0).
- `limit` — сначала выбрасываются самые старые применённые команды, затем, если ветка повтора одна длиннее лимита, её конец.
- `release` вызывается, когда команда выброшена навсегда (обрыв, лимит, `clear`, `destroy`) — освободить ресурсы. В Python через него снимается регистрация колбэка.
- **Повторный вход запрещён.** Пока выполняется `undo`/`redo` команды (`busy`), `push`/`record`/`undo`/`redo`/`clear`/группы из её действий возвращают false.
- `on_change` — после любого изменения стека; `destroy()` его не зовёт.

**Мост в Python.** `UndoStack` — не виджет (как `Tray`): реестр-якорь `g_undo_stacks`, `vgui_undo_stack_destroy`. Одна команда — **один** `cb_id` на `INT_DISPATCHER`, действие кодируется аргументом: 0 — undo, 1 — redo, 2 — release (`vgui_undo_stack_push(ptr, text, merge_id, cb_id, execute)`). На release Python снимает id, поэтому реестр колбэков не растёт с историей. Тонкости:

- Обработчики команд лежат в глобальном `_lib._callbacks` и держат только маленький `_StackState` (живые id, флаг `running`, исключение), а **не** сам `UndoStack` — иначе стек не собирался бы, пока в нём есть шаги (тест `test_no_reference_cycle`).
- Python-`push` выполняет `redo` **сам**, затем кладёт команду через `execute=0`: исключение из `redo` пробрасывается естественно, а команда в стек не попадает. Исключение из действия при `undo()`/`redo()` обработчик запоминает и пробрасывает после возврата из C (пересечь границу C исключение не может); шаг при этом уже считается выполненным.
- `_destroy_now` сначала снимает свои id, потом зовёт V-destroy: release-вызовы находят `None` в реестре и безвредно отбрасываются.

Тесты — `undo_test.v` (история, стек, встроенная отмена виджетов) и `vguipy/tests/test_undo.py`. Демо — `52_undo_stack` (V и Python).

## Иконки элементов (`ItemIcon`, `item_icon.v`)

С 13.10.2026. Одна структура и один код отрисовки для иконок «внутри» виджетов: пункты меню
(`MenuItem` — значит, и `MenuBar`, `ContextMenu`, `MenuButton`), сам `MenuButton`, узлы
`TreeNode`, вкладки `TabBox`, строки `ListBox`, пункты `ComboBox`, заголовки секций
`Accordion`. Раньше каждый виджет держал своё `icon_path string` и сам звал
`load_icon_texture`, а глифы Lucide умели только `Icon` и `Button`.

`ItemIcon` — значение без ресурсов: источник `name` (Lucide) | `path` (файл) | байты (только
через `item_icon_data`, который их клонирует и считает ключ кэша `mem:<FNV-1a>:<длина>`) и
`color`. Приоритет при нескольких — в этом порядке; `ItemIcon{}` — иконки нет, и **место под неё
не резервируется** (`is_set()`). Рисует `ctx.draw_item_icon(ic, rect, size, fallback)`: квадрат
`size` по центру `rect`; глиф без своего цвета (`color.a == 0`) красится `fallback` — виджет
передаёт цвет текста элемента (выделенного, неактивного), поэтому глиф следует за темой и
состоянием. Картинки рисуются как есть. Размер иконки — у владельца (`icon_size`/`icon_gap`; у
`Accordion` — `title_icon_size`, потому что `icon_size` там — стрелка; у меню — константа
`menu_icon_sz` в колонке иконки, которая есть всегда). `measure()` учитывает иконку у
`MenuButton` и `ComboBox`; у `TreeView` — ширина содержимого для горизонтальной прокрутки.

Текстуры — в `RenderContext.icon_cache` окна (ключ — путь или `mem:...`), не вытесняются и
освобождаются вместе с кэшем текста (`clear_text_cache`), поэтому `is_renderer_alive_gen`
здесь не нужен. **Неудачная загрузка тоже кэшируется (nil)**: раньше битый путь читался с диска
на каждой отрисовке — так было с узлами файлового диалога, который хранил путь узла в
`TreeNode.icon_path` (`'dir:/a/b'`); путь переехал в `TreeNode.tag` (строка приложения, vgui её
не читает), а сам диалог позже удалён. Следствие кэширования
неудачи: файл, появившийся позже, подхватится только после сброса кэша. Байтовые иконки с
разным содержимым копят текстуры до закрытия окна — для анимированной смены иконок по кадрам
этот путь не годится.

Иконка строки `ListBox` живёт в `LbRow` и едет вместе со строкой при сортировке; рисуется в
первой колонке слева, текст выравнивается в остатке клетки. У ячеек-виджетов (`ListBox`,
`ComboBox`) иконка не рисуется. V API: фабрики `item_icon`/`item_icon_file`/`item_icon_data`,
`with_color`; `menu_action_lucide`, `MenuItem.set_icon`, `MenuButton.set_icon`,
`tree_node_with`, `TreeView.set_node_icon`, `TabBox.add_tab_icon`/`set_tab_icon`,
`ComboBox.add_icon_item`/`set_item_icon`, `ListBox.add_item_icon`/`set_row_icon`,
`Accordion.set_section_icon`. Старые фабрики с путём (`menu_action_icon`, `tree_node_icon`,
`add_tab_with_icon`...) оставлены и создают `item_icon_file`. `Button` и `Notification`
сохранили свои поля иконок. Мост — `vgui-capi/PROJECT.md`; Python — параметр `icon=` (имя
Lucide или `vguipy.ItemIcon`). Тесты — `item_icon_test.v`, `vguipy/tests/test_item_icon.py`;
пример — `examples/54_item_icons.v`.

## Тестовый инструмент (`testkit.v`) и снапшоты рендера

С 13.10.2026. Публичный инструмент для тестов интерфейса — и самой библиотеки, и приложений (через
C-ABI `vgui_test_*` и Python `vguipy.testing.UiTester`). Раньше каждый `_test.v` держал свою
копию окна, захвата кадра и построителя событий (каждый тест-файл компилируется отдельно, общий
код возможен только в модуле): три копии `SDL_RenderReadPixels`, ~10 вариантов `make_*_window`.

**Ввод — настоящим путём.** `sim_move`/`sim_press`/`sim_release`/`sim_click`/`sim_drag`/
`sim_wheel`/`sim_key`/`sim_text` кладут SDL-события в очередь (`SDL_PushEvent`, `windowID` окна) и
делают одну итерацию цикла: `app.process_events()` + `app.render_all()`. Значит, проверяется
всё, что работает у пользователя: `parse_sdl_event`, деление на `ui_scale`, область модальности,
горячие клавиши, фокус, `mouse_dbl_click` после `mouse_down` с `clicks >= 2`. Прямой
`dispatch_event_with_app`/`handle_event` этого не видит — он годится для юнит-проверки одного
виджета. Тонкости:
- координаты — **логические**, `sim_*` умножают их на `ui_scale` окна;
- модификаторы `parse_sdl_event` читает глобальным `SDL_GetModState()`, а не из события, поэтому
  `sim_pump` выставляет их `SDL_SetModState(mods)` на время разбора и сбрасывает после;
- колесо адресуется по последней позиции мыши (`ctx.mouse_x/y`) — `sim_wheel` сначала двигает
  указатель;
- `sim_text`: SDL хранит указатель на текст, а не копию — строка живёт, пока событие не разобрано
  (внутри того же вызова).

**`TestUi`** (`new_test_ui(width:, height:, theme:, ui_scale:)`) — App + окно на dummy-драйвере
SDL, светлая тема по умолчанию, `anim_fixed_dt` (анимации не зависят от скорости машины).
`add(w)` кладёт корень и рисует кадр (без кадра у виджетов нет bounds — попасть кликом
нельзя); `click_widget`/`center_of`, `settle(n)` — кадры, пока идут анимации; `close()` —
`app.cleanup()`. Каждому тесту — свой `TestUi` (`defer { t.close() }`).

**Кадр** — `capture_frame(mut win)`: читает persistent render target `Window.rt` (то, что на
экране), а не backbuffer после present — его содержимое SDL не гарантирует (под dummy оно
случайно стабильно). `Frame` — физические пиксели RGBA: `px`, `count(rect, color, tol)`,
`diff(other, tol)` → `FrameDiff{count, max_delta, size_mismatch}`, `save_png`,
`load_frame_png`.

**Снапшоты.** `match_frame_snapshot(f, path, tol:, max_pixels:)` / `t.match_snapshot(path)`:
эталона нет или `VGUI_UPDATE_SNAPSHOTS=1` — кадр записывается эталоном; расхождение больше
`max_pixels` пикселей (разница канала больше `tol`, по умолчанию 2) — ошибка с числами и
`<путь>.actual.png` рядом (в `.gitignore`); совпадение удаляет старый `.actual.png`.
`snapshot_test.v` — галерея виджетов (элементы управления, списки, текст, контейнеры) в обеих
темах, в том числе неактивная и при `ui_scale` 1.25 и 2; эталоны в `testdata/snapshots/`.
`snapshot_ui_test.v` — сцены с действием, описанные разметкой `.vui`: наведение (кнопка, тумблер под
полем, строка списка), нажатие, фокус после Tab, открытые выпадающий список и меню, CSS-стили.
**Перед сверкой каждая такая сцена проверяет, что кадр после частичных перерисовок совпадает с полной
перерисовкой** (иначе `<имя>.partial.png`): эталон, снятый полной перерисовкой, баги dirty regions не
увидел бы. Мышь перед действием уводится в угол — первое движение мыши в окне даёт полный кадр.
Эталоны снимаются **программным** рендерером SDL (драйвер `dummy`): его ошибки, которых нет на GPU,

перезаписать эталоны, посмотреть их глазами и закоммитить. **Намеренное изменение вида —
обновить эталоны в том же коммите.**

## Разметка интерфейса (.vui)

С 13.10.2026 (`ui_markup.v`) — замена удалённому YAML UI Builder. Цель — **файл читается глазами
как дерево окна**: одна строка — один элемент, вложенность — отступом, никаких ключей
`children:`/`type:`. Пример — `examples/43_notes.vui` + `43_ui_markup.v`.

```
vbox pad=12 gap=8
  hbox cross=center
    button "Сохранить" icon=save style=accent #save
    spacer flex=1
    toggle "Тёмная тема" #dark
  textarea #note flex=1 hint="Текст заметки"
  label @status.ready #status
```

**Строка** — тип, затем в любом порядке: `"текст"` (экранирование `\" \\ \n \t`),
`@ключ` — текст из перевода `tr('ключ')`, `#id`, `.класс` (для CSS, их может быть несколько; только
у виджетов — у `tab`, `item`, `node`... ошибка; см. «Стили CSS»), `ключ=значение` (слово до пробела или
`"строка"`), голое `слово` — флаг (`слово=true`; `true|false|yes|no|1|0`). Комментарий `//`
до конца строки вне кавычек. Отступ — только пробелы (таб — ошибка); ребёнок правее родителя,
соседи — строго на одном уровне. Корень один.

**Обработчики в разметке не пишутся** — намеренно: файл описывает вид, код находит элементы по
`#id` и вешает колбэки (`ui.get[Button]('save')!.on_click = ...`; Python —
`ui["save"].on_click(...)`). В YAML имена функций жили в строках, и опечатка всплывала только при
клике; здесь неверный `#id` или тип — ошибка сразу.

**Ошибки громкие, с местом**: `notes.vui:12: неизвестный элемент buton`, `свойство colr
неприменимо к label`, `#x уже есть в разметке`, `отступ не совпадает ни с одним уровнем выше`,
`style=fancy: допустимо normal|accent|...`, лишний текст, дети у листового элемента. Механизм:
каждое чтение свойства (`prop_*` в `UiBuilder`) отмечает его использованным, а `finish(n)` после
сборки элемента требует, чтобы использованы были все. Поэтому **свойство, которое строитель
забыл прочитать, — сразу ошибка «неприменимо»**, а не молчаливый пропуск. Свойства раскладки
(`flex`/`min`/`max`/`align`) читает родитель-бокс, поэтому `flex` у ребёнка `grid` или у корня —
тоже ошибка.

**Элементы и свойства** (`disabled` — у любого элемента, у контейнера гасит всё поддерево; см. «Неактивное состояние (enabled)»):

| Элемент | Текст | Свойства | Вложенные |
|---|---|---|---|

`__init__`; полноту проверяет `tests/test_markup.py` разбором `__init__` всех классов — новый
атрибут в классе виджета без правки списка роняет тест.

## Стили CSS (`css.v`, `css_props.v`, `css_apply.v`)

С 14.10.2026. Таблица стилей в синтаксисе CSS поверх темы: по типу элемента, `#id`, `.классу`,
с предками и состояниями. Пример — `examples/56_css_styles.v` + `56_styles.css` (hot-reload).

```css
:root            { --brand: #7c3aed; accent-color: var(--brand); border-radius: 10; }
.sidebar         { background: #1f1b2e; color: #e9e4ff; }   /* vbox: заливка + текст всего поддерева */
.sidebar list:selected { background: var(--brand); color: #fff; }
.danger          { background: #dc2626; color: #fff; }
#save:hover      { background: #8b5cf6; }
menu             { background: #222; }                     /* попап - корневое правило */
```

**Главная идея: CSS не вводит второго способа рисовать.** Каждое свойство сводится к полям `Theme`
(`button:hover background` → `button_hover`), а правило, подошедшее к виджету, рисует **его поддерево**
с изменённой копией темы (`RenderContext.draw_child`). Почему так: все виджеты уже берут цвета из
`ctx.theme` (сотни мест), и подмена темы сразу работает для всех ~50 типов без правки их `draw()`.
Следствия, которые важно помнить:

- **Состояния** (`:hover`, `:pressed`/`:active`, `:selected`, `:checked`, `:focus`, `:disabled`) — не
  проверка состояния при отрисовке, а **выбор другого поля темы**. Когда каким цветом рисоваться, виджет
  решает сам, как и без CSS. Поэтому состояние — только у последнего звена селектора (`.a:hover b` —
  ошибка), и у свойства без поля темы для этого состояния (`button:hover { color }`) — ошибка.
- **Наследование** получается само: тема действует на поддерево. `.sidebar { color }` красит весь текст
  внутри. Обратная сторона: правило на контейнере меняет и потомков, читающих то же поле.
- **Раскладку стили не трогают**: в CSS нет отступов, размеров, шрифтов. `measure()` от таблицы не
  зависит, смена таблицы — только перерисовка. Исключение — `--control-height`: влияет на `measure()`,
  поэтому разрешено только в `:root` (тема окна целиком; `apply_stylesheet` зовёт `invalidate_all`,
  а он взводит и `layout_dirty`); в обычном правиле — ошибка.
- Одно свойство может писать в несколько полей: `button { background }` пишет `button_bg`, `accent`,
  `error_color`, `success` — иначе на кнопке `style=accent`/`danger` оно не сработало бы. Побочного эффекта
  нет: копия темы живёт только на время отрисовки поддерева самой кнопки (но кольцо фокуса этой кнопки,
  выводимое из `accent`, тоже сменит цвет).

**Каскад.** Специфичность как в CSS (id > классы и состояние > типы), при равной — порядок в файле.
Правила сортируются **один раз при разборе** (`css_sort_rules`), отрисовка применяет подошедшие подряд.
Поля для каждого вида виджета тоже считаются при разборе (`CssDecl.fields_by_kind`), так что в кадре
нет поиска по таблице свойств — только сопоставление селекторов и запись полей.

**`draw_child` — контейнеры обязаны рисовать детей через неё**, не `w.draw(mut ctx)`. Указателя на
родителя у виджета нет («Дерево виджетов»), поэтому цепочка предков для селекторов вида
`.sidebar button` копится в `ctx.css_stack` по ходу обхода сверху вниз. Ребёнок, нарисованный мимо
`draw_child`, не получает своих правил (тема предка до него всё равно доходит) и не виден как предок для
своих детей. Через `draw_child` идут: корневые виджеты окна, `BoxLayout`, `Panel`, `Stack`, `Centered`,
`ScrollBox`, `GridLayout`, `Splitter`, `TabBox`, `Accordion`, ячейки-виджеты `ListBox` и `ComboBox`.
Внутренние части виджетов (поле ввода `Spinbox`, редактор `PropertyGrid`/`MarkdownView`) — намеренно
мимо: это детали реализации, селектор `input` не должен их задевать. Без таблицы стилей `draw_child` —
просто `w.draw()`; с таблицей, если ни одно правило не подошло, — без копии темы.

**Заливка контейнеров.** У `vbox`, `hbox`, `grid`, `scroll`, `stack`, `centered` нет своего цвета фона
в теме, поэтому `background` у них — не поле `Theme`, а заливка прямоугольника в `draw_child` перед
`draw()` (особое «поле» `@fill`); скругление — только если правило задало `border-radius`. У `panel`
`background` — это `panel_bg`.

**Корневые правила** — `:root` и голые `menu`, `tooltip`, `notification`, `dropdown` (выпадающий список
`ComboBox`). Они вшиваются в саму тему окна (`css_base_theme`), а не подменяются на время поддерева:
попапы и уведомления рисуются **после** дерева, через оверлей, когда подменённой темы уже нет. Поэтому
`menu`/`tooltip`/... с классами или предками — ошибка с подсказкой. `Window.config.theme` — тема без
стилей, `ctx.theme` — с корневыми правилами; `apply_theme` и `apply_stylesheet` всегда пересобирают
`ctx.theme` из `config.theme`, иначе корневые правила старой таблицы остались бы навсегда.

**Метки виджетов.** У каждой структуры виджета **вторым полем** (после `type_tag`) — `css CssTags`
(`id`, `classes`). Доступ без знания типа — интерфейс по полю `CssTagged`. **Менять через интерфейс —
только присваиванием поля целиком** (`w.css = tags`): `w.css.classes << x` через интерфейс компилируется,
но пишет во временную копию, и изменение молча теряется (V 0137eb5). Функции: `set_css_id`,
`add_css_class`, `remove_css_class`, `has_css_class`, `css_tags_of`; .vui заполняет метки из `#id` и
`.класс`. Как и все сеттеры, кадр не инвалидируют. Полноту поля проверяет `css_test.v` при компиляции.

**Окно и приложение** — как темы: `App.set_stylesheet(ss)` — всем окнам и диалогам без своей таблицы
и будущим (`App.set_stylesheet(nil)` — убрать стили); `Window.set_stylesheet(ss)` — своя (`css_explicit`).
**`Window.set_stylesheet(nil)` — назад к таблице приложения**, а не «без стилей»: указателя на `App` у окна
нет, поэтому `App.set_stylesheet` и `add_window`/`add_dialog` запоминают таблицу приложения в каждом окне
(`app_stylesheet`, `follow_app_stylesheet`), включая окна со своей таблицей. Окно без стилей при стилях
у приложения — пустая таблица `parse_stylesheet('', 'none')`.
`App.load_stylesheet(path, watch)`: при `watch` файл опрашивается в `pump_events` раз в 500 мс
(`poll_stylesheet`, по `mtime`), цикл `run()` просыпается минимум раз в 100 мс, так что опрос идёт и в
простое. **Ошибка в изменённом файле не роняет приложение**: печатается в stderr, стили остаются
прежними. Первая загрузка с ошибкой — ошибка `load_stylesheet`.

**Значения и ошибки.** Цвета `#rgb`, `#rgba`, `#rrggbb`, `#rrggbbaa`, `rgb()`, `rgba()` (альфа 0..1),
несколько имён; числа `8`/`8px`. `transparent` и альфа 0 — ошибка: тема читает альфу 0 как «не задано».
Переменные — только в `:root`, подставляются текстом при разборе (одна область на файл, не каскадом
по дереву). `--имя-поля: значение` — прямой доступ к любому полю `Theme` (`--lb-row-alt-bg`), без
состояния. Ошибки громкие, с местом: неизвестный тип/свойство/состояние (с перечнем допустимых свойств),
неверный тип значения, `!important`, `@media`, незакрытый блок, дубль свойства в блоке.

**Ограничения (намеренно, пока):** нет шрифтов, отступов, размеров; нет состояний предков
(`.panel:hover button`), `:not()`, `+`/`~`, атрибутов; переменные не каскадируются; попапы стилизуются
только корневыми правилами. C-ABI — vgui-capi/PROJECT.md, «Стили CSS»; Python — vguipy/PROJECT.md, «Стили CSS».

## Мост из фоновых потоков (`App.post`) и свой цикл событий

Вся vgui однопоточна (см. «Глобальное изменяемое состояние» ниже).

**Единственное исключение — `app.post(f fn ())` (`sdl3_app.v`), официальный мост из фоновых потоков.** Это ЕДИНСТВЕННАЯ функция vgui, которую можно звать из чужого потока: она кладёт замыкание в потокобезопасный канал `App.posted` (cap 64) и будит спящий в `WaitEventTimeout` цикл кастомным SDL-событием (`SDL_RegisterEvents`/`SDL_PushEvent` — потокобезопасны по контракту SDL). Замыкания выгребаются в `pump_events()` — то есть и в `run()`, и в своём цикле на `process_events()` — **в главном потоке**, между обработкой событий и рендером, поэтому внутри них доступна вся vgui, а рендер после них гарантирован. Контракт однопоточности этим не нарушается, а формализуется: фоновый поток по-прежнему не трогает ни виджеты, ни глобальное состояние — только канал. Данные в замыкание захватывать по значению; замыкания, отправленные после выхода из `run()`, не выполняются (остаются в буфере канала). Грабля V: канал объявлен как `chan Posted` (структура-обёртка) — `chan fn ()`, в том числе через type alias, **сегфолтится при push** в текущем V.

**Свой цикл событий вместо `run()` — `pump_events` / `render_all` (V), `app.process_events()` / `app.render_all()` / `app.is_running()` (Python).** `App.pump_events()` (`sdl3_app.v`) — это ровно та часть итерации `run()`, что предшествует рендеру: `process_events()` + `drain_posted()` + прокачка трея + `invalidate_all_windows()` после них; возвращает «что-то произошло, кадр стоит перерисовать». `run()` собран из неё же (`pump_events` + троттлинг 60fps + `render_all` + `update_running`), поэтому свой цикл не может «отстать» от штатного: он не теряет ни `post()`-замыканий, ни кликов по трею, ни авто-выхода при закрытии последнего окна (`update_running`; при `keep_alive` — не гасит). Capi: `vgui_app_process_events` (int-успех), `vgui_app_render_all`, `vgui_app_is_running`, `vgui_app_post(app, cb_id)` (колбэк без аргументов едет на существующем `CLICK_DISPATCHER`, отдельный диспетчер не нужен). `Dialog.exec()` (Python) тоже крутится через этот общий путь, а не через `vgui_dialog_process_events` — тот не выгребал `post()` и не качал трей, из-за чего на время модального диалога фоновый поток и трей молча замирали (сам экспорт оставлен для стороннего кода).

## Глобальное изменяемое состояние — контракт «единственного главного потока»

vgui построена на десятках `__global`-слайсов/map и предполагает **ровно один `App` на процесс**. Ничто из этого состояния не защищено мьютексом. **Это правильно, а не баг** — та же однопоточная реальность, описанная в «Контракте потоков» выше, действует на всю библиотеку: рабочих потоков нет нигде (нет `SDL_CreateThread`/`spawn`/`go` в боевом коде), весь цикл событий и каждый колбэк выполняются в одном потоке, создавшем `App`, а C-колбэки нативных диалогов SDL3 срабатывают синхронно внутри `SDL_PumpEvents` в том же потоке. Поэтому глобальное состояние трогается только из одного потока, и локи добавили бы накладные расходы, ничего не защищая.

Глобальное состояние по категориям (всё в ``):

- **Реестры объектов и указатели на диспетчеры моста** живут в модуле `vgui_capi` (vgui-capi/PROJECT.md, «Реестры объектов — якоря Boehm-GC»).
- **Монотонные счётчики + map ожидающих запросов** — `g_native_fd_counter`/`g_native_fd_requests` (`native_file_dialog.v`), `g_renderer_gen` (`sdl3_window.v`) и Python-`_cb_counter` (`_lib.py`). Id/поколения никогда не переиспользуются (защита от ABA); запоздавший колбэк брошенного id ничего не находит и отбрасывается.
- **Реестр живых рендереров** `g_live_renderers` (`sdl3_window.v`, пары указатель+поколение) — см. раздел о времени жизни текстур выше.
- **Состояние i18n** `g_tr_*` (подмодуль `i18n/i18n.v`) — текущая/запасная/исходная локаль, каталог переводов, загрузчик; `g_i18n_inited` (`i18n.v`) — `i18n_init()` идемпотентна. Пишутся при запуске (`set_locale`, `add_*`), дальше только читаются — `tr` безопасна из потоков (см. «Перевод интерфейса»).
- **Кэши / флаги** — `g_font_cache` (`font_cache.v`), таблицы имён месяцев/дней `cal_*` (`calendar.v`, после инициализации только чтение), `g_tray_activity` (`tray.v`).

**Контракт, сформулированный прямо:** вызывайте любую функцию vgui только из потока, создавшего `App` — кроме `app.post()`, которая существует ровно для того, чтобы фоновый поток мог передать работу главному (см. «Контракт потоков» выше). Не создавайте второй `App`. Если когда-нибудь появится настоящий фоновый поток, трогающий виджеты, вызывающий колбэки или запускающий диалоги, — **каждый** реестр/счётчик/map из списка выше (V-сторона) **и** `_callbacks`/`_cb_counter` (Python-сторона) должны уйти под локи; до тех пор ни один из них не защищён — намеренно (решение аудита №5).

Две второстепенные поверхности тоже проверены и безопасны как есть (аудит №6): **буфер обмена** (`vgui_app_{get,set}_clipboard` гоняет явный UTF-8 туда-обратно; SDL копирует буфер), **фильтры диалогов** (`_encode_filters` вычищает случайные `|`/`\n`, так что пользовательский ввод не может испортить проводной формат `"name|pat\n…"`) и **кодировки** в целом (каждая строковая граница capi использует явные `.encode("utf-8")`/`.decode("utf-8")`; `decode` на враждебном не-UTF-8 входе бросает исключение, а не ведёт себя неверно). Изменений там не требуется.
## Добавление нового виджета (часть библиотеки)

Полный чек-лист с C-ABI - vgui-capi/PROJECT.md, «Добавление нового виджета»; Python-класс - vguipy/PROJECT.md. В самой библиотеке:

- **первым полем** структуры - `type_tag int = kind_<name>`, константа - в `widget_kinds.v`, строка - в `widget_tag_test.v` («Тег типа виджета»); **вторым** - `css CssTags` (метки для CSS) и строка в `css_test.v` (`test_every_widget_type_has_css_tags`); имя типа для селекторов - в `css_kind_by_name` («Стили CSS»);
- контейнер рисует детей через `ctx.draw_child(mut w)`, а не `w.draw(mut ctx)` - иначе правила CSS с предками его не видят («Стили CSS»);
- реализовать `bounds_of()`/`set_bounds()` для нового типа в `widget_tree.v` (интерфейс `Layouted`) — **критично**: без этого `get_widget_bounds`/`set_widget_bounds` не узнают тип, поле `bounds` виджета никогда не выставляется движком компоновки, и он рендерится в (0,0) с нулевым размером, то есть невидим. Плюс, если новый тип — контейнер, реально держащий детей-`Widget`: `child_widgets()` (`HasChildren`); `arrange()` (`Arrangeable`) — bounds детям выставляются только там, не в `draw()` (см. «Фаза arrange»); `hit_children()` (`HitTestable`) — если `arrange()` выставляет `bounds` не всем детям, а только части (активная вкладка, развёрнутая секция, видимый диапазон строк); и собственное топ-уровневое поле `visible bool`, а не спрятанное во вложенной структуре (иначе `HasVisibility` его не увидит и `widget_at` будет попадать в скрытый виджет — та же ловушка, что у `HBox`/`VBox`). Добавьте заодно проверку в `widget_tree_test.v` — тест не самопроверяющийся, забытый тип он молча пропустит. См. раздел «Дерево виджетов» выше
- по желанию — `measure()` в `layout_measure.v`: без него виджет в `add(w)` занимает свободное место, а в окно по содержимому, `fit_to_content` и дорожки сетки входит своими текущими `bounds`. **Внутренний вспомогательный виджет без `measure()` в окне по содержимому ломает раскладку** (так было с `CpPreview` палитры: «растягивающийся во все стороны» ряд съедал высоту) — давайте `measure()` и им
