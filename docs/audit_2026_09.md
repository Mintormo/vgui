## 2. Ошибки

### 2.1. `FocusManager` никогда не отпускает виджеты

**Приоритет: 1 (чинить первым).** — **ИСПРАВЛЕНО 09.09.2026.** `FocusManager.unregister()`
(`focus.v`) снимает запись и корректирует `fm.current`; вызывается из
`vgui_destroy` через `capi_unregister_focus_everywhere` → `App.unregister_focus`
(обход `g_apps`, как у `capi_invalidate_everything`). `registered` стал
`map[voidptr]FocusKind`, и регистрация того же адреса с другим kind заменяет
запись — ABA закрыта. Тесты — `v/vgui/focus_test.v`; интроспекция —
`vgui_window_focus_count(win)`.

#### Симптом

Каждый виджет, который хоть раз отрисовался, остаётся в фокус-менеджере окна
навсегда — даже после `vgui_destroy`. Память не возвращается; уничтоженный
виджет продолжает участвовать в Tab-навигации; при переиспользовании адреса
возможна путаница типов.

#### Где

- [`v/vgui/focus.v:37`](../v/vgui/focus.v#L37) — `register_ptr()`: единственная
  точка входа. **Парной `unregister` в файле нет вообще.**
- [`v/vgui/focus.v:32`](../v/vgui/focus.v#L32) — `registered map[voidptr]bool`,
  вторая структура, которая тоже растёт вечно.
- [`v/vgui/vgui_capi.v:5770`](../v/vgui/vgui_capi.v#L5770) — `vgui_destroy`:
  удаляет виджет только из GC-якоря `g_*`, про фокус не знает.
- Регистрация происходит **из `draw()`** каждого focusable-виджета, например
  [`v/vgui/text_input.v:250`](../v/vgui/text_input.v#L250),
  [`v/vgui/button.v:160`](../v/vgui/button.v#L160),
  [`v/vgui/list_box.v:763`](../v/vgui/list_box.v#L763). То есть достаточно
  одного отрисованного кадра, чтобы виджет попал в реестр навсегда.

#### Почему так (механизм)

`libvgui.so` собрана с Boehm-GC языка V. `FocusEntry` хранит `voidptr` на
структуру виджета. Boehm — **консервативный** сборщик: он сканирует память и
считает всё, что похоже на указатель, живой ссылкой. Поэтому запись в
`fm.entries` **пинит** структуру виджета, и после `vgui_destroy` (который снял
якорь `g_buttons` и т.д.) она всё равно не собирается.

Из этого следуют три разных последствия:

1. **Утечка памяти** — по структуре виджета на каждый уничтоженный виджет,
   плюс запись в `entries` и ключ в `registered`.
2. **Логическая ошибка** — `tab()` может встать на уничтоженный виджет:
   `is_entry_available()` прочитает его поля (память валидна, объект
   осиротевший) и вернёт «доступен», а `focus_index()` выставит ему
   `focused = true`. Пользователь нажимает Tab и фокус «пропадает в никуда».
3. **ABA / путаница типов** — самое неприятное. Если аллокатор отдаст адрес
   освобождённой структуры под новый виджет **другого типа**, то:
   - `registered[ptr]` уже `true` → новый виджет **не зарегистрируется**
     (молча не попадёт в Tab-цикл);
   - старая запись хранит **старый** `kind` → `blur_current()`/`focus_index()`/
     `is_entry_available()` сделают cast чужого типа по этому адресу.

   Это ровно та дыра, от которой в проекте уже защищаются в двух других
   местах: монотонный `_cb_counter` в `_lib.py` и `renderer_gen` в
   `sdl3_window.v`. В `focus.v` защиты нет.

#### Доказательство

Замер: цикл «создать 30 кнопок → отрисовать кадр → `box.clear(destroy=True)`»,
200 повторов = 6000 виджетов. Мерилось `resource.getrusage().ru_maxrss`.
Полный скрипт — раздел 6.2.

| сценарий | прирост RSS |
|---|---|
| **с отрисовкой кадра** (регистрация в фокусе происходит) | **+10 МБ** |
| без отрисовки кадра (регистрации не происходит) | +2 МБ |

Разница ~8 МБ — это и есть удерживаемые фокусом уничтоженные кнопки
(~1.4 КБ на виджет: сама структура + `FocusEntry` + запись в map).

ABA проверена отдельным V-тестом (раздел 6.5): после `register_text_input(ti)`
и последующего `register_button` по **тому же адресу** запись в `entries`
остаётся `.text_input`, а `entries.len` не меняется.

#### Как чинить

1. В `focus.v` добавить:
   ```v
   pub fn (mut fm FocusManager) unregister(ptr voidptr) {
       if !fm.registered[ptr] { return }
       fm.registered.delete(ptr)
       for i, e in fm.entries {
           if e.ptr == ptr {
               fm.entries.delete(i)
               // current — индекс в entries: после delete он съезжает
               if fm.current == i { fm.current = -1 }
               else if fm.current > i { fm.current-- }
               break
           }
       }
   }
   ```
   **Внимание на `fm.current`** — это индекс, а не указатель; при удалении
   элемента его обязательно корректировать, иначе фокус «переедет» на соседа.
2. Вызвать `unregister` из `vgui_destroy` для всех focusable-kind. Виджет не
   знает своего окна (родительского указателя в vgui намеренно нет), поэтому
   проще всего обойти все окна и диалоги через `g_apps` — тем же приёмом, что
   уже используется в `capi_invalidate_everything` (см. CLAUDE.md, раздел про
   инвалидацию в сеттерах анимации).
3. Дополнительно закрыть ABA: добавить в `FocusEntry` поле `gen u64` из
   монотонного счётчика (как `g_renderer_gen`) **или** хранить `kind` и
   сверять его перед cast, возвращая «недоступен» при несовпадении. Второе
   дешевле и решает пункт 2.2 заодно.

#### Как проверить, что починено

- [x] Замер из раздела 6.2: было +10 МБ с отрисовкой против +2 МБ без,
      стало +5 МБ против +2 МБ на тех же 6000 виджетах (~1.4 КБ на виджет →
      ~0.25 КБ). `vgui_window_focus_count(win)` после уничтожения = 0.
      Остаточная разница не линейна по числу виджетов и на не-focusable
      виджетах (Label) воспроизводится тоже — это рост кучи Boehm, а не
      фокус-учёт: отдельный V-замер даёт +8 КБ на 200 000 циклов
      register/unregister.
- [x] Новый V-тест: `register` → `unregister` → `entries.len == 0`,
      `registered.len == 0`, `current == -1` (`focus_test.v`).
- [x] Новый V-тест на `fm.current`: зарегистрировать три виджета, встать
      фокусом на третий, снять первый — фокус остаётся на том же виджете
      (`test_current_follows_widget_when_earlier_entry_removed`; проверено,
      что тест падает, если убрать коррекцию индекса).

#### Осторожно

- `fm.current` используется в `is_focused()`, `tab()`, `activate_current()` —
  проверьте все места, где он сравнивается с индексом.
- `blur_current()` вызывается из `focus_index()` до смены `current`; если
  `unregister` вызвать в момент, когда `current` указывает на удаляемый
  элемент, blur должен либо отработать до удаления, либо быть пропущен —
  но не выполниться по уже удалённому индексу.

### 2.2. `MenuButton` регистрируется в фокусе как `Button` — чтение чужих смещений

**Приоритет: 2 (три строки, убирает UB).** — **ИСПРАВЛЕНО 09.09.2026.** Добавлен
`FocusKind.menu_button` + `register_menu_button`/`focus_menu_button` и ветки в
`blur_current` (сбрасывает `pressed`/`pressed_arrow`/`open`), `focus_index`,
`is_entry_available`; `menu_button.v` регистрируется своим kind. Заодно
MenuButton получил focus-ring (поле `focus_anim` было объявлено, но нигде не
использовалось) и `mark_anim` — без него анимации виджета замирали после
первого кадра под dirty regions. `activate_current` оставлена и
задокументирована: cast к `&Button` идёт после проверки kind, поэтому чужой
тип в фокусе просто даёт `false`.

#### Симптом

`MenuButton` никогда не доступен по Tab, а `blur_current()` пишет байт внутрь
чужого поля структуры `MenuButton`.

#### Где

[`v/vgui/menu_button.v:409`](../v/vgui/menu_button.v#L409), внутри `draw()`:

```v
if mb.enabled && !mb.no_focus {
    ctx.focus.register_button(unsafe { &Button(&mb) }, mb.focus_group)
}
```

Это **единственный** кросс-типовой cast во всей кодовой базе (проверено
grep'ом по всем `*.v`, кроме тестов).

#### Почему так (механизм)

`FocusManager` хранит `kind = .button` и во всех своих ветках трактует
`e.ptr` как `&Button`. Но по адресу лежит `MenuButton`, у которого другая
раскладка полей:

```
Button:      bounds Rect | text string | style ButtonStyle | visible | enabled | hovered | pressed | ...
MenuButton:  bounds Rect | text string | placeholder string | items []&MenuItem | style | visible | ...
                                        ^^^^^^^^^^^^^^^^^^^ расхождение начинается здесь
```

Замерено в V: `sizeof(Button) = 176`, `sizeof(MenuButton) = 240`.

#### Доказательство

Тест-зонд (раздел 6.5): менять `mb.visible`/`mb.enabled` и читать
`b.visible`/`b.enabled` через cast. Результат:

```
visible(true)->false, visible(false)->false, enabled(true)->false, enabled(false)->false
sizeof(Button)=176  sizeof(MenuButton)=240
```

То есть чтение по смещениям `Button` даёт `false` **всегда**, независимо от
реального состояния MenuButton.

#### Последствия

1. `is_entry_available()` всегда `false` → **MenuButton не участвует в
   Tab-навигации никогда**; регистрация бессмысленна и вводит в заблуждение.
2. `blur_current()` выполняет `b.pressed = false` — запись одного байта по
   смещению 39, что в `MenuButton` попадает внутрь строки `placeholder`
   (конкретно — в старший байт указателя `placeholder.str`). На x86-64
   пользовательские адреса меньше 2^48, поэтому старший байт и так нулевой —
   запись пока безвредна. Но это UB: изменится порядок полей в `Button` или
   `MenuButton` — и мы получим порчу указателя.
3. `activate_current()` ([`focus.v:436`](../v/vgui/focus.v#L436)) прочитал бы
   `b.on_click` по смещению `Button.on_click` и **вызвал бы его как функцию** —
   то есть прыжок по мусорному адресу. Сейчас эта функция **не вызывается
   ниоткуда** (проверено grep'ом), то есть мина стоит и ждёт того, кто
   реализует «Enter активирует кнопку в фокусе».

#### Как чинить

1. Добавить `menu_button` в `enum FocusKind` ([`focus.v:10`](../v/vgui/focus.v#L10)).
2. Добавить `register_menu_button`/`focus_menu_button` и по ветке в
   `blur_current()` ([`focus.v:183`](../v/vgui/focus.v#L183)),
   `focus_index()` ([`focus.v:257`](../v/vgui/focus.v#L257)),
   `is_entry_available()` ([`focus.v:364`](../v/vgui/focus.v#L364)).
   В blur разумно сбрасывать `mb.pressed`, `mb.pressed_arrow`, `mb.open`.
3. Заменить вызов в `menu_button.v:409` на новый метод.
4. Отдельно решить судьбу `activate_current()`: либо удалить как мёртвый код,
   либо реализовать корректно (через `kind`-диспетчеризацию, а не через один
   тип).

#### Как проверить

- [x] V-тест: скрытый/выключенный MenuButton → `is_entry_available == false`;
      видимый и включённый → `true` (`focus_test.v`,
      `test_menu_button_availability_follows_its_own_fields`), плюс
      `test_tab_reaches_menu_button`, `test_blur_menu_button_closes_its_menu`,
      `test_activate_current_ignores_non_button_kind`.
- [x] Вместо ручной проверки — пиксельный тест
      `test_menu_button_focus_ring_is_rendered` (`render_dirty_test.v`,
      переиспользует capture_rgba/diff_count): после кадра запись в фокусе
      лежит с kind `.menu_button`, а сфокусированный MenuButton меняет 1057
      пикселей с max diff 142. Порог отделяет доигравшую анимацию от замершей
      (без `mark_anim` — max 26).

### 2.3. Утечка шрифтов при изменении `ui_scale`

**Приоритет: 4.** — **ИСПРАВЛЕНО 14.09.2026.** Выбран не LRU и не квантование,
а подсчёт ссылок: `FontSet` получил `refs`/`cache_key`, каждое окно держит ровно
одну ссылку (`get_or_load_fonts` берёт, `release_fonts` отдаёт), последний
владелец закрывает все `TTF_Font` набора вместе с `size_cache` и удаляет запись.
`set_ui_scale` и HiDPI идут через общий `Window.reload_scaled_fonts()`: сначала
берётся новый набор, потом отпускается старый, так что соседнее окно с тем же
набором не страдает. Ключ кэша — FNV-1a по содержимому буфера плюс длина, хит
проверяется сравнением байтов (коллизия даёт отдельный набор, а не чужой шрифт).
Попутно найден и закрыт смежный баг: `reload_fonts_for_dpi` на HiDPI
переинициализировал **общий** `FontSet` на месте — старые хэндлы текли, а у
второго окна с тем же набором шрифт удваивался. Тесты — в
`text_font_cache_test.v`.

#### Симптом

Каждое **уникальное** значение `ui_scale` навсегда добавляет в память один
`FontSet` с шестью открытыми `TTF_Font`. Плавный зум колесом «съедает» десятки
мегабайт за один жест.

#### Где

- [`v/vgui/sdl3_window.v:1282`](../v/vgui/sdl3_window.v#L1282) — `set_ui_scale`:
  считает `scaled_font = base_font * dpi_scale * s` и зовёт `get_or_load_fonts`.
- [`v/vgui/font_cache.v`](../v/vgui/font_cache.v) — `g_font_cache`,
  ключ включает размер шрифта; освобождение только в `destroy_font_cache()`,
  который вызывается один раз, в `App.cleanup()`.
- [`v/vgui/render_context.v:37`](../v/vgui/render_context.v#L37) —
  `FontSet.size_cache`, тоже ничем не ограничен.

#### Почему так

`get_or_load_fonts` — кэш «на всю жизнь процесса», рассчитанный на то, что
разных конфигураций шрифтов немного (одна-две на приложение). Но масштаб
входит в размер, а размер входит в ключ — и кэш превращается в накопитель.

#### Доказательство

Замер (окно 400×300, 20 меток; полный скрипт — раздел 6.3):

```
RSS база:                           25 МБ
после 70 разных ui_scale:           63 МБ   (+38 МБ, ~0.55 МБ на масштаб)
после 70 повторов трёх масштабов:   63 МБ   (+0 — кэш при попадании работает)
```

70 значений — это один жест Ctrl+колесо с шагом 0.05 в диапазоне 0.5–4.0.
Именно такой зум предлагает `python/examples/45_canvas.py`.

#### Как чинить

Варианты (можно комбинировать):

1. **LRU-эвикция `g_font_cache`**: держать не больше N (скажем, 4) FontSet;
   при вытеснении закрывать все `TTF_Font` вытесняемого набора, включая
   `size_cache`. Осторожно: FontSet шарится между окнами — нужен счётчик
   ссылок или проверка, что ни один живой `RenderContext` на него не смотрит.

### 2.4. Один слот `overlay_cb` на окно, и он держит указатель виджета

**Приоритет: 6.** — **ИСПРАВЛЕНО 14.09.2026.** Выбран вариант «слот с
владельцем», а не стек: подменю и так живут внутри `MenuState`, а два
независимых попапа одновременно на десктопе не показывают. Новый `overlay.v`:
`ctx.set_overlay(owner, draw, ev, close)` сначала закрывает попап **другого**
владельца его close-хуком, `ctx.clear_overlay(owner)` чистит слот только свой.
Попутно закрыта вторая половина бага: `close_dropdown`/`MenuState.close_all`
обнуляли слот без проверки и стирали чужой оверлей (например, ComboBox,
закрываясь по потере фокуса из `draw()`, стирал уже открытое ContextMenu).
`vgui_destroy` → `capi_release_overlay_everywhere` → `App.release_overlay`
снимает оверлей во всех окнах и диалогах. Описано в PROJECT.md, «Оверлеи
попапов»; тесты — `v/vgui/overlay_test.v`.

#### Симптом

Два одновременно открытых попапа затирают друг друга (нижний «залипает» в
состоянии `open = true`, но не рисуется и не получает событий). Уничтожение
виджета с раскрытым попапом оставляет оверлей на экране.

#### Где

- [`v/vgui/render_context.v:56-57`](../v/vgui/render_context.v#L56) —
  `overlay_cb` / `overlay_ev`: **по одному полю на окно**.
- Пишут в них: `combo_box.v:359` и `:438`, `menu_button.v:186` и `:195`,
  `menu.v:650/659` (ContextMenu) и `menu.v:1027/1036` (MenuBar).
- Чистят: только `combo_box.v:302` и `menu.v:598` — то есть сам виджет при
  закрытии. `vgui_destroy` про оверлей не знает.

#### Почему так

Замыкание захватывает `mut cb` (указатель на конкретный виджет). Поле одно, а
претендентов четыре. Присвоение второго попапа просто перетирает первый — и
первый уже никогда не узнает, что он «закрыт», потому что его `overlay_ev`
больше не вызывается.

Уничтожение виджета с открытым попапом оставляет замыкание в поле; оно держит
указатель, Boehm не даёт структуре умереть (как в 2.1), и `render()`
продолжает вызывать `overlay_cb` каждый кадр — рисуя выпадающий список от
логически мёртвого ComboBox.

#### Как чинить

1. Минимально: чистить `overlay_cb`/`overlay_ev` в `vgui_destroy` для
   kind 16 (ComboBox), 28 (MenuButton), 30 (ContextMenu), 31 (MenuBar) —
   если текущий оверлей принадлежит уничтожаемому виджету. Чтобы это
   определить, придётся хранить рядом с колбэком владельца:
   `overlay_owner voidptr`.
2. Правильно: заменить одну ячейку стеком попапов
   `overlays []OverlayEntry{owner voidptr, draw fn, ev fn}` — тогда
   `render()` рисует их снизу вверх, а события идут сверху вниз до первого
   поглотившего. Заодно решается вложенное меню (подменю поверх меню).

#### Как проверить

- [x] Открыть ComboBox, не закрывая его — открыть ContextMenu правой кнопкой.
      Оба должны вести себя корректно (либо первый закрывается явно, либо оба
      отображаются в правильном порядке). — Первый закрывается явно:
      `test_context_menu_preempts_open_combo`, `test_combo_preempts_menu_button`,

### 2.5. `app.process_events()` / `render_all()` / `post()` в Python не существуют

**Приоритет: 3.** — **ИСПРАВЛЕНО 10.09.2026.** В `sdl3_app.v` шаг цикла вынесен
в `App.pump_events()` (события + `drain_posted` + трей + инвалидация), рядом
`update_running()`/`needs_animation_now()`; `run()` собран из них же, так что
свой цикл не может отстать от штатного. Экспортированы
`vgui_app_process_events` / `vgui_app_render_all` / `vgui_app_is_running` /
`vgui_app_post` (последний едет на существующем `CLICK_DISPATCHER`).
В Python добавлены `App.process_events()`, `App.render_all()`, `App.post(fn)`
(одноразовый колбэк, снимается в `finally`), а `App.is_running()` перестал быть
фикцией и читает флаг из V. `Dialog.exec()` переведён на этот же общий путь.
Демо — `python/examples/49_background_thread.py`.

#### Симптом

Документированный сценарий «свой цикл событий» не работает: код из docstring
падает с `AttributeError`. Фоновый поток в Python не имеет легального способа
что-либо сообщить UI.

#### Где

- [`python/vguipy/window.py:357`](../python/vguipy/window.py#L357) — docstring
  класса `Dialog` содержит пример:
  ```python
  while app.is_running() and dlg.is_open():
      app.process_events()   # AttributeError: 'App' object has no attribute 'process_events'
      app.render_all()       # AttributeError
  ```
- [`python/vguipy/window.py:204`](../python/vguipy/window.py#L204) — docstring
  `Window.invalidate` ссылается на те же несуществующие методы.
- `CLAUDE.md` упоминает `app.process_events()` в описании контракта потоков и
  в разделе про инвалидацию.
- [`python/vguipy/app.py`](../python/vguipy/app.py) — реально есть только
  `run()`, `quit()`, `is_running()`, `add_window()`, `add_tray()`,
  `set_keep_alive()`, буфер обмена, тема.
- В `vgui_capi.v` экспортов `vgui_app_process_events` / `vgui_app_render_all` /
  `vgui_app_post` **нет**; есть только `vgui_dialog_process_events`
  (он и качает цикл внутри `Dialog.exec()`).

Проверено: `hasattr(app, 'process_events') == False`, `render_all == False`,
`post == False`.

#### Почему это важно

1. Публичные `Window.invalidate()` / `invalidate_all()` были добавлены именно
   для случая «пользователь крутит свой цикл». Без `process_events`/`render_all`
   этот случай из Python недостижим — API есть, а применить его негде.
2. **`app.post()` — единственный официальный мост из фонового потока** (см.
   CLAUDE.md, «Контракт потоков») — тоже только в V. А `ctypes.CDLL` отпускает
   GIL на время `vgui_app_run`, поэтому фоновый Python-поток спокойно вызовет
   `label.set_text(...)` во время работы цикла и тихо нарушит однопоточный
   контракт vgui. Ничто об этом не предупреждает — ни исключение, ни
   документация на стороне Python.
3. От этого же зависит поведение Ctrl+C (см. 2.6).

#### Как чинить

1. В `vgui_capi.v` добавить:
   ```v
   @[export: 'vgui_app_process_events']
   pub fn vgui_app_process_events(app_ptr voidptr) int {
       if app_ptr == unsafe { nil } { return 0 }
       mut app := unsafe { &App(app_ptr) }
       return if app.process_events() { 1 } else { 0 }
   }

   @[export: 'vgui_app_render_all']
   pub fn vgui_app_render_all(app_ptr voidptr) { ... app.render_all() }
   ```
   `process_events`/`render_all` сейчас приватные (`fn (mut app App) ...` в
   `sdl3_app.v`) — их нужно сделать `pub` либо звать через тонкую обёртку в
   том же модуле.
2. `vgui_app_post(app_ptr, cb_id u64)` — строит замыкание
   `fn [cb_id] () { g_py_click_dispatcher(cb_id) }` и передаёт в `app.post()`.
   **Новый диспетчер не нужен** — подходит существующий `CLICK_DISPATCHER`.
   Важно: колбэк должен сниматься с регистрации после выполнения (иначе
   `_callbacks` будет расти на каждый post), либо документировать, что
   `App.post` регистрирует одноразовый колбэк и удаляет его в обёртке
   диспетчера.
3. В `python/vguipy/app.py` добавить `process_events()`, `render_all()`,
   `post(fn)`; в `_lib.py` — три `_sig(...)`.
4. Дописать в README/CLAUDE.md явный абзац для Python-пользователя: «vgui
   однопоточна; из другого потока можно вызывать только `app.post()`».

#### Как проверить

- [x] Пример из docstring `Dialog` выполняется как написано (проверено:
      `dlg.show()` + ручной цикл возвращает результат, `exec()` — тоже).
- [x] Новый пример `python/examples/49_background_thread.py`: поток считает,
      через `app.post` обновляет `ProgressBar`, UI не подвисает.
- [x] Реестр колбэков не растёт: 5 post-ов подряд → `len(_callbacks) == 0`.
- [x] Docstring'и `Dialog` и `Window.invalidate` больше не врут — методы есть.

### 2.6. Ctrl+C не завершает `app.run()`

**Приоритет: 3 (решается вместе с 2.5).** — **ЗАКРЫТО 10.09.2026 основным
путём:** цикл на `app.process_events()` прерывается штатно (проверено
`kill -INT`: `KeyboardInterrupt` ловится, процесс выходит), потому что
`process_events` блокируется не дольше 100 мс. Сам `vgui_app_run` остался
блокирующим и по Ctrl+C по-прежнему не выходит — это задокументировано
в docstring `App.run()` и в CLAUDE.md; отдельный quit-флаг/перехват SIGINT
не заводился (см. «Как чинить» ниже — не нужен при наличии своего цикла).

#### Симптом

Пример, запущенный из терминала, не закрывается по Ctrl+C — процесс приходится
убивать `kill -9`.

#### Доказательство

Запустил `app.run()` фоном, отправил `SIGINT`, подождал 4 секунды — процесс
жив (`kill -0` успешен). Скрипт — раздел 6.4.

#### Почему так

`vgui_app_run` — блокирующий вызов в C. ctypes отпускает GIL, Python-обработчик
`SIGINT` только выставляет флаг, а исполняется он лишь при возврате управления
в интерпретатор — то есть после выхода из `run()`. Цикл V об этом флаге не
знает. SDL свой обработчик сигналов не ставит (Python установил свой раньше).

#### Как чинить

- Основной путь — 2.5: цикл, написанный на Python поверх `process_events()`,
  прерывается штатно между итерациями.
- Дополнительно можно завести `vgui_app_set_quit_flag_ptr` или проверять
  в `run()` флаг, который выставит Python-обработчик сигнала. Это сложнее и
  вряд ли нужно, если появится `process_events`.
- Минимум — задокументировать: «закрывайте окно или зовите `app.quit()`;
  Ctrl+C во время `app.run()` не сработает».

## 3. Архитектурные вопросы

Это не баги — это решения, которые сегодня работают, но ограничивают развитие.
Каждое стоит держать в голове при следующем крупном рефакторинге.

### 3.A. Раскладка выполняется внутри `draw()`

[`v/vgui/containers.v:254`](../v/vgui/containers.v#L254) — `draw_impl` первым
делом зовёт `b.layout(ctx)` ([`containers.v:109`](../v/vgui/containers.v#L109)).
Отдельной фазы arrange не существует. Следствия:

1. **Раскладка всего дерева пересчитывается каждый кадр**, включая
   `measure_widget()` для `.auto`-детей и для любого ребёнка с
   `align != .stretch` — а это обращения к метрикам TTF. Кэша измерений нет.
2. **Hit-тест работает по bounds прошлого кадра.** Отсюда целый класс уже
   описанных в CLAUDE.md проблем (`HitTestable`, устаревшие bounds неактивных
   вкладок, видимый диапазон `ListBox`). Важно понимать: это не отдельные
   частные баги, а симптом одной причины — состояние раскладки является
   побочным эффектом отрисовки.
3. **С появлением dirty regions добавился новый эффект:** в ветке `skip_draw`
   `layout()` не вызывается вообще, то есть актуальность раскладки теперь
   зависит ещё и от того, был ли кадр «грязным».

Направление: флаг `layout_dirty` + отдельный проход `arrange()` перед циклом
отрисовки, плюс кэш `SizeHint` с инвалидацией по изменению текста, шрифта,
темы и размеров.

- [x] вынести `layout()` из `draw()` в отдельную фазу — сделано 14.09.2026:
      `Arrangeable.arrange()` у всех контейнеров, `Window.arrange()` перед
      каждым рисуемым кадром (и в `skip_draw` по `ctx.layout_dirty`) и лениво
      перед каждым событием; шаг анимации Accordion перенесён в `arrange()`
      (раз за `ctx.frame_no`). Тест — `v/vgui/arrange_test.v`. Отрисовка
      остаётся консервативной: `layout_dirty` взводит любая инвалидация.
- [x] кэшировать `SizeHint` виджета — сделано 16.09.2026: кэш на один
      **проход измерения** (`v/vgui/measure_cache.v`). Проход открывает
      `Window.arrange()`, а измерение «с нуля» вне arrange — само
      (`g_measure_depth == 0 && ctx.arrange_depth == 0`), поэтому hint
      из прошлого кадра не всплывает и инвалидация по тексту/шрифту/теме
      не нужна: внутри прохода это не меняется. Ключ — адрес объекта за
      интерфейсом (`unsafe { &WidgetTagHeader(w) }`, снимается до сужения
      типа в `if w is Measurable`); разовая самопроверка сверяет его
      с адресом известного `&Label{}` и при расхождении выключает кэш
      целиком. Деградация к `bounds` (виджет без `measure()`) не
      кэшируется — bounds меняются в том же проходе. Тест —
      `v/vgui/measure_cache_test.v`. Замер — 6.8: на дереве глубины 8
      измерение стало быстрее в ~45 раз.

### 3.B. `kind` — непроверяемый тег типа

`vgui_resolve_widget` ([`vgui_capi.v:3640`](../v/vgui/vgui_capi.v#L3640))
делает `unsafe { &Label(ptr) }` по целому числу, пришедшему из Python. Никакой
верификации, что по адресу лежит именно `Label`, нет и быть не может. Любое
расхождение — неверный `_kind` в стороннем классе, сырой handle из
`tree.widget("id")`, ошибка в другом языке-биндинге — даёт порчу памяти
без единого шанса её заметить.

Дешёвое решение: общий заголовок у каждой структуры виджета — первое поле
`kind int`, проставляемое фабрикой. Тогда резолвер сверяет тег и возвращает
`none` вместо cast. Цена — одно поле в структуре и одно сравнение на вызов;
выигрыш — целый класс ошибок превращается в понятный `TypeError` на стороне
Python. Заодно это закрывает 2.2 (MenuButton) на уровне механизма.

- [x] добавить тег типа в структуры виджетов и проверку в `vgui_resolve_widget`
      — сделано 15.09.2026. Первое поле каждой из 51 структуры виджета —
      `type_tag int = kind_<name>`; значение по умолчанию проставляется при
      любом создании (фабрика, литерал `&Label{}`, сборка из YAML), поэтому
      шага «не забыть записать тег» в фабриках нет. `vgui_resolve_widget`
      сверяет тег с пришедшим `kind` и при расхождении возвращает `none`
      вместо каста. `widget_tag_test.v` проверяет тег и смещение 0 для всех
      типов. Python: экспорт `vgui_widget_tag` + `_check_added` отличает
      «kind не добавляется в контейнеры» от «`_kind` врёт про объект».
      Не закрыто тегом: висячий указатель (в освобождённой памяти тег может
      уцелеть) и прямые касты в узких capi-функциях, куда `kind` не приходит.

### 3.C. Dirty regions почти не работают на практике

даёт основную часть выгоды: на `mouse_move` инвалидировать только
прямоугольники виджета, потерявшего hover, и виджета, получившего его.

### 6.1. Сверка C-ABI (сегодня даёт 0 расхождений)

```python
#!/usr/bin/env python3
"""Сверяет экспорты vgui_capi.v с объявлениями _sig(...) в _lib.py."""
import re

v = open('v/vgui/vgui_capi.v').read()
vfuncs = {}
for m in re.finditer(r'^pub fn (vgui_\w+)\(([^)]*)\)\s*([\w&\[\]\. ]*)\s*\{', v, re.M):
    params = [p.strip().split()[-1] for p in m.group(2).split(',') if p.strip()]
    vfuncs[m.group(1)] = (params, m.group(3).strip())

py = open('python/vguipy/_lib.py').read()
sigs = {}
for m in re.finditer(r'_sig\(\s*"(\w+)"\s*,\s*\[([^\]]*)\]\s*(?:,\s*([\w\.]+))?\s*\)', py, re.S):
    args = [a.strip() for a in m.group(2).split(',') if a.strip()]
    sigs[m.group(1)] = (args, m.group(3))

MAPV = {'voidptr':'p','&char':'p','&u8':'p','&f32':'p','&int':'p','int':'i',
        'f32':'f','u64':'u','u8':'b','bool':'i','u32':'u32'}
MAPP = {'c_voidp':'p','c_charp':'p','c_int':'i','c_float':'f','c_uint64':'u',
        'c_uint8':'b','c_uint32':'u32','ctypes.c_bool':'i'}

print('V-экспортов:', len(vfuncs), ' _sig:', len(sigs))
print('в V, но не объявлено в Python:', sorted(set(vfuncs) - set(sigs)))
for name, (al, ret) in sigs.items():
    if name not in vfuncs:
        print('  объявлено в Python, но нет в V:', name); continue
    vp, vr = vfuncs[name]
    if len(al) != len(vp):
        print(f'  АРНОСТЬ {name}: py={len(al)} v={len(vp)}'); continue
    for i, (a, b) in enumerate(zip(al, vp)):
        pa, pb = MAPP.get(a, '?'), MAPV.get(b, '?')
        if pa != '?' and pb != '?' and pa != pb:
            print(f'  ТИП {name} arg{i}: py={a} v={b}')
    vrk = MAPV.get(vr, 'void' if vr == '' else '?')
    prk = MAPP.get(ret) if ret else 'void'
    if (vr == '') != (ret is None) or (vrk != '?' and prk not in (None, '?') and vrk != prk):
        print(f'  RESTYPE {name}: v={vr!r} py={ret!r}')
```

### 6.8. Замер кэша `SizeHint` (проверка второго пункта 3.A)

Разовый зонд `v/vgui/zz_bench_test.v` (после замера удалён; module vgui —
иначе не видно приватных функций). Кэш выключается присваиванием
`g_measure_cache_ok = -1`, поэтому «до» и «после» меряются в одном запуске:

```v
module vgui

import time

fn build_tree(depth int, fanout int) &VBox {
	mut box := create_vbox_fill()
	if depth == 0 {
		for i in 0 .. fanout {
			mut ic := icon('a')
			ic.size = 16 + i
			box.add_auto(ic)
		}
		return box
	}
	for _ in 0 .. fanout {
		box.add_auto(build_tree(depth - 1, fanout))
	}
	return box
}

fn bench(root &VBox, ctx &RenderContext, iters int) i64 {
	sw := time.new_stopwatch()
	for _ in 0 .. iters {
		measure_pass_enter()
		measure_widget(root, ctx)
		measure_pass_leave()
	}
	return sw.elapsed().microseconds()
}

fn test_bench_measure_cache() {
	ctx := &RenderContext{
		screen_width:  800
		screen_height: 600
	}
	shapes := [[2, 3]!, [4, 3]!, [6, 2]!, [8, 2]!]
	for sh in shapes {
		root := build_tree(sh[0], sh[1])
		bench(root, ctx, 3) // прогрев
		g_measure_cache_ok = 1
		with_cache := bench(root, ctx, 20)
		g_measure_cache_ok = -1
		without := bench(root, ctx, 20)
		g_measure_cache_ok = 1
		println('глубина ${sh[0]}, fanout ${sh[1]}: с кэшем ${with_cache} мкс, без кэша ${without} мкс (20 проходов)')
	}
	assert false // иначе V не печатает stdout прошедшего теста
}
```

Запуск: `cd v && SDL_VIDEODRIVER=dummy VFLAGS="-enable-globals" ~/soft/v/v test vgui/zz_bench_test.v`.

Результат (16.09.2026, вложенные `VBox` с `add_auto`, 20 проходов измерения):

| дерево | без кэша | с кэшем | выигрыш |
|---|---|---|---|
| глубина 2, fanout 3 | 656 мкс | 606 мкс | ~1.1× |
| глубина 4, fanout 3 | 14 565 мкс | 6 117 мкс | 2.4× |
| глубина 6, fanout 2 | 33 787 мкс | 3 384 мкс | 10× |
| глубина 8, fanout 2 | 533 332 мкс | 11 686 мкс | **45×** |

Ровно та картина, из-за которой пункт и заводился: без кэша стоимость
измерения растёт с глубиной экспоненциально (каждый уровень спрашивает
ребёнка дважды — `content_size()` и `child_main_item()`), с кэшем —
линейно по числу виджетов. Замер сделан на `Icon`, то есть **без**
шрифтовых метрик; в реальном UI с текстом экономия больше, потому что
повторное измерение `Label`/`Button` идёт в `TTF_GetStringSize`.
